# 批量任务可执行性检查

## 目标

部分任务是否需要执行只取决于当前用户的 Profile，无需进入游戏确认。批量调度必须在
条目准备之前完成这些判定，避免先启动应用、登录角色，再发现所有任务均不需要执行。

## 责任边界

- 业务工作流拥有判定规则，通过文件头 `batch_check` 指向同文件内的 DSL 子过程。
- 批量调度器只负责按元数据调用子过程，并解释通用的 `success` / `skipped` 协议；
  不理解 Profile 字段、额度或游戏页面。
- 条目准备与收尾工作流继续通过自己的 `#% parameters` 声明能力参数。批量引擎只注入
  参数，不内置“重启应用”“停止应用”等行为。
- 直接运行业务工作流不会隐式调用批量检查子过程。

## 执行语义

1. 每个用户、每个轮次，在条目准备之前逐个检查任务。
2. 未声明 `batch_check` 的任务默认可以执行。
3. 返回 `skipped` 表示该任务本身没有提供登录该用户的理由；检查异常或协议错误不算可执行。
4. 至少一个任务可执行时，正常运行条目准备、全部选中任务与条目收尾。前置检查不是任务
   过滤器，避免登录后漏掉用于刷新共享 Profile（例如货币数据）的扫描任务。
5. 没有任何任务可执行时，忽略该用户，不运行条目准备与收尾。
6. 检查接收启动时冻结的任务参数，不在运行中重新读取任务配置。

## 花蕊织

`weekly_huaruizhi.wf` 的批量检查先通过全局 Profile 注册表幂等声明
`huaruizhi_of_week`，再读取进度。达到 3000 时返回跳过；
任务正文仍保留进入渡尘墟后同步实际进度并阻止多开一局的保护。通用
`prepare_item.wf` 通过默认关闭的“不在登录页时重启应用”参数提供花蕊织轮次所需的
现场恢复能力，批量目录不再保留花蕊织专用生命周期工作流。
