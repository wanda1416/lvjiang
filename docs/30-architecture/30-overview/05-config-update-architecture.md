# 官方配置增量更新架构调整方案

> 状态：开发分支已接入新协议，目标发布为 0.15.0（跳过 0.14）。正式版本号未提升，线上尚未切换；验证与发布边界见第 12 节。

## 1 目标与现状

在不发布新版应用的情况下修正拼写、场景与区域定义、布局坐标、默认调律配置及 WF。
应用维护频率降低后，仍可持续更新现有代码能够支持的任务和配置。
没有网络或下载失败时，应用继续使用当前可用配置。

开发分支已移除 remote 读取层及 content_version 仲裁。更新器将公开累计增量
和有效会员内容事务安装到 system，业务加载只保留 local 与 system；WF 可更新已有官方脚本。
现行实现见 [配置分层](04-config-layering.md)，需求与验收见
[官方配置增量更新需求](../../20-requirements/50-platform/14-official-config-publication.md)。

## 2 来源与生效语义

| 对象 | 职责 |
|------|------|
| 官方 system 源文件 | 公开预置及公开增量的维护、上传来源；不从用户 local 合并视图导出公开内容 |
| 客户端 system | 当前已经应用的全部官方配置，包括预置、公开修正和有效会员文件 |
| 客户端 local | 用户配置，按登记的合并策略优先于 system |
| 客户端 updates | 原始预置备份、下载包、更新状态及事务恢复资料；不作为配置解析层 |
| 客户端 session | 用户与运行数据，不参与更新包构建或覆盖 |

会员内容没有随包预置，保持独立授权和完整包发布，不能因为统一安装到 system 就进入
普通安装包或公开增量。会员内容源的仓库搬迁不属于本方案；发布来源与渠道归属不能因
客户端统一安装到 system 而混淆。

### 2.1 下发边界与加载边界分离

**官方 system 源目录内的一切文件均可下发，无论客户端能否识别。** 不按文件名、扩展名、
已登记配置类型或当前加载器能力设置下发白名单；app.yaml、说明文件、新目录和未知格式
同样可以进入增量包。目录是内容分发边界，配置类型登记只决定如何加载、校验与刷新，
不是准入条件。管理端可以选择本次发布文件，不意味着每次必须上传整个目录。

更新器按清单与摘要完整安装文件。未知文件作为不透明内容保存，不能因没有加载器而拒收、
丢弃或强行解析；不会仅因安装就自动导入模块、执行文件或激活新功能。已知加载器仍只消费
自己负责的内容。未来客户端能识别这些文件时，再按其加载契约读取；跨应用系列仍遵守
版本隔离，不自动继承旧系列增量。

全目录可下发不取消包来源、授权、摘要、体积及解压路径安全校验：拒绝绝对路径、路径穿越、
越界链接及无法安全落盘的路径，包只能修改候选 system，不能写 local、session 或应用代码
目录。官方源内不得混入凭据、用户数据和会员专属内容；这是发布内容审查和渠道隔离责任，
不能用客户端文件类型白名单代替。客户端 system 已吸收会员内容，不能反向当作公开发布源。

### 2.2 local 与 system 的读取策略

有效官方配置由更新器构建：原始预置 r0 加当前公开累计增量，再安装当前有效会员内容。
构建完成后，解析器只对 local 与这份 system 执行以下两类读取：

| 策略 | 示例 | 契约 |
|------|------|------|
| 语义合并 | scenes.yaml、layouts.yaml、已登记的聚合业务配置 | system 为基底，叠加 local 字段及登记表增量；保留现有列表、删除和受保护条目规则 |
| 整体覆盖 | 单个场景、布局实体、WF | local 存在同路径实体时完整采用 local，否则采用 system |

复用配置策略注册，不把所有文件统一做字典深合并，也不改变已有实体或聚合文件的归类。
官方更新不会修改 local；有 local 覆盖时，界面应能解释为何官方修正未改变有效值。

下表覆盖当前 system 目录中的全部文件类别，并列出现有加载器支持的补充资源路径。
“语义合并”不保证所有列表都追加：普通列表、标量整键替换，登记表与受保护条目沿用各自
增删、排序规则。下表所有文件均可下发；读取策略不能反过来成为下发限制。

| 文件或路径 | local 优先方式 | 加载契约与例外 |
|------------|----------------|----------------|
| `app.yaml` | 语义合并 | `load_app_config()` 聚合应用、环境、输入与延迟等配置；不能以包含启动配置为由禁止下发，新任务重新加载，主页面刷新方案选择 |
| `scenes.yaml` | 语义合并 | 场景登记表分层规范化后合并；条目列表支持登记的增删、排序语义，不整份替换登记表 |
| `layouts.yaml` | 语义合并 | 布局登记、画布及继承声明按键合并；与下面的单场景坐标文件不同 |
| `ocr.yaml` | 语义合并 | OCR 参数和清洗组按现有键级合并规则读取 |
| `scenes/*.yaml` | 整体覆盖 | 同路径场景定义取 local 全文，不与 system 场景字段拼接 |
| `layouts/<布局>/<场景>.json` | 整体覆盖 | 同路径坐标实体取 local 全文，包括实例属性 |
| `layouts/<布局>/_reference.png`、`_reference.json` | 各文件整体覆盖 | 标定参考画面及画布信息；发布时检查配套关系，当前 system 未携带也允许新增 |
| `workflows/**/*.wf` | 整体覆盖 | 主脚本及导入脚本逐路径解析，local 同路径脚本优先；官方已存在脚本也可更新 |
| `templates/**/*.png` 等模板资源 | 整体覆盖 | 由模板定位器选择同路径 local 资源，否则 system；能否被图像库使用与能否下发分开 |
| `references/<空间>.yaml` | 专用语义合并 | `ReferenceDB` 按参考条目的 `file` 合并，local 同项替换、`deleted` 隐藏系统条目，`meta_schema` 整列表覆盖；不走通用深合并 |
| `references/` 下的图像资源 | 整体覆盖 | 参考库按其资源路径选择 local 图像，否则 system；条目定义和实际图像分别解析 |
| `yysls/game_config/basic.yaml`、`seasons.yaml`、`affixes.yaml`、`equipment.yaml`、`martial_arts.yaml`、`schools.yaml`、`playstyles.yaml` | 语义合并 | 七份文件各自合并后组成领域视图；武器类型、等级、赛季等已登记列表保留专用规则 |
| `yysls/tune_config.yaml` | 语义合并 | 调律品质阈值、开关等聚合设置 |
| `yysls/tuning_rules/*.yaml` | 整体覆盖，停用桩例外 | 完整 local 规则替换正文；local 仅保存停用桩且官方正文存在时，沿用官方正文，仅叠加 `disabled`，不能误当成空规则覆盖 |
| `yysls/base_groups/*.yaml` | 整体覆盖 | 一组一文件，不逐条拼接规则组 |
| `yysls/gear_sets/*.yaml` | 整体覆盖 | 一套出装一文件，词条约束随整套搭配读取；不是聚合配置的深合并 |
| `yysls/graduation/<等级>/*.json` | 整体覆盖 | 同路径毕业率方案完整替换 |
| `yysls/attr_model/*.yaml` | 整体覆盖 | 属性模型管理器按文件读取，不能因 YAML 内有多个条目就判为语义合并 |
| `yysls/attr_model/profiles/*.yaml` | 整体覆盖 | 同路径角色属性模板完整替换 |
| `yysls/damage_model/*.yaml` | 整体覆盖 | 同路径伤害模型完整替换 |
| `maps/<地图>/map.yaml`、`base.png` | 各文件整体覆盖 | 已有地图读取路径支持，当前 system 清单为空；配置与底图发布时检查配套关系 |
| `templates/README.md` 等说明及其他未知文件 | 暂无业务加载语义 | 原样安装到 system，不要求解析；未来按消费者契约定义 local 读取方式，不能默认对未知文件做深合并 |

核对入口：`core/config/resolver.py`、`scene_config.py`、`layout_config.py`、`ocr_config.py`、
`scene_definition.py`、`layout_manager.py`、`reference_db.py`，以及
`apps/yysls/config/{game_config_files,builds}.py`、`core/{tuning_rules,attr_model,damage}`
对应管理器。在线安装与 local 覆盖是两个职责；原有 local 读取契约保持不变。

## 3 公开更新的应用版本边界

公开增量默认采用管理端对应 project 正在维护的版本号，计划中允许手动修改。三段版本 x.y.z 对应唯一范围
`[x.y.z, x.y.(z+1))`，按数值分段比较，不能用字符串前缀判断。

- 0.15.0、0.15.0.1、0.15.0.2 读取同一份 v0.15.0 索引条目。
- 0.15.1 及其他三段版本不读取 v0.15.0 的更新。
- 没有所属版本的条目时使用该版本的随包预置；不得寻找最接近版本替代。
- 第四段修订必须保持同系列配置兼容，且使用同一份公开预置基底；需要不同基底或破坏
  配置兼容性时提升第三段。依赖仅第四段新代码能力的配置不能下发给整个系列。
- 开发版、预发布版不自动按正式版规则接收生产配置；验证使用显式隔离环境。

管理端冻结计划版本、所选内容与公开预置基底；基底默认 admin 父目录的 config/system。
管理端不运行源码或配置自检，不要求源码标签。公开更新的基底匹配仍由包摘要及客户端安装校验保证。
线上版本目录用于浏览与核对，
不会覆盖计划版本或本地勾选。project 维护版本在审核期间变化时重新准备。
手动指定其它系列需选择对应预置基底。旧系列目录保留供历史客户端获取修正。

会员包不采用这一预置修正周期：没有 r0，也不按 vX.Y.Z 划分目录。它维护独立发布修订，
有必要时声明客户端代码兼容要求。没有公开增量版本问题不等于忽略代码兼容性。

## 4 站点目录与索引

```text
site/lvjiang/
├─ public/
│  ├─ index.json
│  ├─ v0.15.0/
│  │  ├─ r1/
│  │  │  ├─ manifest.json
│  │  │  └─ update.zip
│  │  └─ r2/
│  │     ├─ manifest.json
│  │     └─ update.zip
│  └─ v0.15.1/
│     └─ r1/
│        ├─ manifest.json
│        └─ update.zip
├─ member/
│  ├─ index.json
│  └─ packages/
│     └─ <包ID>.bin
├─ config/                    旧应用专用，原有文件保持不动
├─ protected/                 旧应用专用，原有文件保持不动
└─ … 公告等现有内容
```

public/index.json 按三段应用版本记录当前修订、对应 manifest 相对地址和摘要。
公开 manifest 记录所属版本、修订、预置基底摘要、更新包摘要以及包内文件清单和摘要。
公开包携带完整文件内容，路径相对 system，不携带 config、system 等外层目录。

member/index.json 描述最新发布的会员完整包、包 ID、独立修订、密文摘要和必要兼容信息。
继续经授权服务取得解密材料；公开站点不存会员明文、包密钥或管理凭据。
会员索引的 public_revisions 按应用系列记录所需的最低公开修订。客户端安装校验使用该组合；
客户端缺少依赖时拒绝候选，保留当前可用内容，而非在断网时安装不完整组合。

包与修订清单发布后不可原址改写。先上传完整内容，最后更新索引；旧版本和旧修订可保留。
读取到旧索引仍能得到完整旧包。索引与内容因部署时序暂时不一致时，本次更新忽略，
保留当前有效内容并在后续检查重试。

公开修订在各三段版本内递增，会员修订独立递增。文件变化和下载完整性由摘要判断；
同一修订出现不同摘要属于发布错误。恢复历史内容创建新修订，重试原发布不生成新修订。
无需另设与这些修订重复的全局内容版本。

## 5 累计增量与会员完整包

公开 rN 是相对该应用系列 r0 的累计增量，不是相对 rN-1 的差分补丁。r1 修场景、r2 修 WF，
r2 必须同时包含仍有效的场景修正和 WF 修正。全新安装可以直接应用 rN，无需下载历史链。

管理端允许只选择本次修改，但生成新修订时保留此前仍有效的覆盖；移除覆盖必须是明确
审核的动作。增量中的同路径文件完整替换官方预置文件，聚合文件应是准备好的官方完整
结果，不能误把用户 local diff 当作官方完整配置。

从增量移除一个文件意味着恢复其 r0 内容；若 r0 中也没有该文件，则不再安装。
删除或停用随包已有实体优先采用已有配置语义；首轮不增加隐式文件删除指令。

会员包始终是完整快照。更新会员包时移除旧包独有文件，公开更新时保留仍有效的会员内容。
会员准备及客户端安装均拒绝同路径实体的公开/会员归属冲突，不按下载先后决定结果；需要补充
scenes.yaml、layouts.yaml 等共享登记表时，使用已登记的语义合并并检查实体引用。

## 6 本地存储与基底备份

```text
config/
├─ system/
├─ local/
├─ session/
└─ updates/
   ├─ state.json
   ├─ v0.15.0/
   │  ├─ r0.zip
   │  ├─ r1.zip
   │  ├─ r1.json
   │  ├─ r2.zip
   │  └─ r2.json
   └─ member/
      └─ <包ID>.bin
```

state.json 记录当前应用系列与基底摘要、已应用公开修订、会员包 ID 与修订、文件归属和
摘要和生效代次。独立 transaction.json 记录尚未完成的更新事务。不同应用系列的修订记录必须隔离。事务临时文件和上一份
system 的恢复资料也放在 updates 下，不再增加 config/member 或配置加载层。

每组三段版本只建立一份 r0.zip，且必须在首次公开或会员更新之前生成并校验。
普通用户模式的 system 应来自可信预置；不能把来源不明、已经在线更新或带有会员文件
的目录直接当成 r0。无法确认原始基底时停止安装更新，保留现状并提供恢复预置的诊断。
安装包应提供基底身份和摘要供确认。开发工作区不得由自动更新覆盖被 Git 跟踪的源文件，
开发验证使用隔离运行目录。

下载的 rN.zip 和会员密文包单独留存并校验；只有原子替换已完成的下载文件才能进入缓存。
正常更新不覆盖 r0，不自动清理历史归档；未来如增加清理功能，必须保留当前应用所需基底
和恢复资料，并明确磁盘占用。

会员密文缓存不等于离线即可解密。公开更新可依据归属清单和摘要保留当前已安装且仍有
有效授权的会员文件；密钥持久化和离线授权边界沿用授权协议，不为本次目录改造新增保证。

## 7 下载后即时应用

下载、解压与校验在后台进行。连接失败、没有对应更新或下载失败均保留当前状态；
不阻断启动或任务，不弹阻断对话框，也不因暂时断网撤回已应用配置。
摘要、路径或已知消费者所需格式不合法时拒绝本次候选并留下可行动诊断，不能把部分文件
投入使用；未知文件没有业务格式校验器不属于格式错误。

成功更新按以下顺序执行：

1. 冻结目标版本、所选公开修订和会员包，获取更新安装锁，避免多个进程并发替换。
2. 将 r0 解压到临时目录，应用选定公开累计增量，并安装有效会员内容，构造候选 system。
3. 对客户端已知且会消费的内容校验格式、WF 语法、场景与布局引用、资源存在性及领域配置；
   未知文件仅做安装完整性与安全校验，不要求客户端认识。结合现有 local 构造候选有效
   视图，检查更新后实际使用的组合。不得为消除冲突修改用户 local。
4. 准备对应的内存配置和失效范围；短暂暂停新任务接收配置快照，完成磁盘目录交换、
   内存配置切换和状态记录。使用安装事务与恢复目录处理跨文件操作，不声称两次改名
   就天然构成跨平台事务。
5. 通知受影响消费者刷新，恢复新任务入口。应用完成即生效，不要求重启，也不默认等到
   所有当前任务结束。失败时恢复上一份完整 system 和对应内存视图。

生效要求覆盖表 2.2 中所有已知消费者，包括应用聚合配置、场景登记与定义、布局、WF
发现和解析缓存、OCR、参考与模板资源、游戏、调律及模型配置和相关界面。复用既有
变更通知并补齐遗漏消费者，按受影响路径刷新，避免无关全页面重载。未知文件下载后即
安装可用，但没有消费者就不产生业务行为；“即时生效”不代表凭配置获得尚未实现的能力。
界面上的未保存草稿保留；草稿依赖的官方基底变化时提示重新核对，不能静默覆盖草稿。

运行中的任务继续使用启动时的配置、WF 导入闭包和资源快照。只缓存主 WF AST 不足以
保证这一点：后续调用的子脚本、识别配置和延迟读取资源也必须来自原快照。
任务在安装锁内复制 system 和相关 local 配置到独立临时目录，退出后回收；整个批量执行
共享一次快照，延迟读取的子脚本、图库、模板和领域模型也保持隔离。各进程在新任务启动前确认当前配置代次，界面通过变更通知或
文件状态监听跟进更新。快照隔离是即时更新的交付前提，不能以“重启生效”替代验收。

已确认的授权失效按授权规则停用会员能力并重建官方内容，与网络暂时不可用分开处理。
任务快照不能成为绕过会员授权检查的手段。

## 8 升级与人工恢复

升级至新的三段版本时安装新预置、建立新基底身份，不把旧系列公开增量搬入新 system。
保留历史归档不代表继续加载它们。会员包可独立复用，但需重新检查授权与代码兼容性。

极端情况下支持用户关闭所有实例，删除 system，将当前应用系列的 r0.zip 解压到 system。
r0 压缩包的根就是配置内容，不能再嵌套一层 system。此操作只恢复公开预置。

system 必须带有与所安装内容一致的身份标记或可验证摘要。启动时不能仅凭外部 state.json
宣称某修订已应用；手工恢复 r0 后应识别为预置状态并修复安装状态。
若要持续使用 r0，用户关闭在线更新，避免随后又自动应用有效增量。
恢复会员内容需要有效授权及可用解密材料，不能承诺仅凭缓存密文一定可以离线恢复。

当前设置只有“接收在线配置更新”总开关。关闭或进入离线模式恢复 r0 并撤下会员内容；
未提供分别关闭两渠道的 UI。授权明确失效只撤下会员，保留有效公开修订。
恢复和重建都不删除或重写 local、session、用户数据库。

## 9 发布端与依赖检查

管理控制台使用单个推送页，通过按钮切换公开、会员模式。公开模式显示计划版本、所属版本目录、
线上修订与冻结的累计文件清单；会员模式显示独立的会员修订与授权发布状态。
两种模式共用目录栏、编辑表单、详情组件与分栏比例；计划和冻结快照各自独立。
切换模式不更改草稿和文件选择，不自动联网。站点发布锁、摘要校验和失败重试能力保持原契约。

公开发布可以选择官方 system 源目录内任意文件，不按扩展名或已登记类型过滤，也不因
目标客户端无法识别就禁止上传。配置内容按原始字节打包；发布端不加载地图、场景、布局或工作流
做完整运行自检。公开源的隐私与会员归属仍须由操作者确认。

会员包可以依赖客户端已有 system，发布端不要求包自包含。完整组合的依赖检查在客户端安装时执行。
会被现有消费者读取、却依赖未发布代码能力的改动不能作为当前系列的有效修正发布。
没有消费者的未知文件可以先行下发留存，这与兼容性检查不冲突；不能宣称它已提供新功能。
静态引用检查复用现有能力，动态引用与业务行为仍需对应验证，不将“能解析”表述为
“完整兼容”，也不将“安装成功”表述为“业务已支持”。

上传时冻结源内容，源文件或站点基线在审核后变化则重新准备。发布先生成不可变包与清单，
再切换站点索引，区分已准备、已推送待部署、线上已确认。失败重试使用同一快照与修订。
发布控制台不会自动提交主工程、local 或 session；站点提交只包含本次发布产物。

新版应用发布必须确认当前公开修正已进入其预置，或有经过验证的替代实现；打包期间新增
在线修正时重新核对。会员内容由会员发布链承接，不进入普通预置。

## 10 新协议切换与实施范围

以 0.15.0 作为新协议边界，跳过 0.14；维护版本号已提前同步，不代表正式发布完成。
新客户端只读 public/index.json 与 member/index.json，不继续以旧
config/config.json、protected/config.json 或 config/remote 参与配置加载。
旧站点入口可冻结保留供旧客户端使用，新代码不新增永久兼容分支。

开发分支的 system 文件 content_version 已统一为 1；暂留字段读写工具，后续另行删除。
新逻辑从一开始就不依赖该字段；结构 schema_version 与发布修订仍各负其责。
不能提前归一化旧线上文件，旧客户端仍依赖其内容版本。历史不可变包不为归一化而重写。

WF 同步必须移除公开只新增限制，并同步调整 resolver、发现时来源仲裁、导入路径与
AST 缓存，使已存在的官方脚本也能更新；保留 local 优先和当前任务快照。
会员 URL 的客户端校验、管理端发布地址以及授权服务中的包地址约束须一并调整，
避免只改站点路径而出现密文能下载、密钥授权却仍绑定旧地址的问题。

按职责实施：新清单与打包协议、更新归档与可恢复安装、两层解析与任务快照、即时刷新、
管理控制台发布与线上确认、打包基底与旧协议退出。公开与会员的新链路全部验证后才切换；
不能在只完成目录改名时宣布架构调整完成。

## 11 验证门禁

| 场景 | 必须满足 |
|------|----------|
| 首次启动断网或下载失败 | 使用完整预置，应用与任务入口可用 |
| r0 直接安装 r5 | 无需历史补丁链，得到累计更新结果 |
| 新修订撤回旧覆盖或新增文件 | 恢复 r0 对应内容，移除已不属于有效组合的文件 |
| 同系列第四段与下一第三段版本 | 前者适用，后者不加载旧公开更新，包括已有缓存 |
| 当前任务运行时更新 WF、布局 | 更新立即供界面和新任务使用，当前任务持续读取原快照 |
| 本地语义合并与实体覆盖 | 延续登记策略，local 内容与未保存草稿不被更新器修改 |
| app.yaml、说明文件及客户端未知的新格式文件 | 均可下发并完整安装，不受旧白名单限制；未知内容不强行解析或自动执行 |
| 未知内容与已知格式损坏 | 前者安全安装，后者按实际消费者校验并保留上一完整可用状态 |
| 公开更新与会员更新分别发生 | 彼此有效内容被保留，归属冲突或依赖不完整时拒绝候选 |
| 更新中断、磁盘失败或内存切换失败 | 恢复完整上一状态，不出现磁盘与内存配置混代 |
| 多实例及文件占用 | 安装串行，新任务读取同一生效代次，旧资源不提前回收 |
| 手工删除 system 并恢复 r0 | 识别预置状态，不被残留 state.json 误判为已应用 rN |
| 会员断网与授权明确失效 | 分别遵守已有授权协议，不把下载失败当成撤权或续权 |
| 发布重试、过期索引及线上部署延迟 | 不重复升修订、不应用混合产物、不把 Git 推送当作线上完成 |

测试使用临时配置根、临时站点与授权 fake，不操作真实用户配置、Session、数据库或手机。
Windows 原生文件占用验证须在发布环境执行；Android 本轮验证预置打包与 PC 同步，不包含手机在线更新；
各平台未完成的能力必须单独报告，不能以桌面通过代替全部平台通过。

## 12 实现入口与发布边界

- `core/update_bundle.py`：所有安全路径文件的确定性包、系列清单、摘要和解压限制。
- `core/config/update_store.py`：r0/rN/member 归档、安装锁、累计重建、事务恢复及回滚；
  `remote.py`、`update_activation.py`：后台已知消费者校验、主线程切换及按路径失效。
- `runtime_snapshot.py`：单任务与整批配置快照；`update_observer.py`：其他实例安装代次感知。
  场景、布局、WF、OCR 清洗、参考与模板资源、插件领域模型使用对应新视图。
- admin 推送页切换公开/会员模式：公开基底摘要、累计更新与显式撤回、冻结审核、同修订重试，不执行运行自检，
  线上状态查询。会员使用 `member/index.json`，密文缓存放在 `updates/member`。
- Windows 打包和 Android 预置生成器均写入可信基底身份及 r0。APK 已完成构建验证；
  Windows 文件占用/安装器的原生实测仍属于发布前门禁，不能以 Linux 回滚测试替代。
- 手机继续接收 PC 的 system 快照，不投影成 local；同步保留手机自己的 updates 与基底身份，
  不把 PC 同步结果冒充官方 r0。手机本轮不启动在线更新，未来启用时需单独设计同步基底。
- 未提升应用版本号、未发布站点索引、未操作真实手机。发布 0.15.0 后才允许管理端面向
  新系列生产发布；旧线上入口保留给旧客户端，新客户端不读取旧协议。

静态校验不能证明动态业务行为；发布具体 WF 修正仍须执行对应任务验证。
