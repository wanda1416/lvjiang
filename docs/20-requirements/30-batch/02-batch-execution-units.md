# 批量执行单元
> 状态：已实现（2026-10-06，基线 v0.13.11）。

## 范围与状态

批量配置窗口只决定可见用户名及其初始顺序，沿用原有 `usernames` 字段。
主页面「参数 → 批量设置」选择调度单元，默认 `user`（用户名）；其他候选键来自
可见用户资料的非空属性。主页面「单元」页按所选属性对可见用户去重分组，
再勾选本次执行的单元，勾选集合按属性键保存。旧配置无需迁移；其中的
`visible_units` 数据不再决定属性单元范围，读取时忽略，
下次保存批量配置时移除该废弃字段。

切换配置组时按已保存的键重建列表。启动时冻结可见用户的属性、单元成员、
任务参数与生命周期参数。运行中只重新读取业务 Profile，不重新读取用户配置。

## 属性单元执行

一个属性值可对应多名用户。批量层在条目准备前对每名成员执行任务声明的
`batch_check`；至少有一名可执行时，把可执行成员的
`[{username, attributes}, ...]` 交给条目准备工作流。准备工作流成功时必须返回
属于该列表的 `username`。任务、独立参数、Session、历史与条目收尾均绑定此用户名。
条目准备工作流用 `#% batch_unit_prepare: true` 声明它实现这条协议；未声明的
工作流在按属性调度时不允许启动，主页面在开始前拦截并说明如何修改。声明与否
不改变用户单元的行为。
选定角色后，每个脚本执行前重新运行该角色的 `batch_check`，仅执行返回 `success`
的任务；其余任务按即时检查得到的
`skipped` 或 `failed` 写入进度、报告和任务历史。结果文件或历史写入失败只记录告警，
不改变已完成任务的业务结果。
生命周期返回 `stopped` 时停止调度后续单元；批次准备失败时将计划中的
单元轮次标记为跳过，并写入进度和报告。属性准备阶段尚未绑定具体用户，
Profile 读取须显式指定用户名，隐式读写在缺少执行用户名时直接失败。
准备阶段之前锁定本单元全部成员，结束后释放；无法锁定时每 60 秒延期尝试，
连续 30 次锁冲突后停止调度该单元并记录原因。该等待只针对用户锁，
不用于角色在线等业务状态。

生命周期新增 `batch_unit_key`、`batch_unit_value`、`batch_unit_members`，
仅属性单元提供。条目准备返回 `skipped` 时跳过当前单元的业务脚本，并消耗一次
执行轮数；还有轮次时由普通批量循环再次选择单元。调度器不设置业务等待时间，不解释
Profile key、账号或角色的业务含义。属性单元始终执行生命周期工作流。

## 内置属性准备工作流

`batch/prepare_item_by_attr.wf` 有一个 `profile_key` 参数。它逐个读取候选用户
对应 Profile 的当前值；无记录按 0 参与比较，同值保留原成员顺序。选出的用户交给
已有 `prepare_user` 登录，后者根据用户资料中的 `account`、`tail`、`role` 和
`role_index` 选择游戏角色。发现角色仍在线时，本轮跳过该单元；登录成功后
执行任务并进入普通批量循环。任务是否已达目标仍由业务工作流的
`batch_check` 决定。
