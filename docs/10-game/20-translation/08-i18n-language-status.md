# 多语言词表现状与日文术语生成

本篇记录律匠 i18n 词表（`config/i18n/`）的**工程状态**：每种语言完成到什么程度、
生成出来的词表用什么方法产生、质量等级如何。与 01–07 的「中英术语对照」不是一回事——
那几份是给人和文档用的词典，本篇是词表本身的进度与取舍记录。

术语来源与游戏客户端容器格式见 [README](README.md)。

## 1. 语言完成度

随包 12 种语言，分三档：

| 档位 | 语言 | 词表来源 | 质量等级 |
|---|---|---|---|
| 母本 | `zh_CN` | 源码 `tr("…")` 的中文原文 | 权威（就是原文） |
| 人工全译 | `en_US` | 人工翻译 | 权威（可直接对外） |
| 同源生成 | `zh_TW` | 简体经 OpenCC `s2twp` + 区域校订 | 可读，措辞非官方 |
| 术语生成 | `ja_JP` | 中文经 `s2t` + 日本新字体 + 词组修正 | 可读，直译调 |
| 英文回退 | `ko_KR`、`de_DE`、`fr_FR`、`es_ES`、`pt_BR`、`ru_RU`、`th_TH`、`vi_VN` | 与 `en_US` 逐字相同 | 无本地化 |

「完成度」对生成档和回退档含义不同：回退档的指标是**英文覆盖率**，不是本地化程度。
这几档语言的词表值 99% 与 `en_US` 逐字相同。

## 2. 词表分层

```
config/i18n/zh_CN.yaml          ← 只留 meta，模块文案在 zh_CN/ 下
config/i18n/zh_CN/*.yaml        ← 核心层 19 个模块（4850 条叶子）
config/i18n/apps/yysls/zh_CN.yaml ← 插件层：yysls 段 + auto_strings 段
```

核心层放律匠自身的 UI 文案（按钮、报错、对话框）；插件层放燕云游戏术语。
`tr()` 以中文原文为键，两层合并到同一张扁平表（见
[08-i18n 架构文档](../../30-architecture/38-platform/08-i18n.md)）。

**生成档只覆盖插件层的术语**；核心层仍是英文回退——这与既有「非游戏内容一律
以英文回退，宁可显示英文也不给非中文用户显示中文」的策略一致。

## 3. 繁中生成（zh_TW）

| 项目 | 内容 |
|---|---|
| 转换器 | OpenCC `s2twp`（繁体·台湾，含短语表） |
| 为什么不用 `s2tw` | `s2tw` 只给大陆式繁体（软件→軟件、视频→視頻、设置→設置），`s2twp` 才是台湾语体（軟體、影片、設定） |
| 范围 | 核心层 19 个模块 + 插件层，共 20 个文件 |
| 手工校订 | 5 组，见下表 |

| 原词 | 误转 | 校订 | 原因 |
|---|---|---|---|
| 夹钟 | 夾鍾 | 夾鐘 | 十二律乐钟用「鐘」，姓氏才用「鍾」 |
| 背包 | 揹包 | 背包 | 繁中写「背」，不写「揹」 |
| 账号/账户/记账 | 賬 | 帳 | 繁中正体「帳」 |
| 网卡 | 網絡卡 | 網路卡 | 用「網路」不用「網絡」 |
| 平台/后台/一台 | 臺 | 台 | 日常用「台」 |

## 4. 日文术语生成（ja_JP）

| 项目 | 内容 |
|---|---|
| 转换链 | 简体 → `s2t`（繁体）→ 日本新字体表（约 300 字）→ 词组级修正表（约 30 条） |
| 转换范围 | 只转「术语样」条目：2–12 字、无标点空格、无 `{0}` 占位符 |
| 实际条数 | 转日文 1510 条；长句、含占位符、纯 ASCII 的 1046 条保持英文 |
| 残留中文 | 1510 条中 74 条（4.9%）仍含中文功能字（的、是、被、让…） |

词组级修正表的必要性：逐字转换只解决字形，不解决词序。`用户`→`用戸`、
`缓存`→`緩存`、`网格`→`網格` 在日语里都不成立，必须整词替换成
`ユーザー`／`キャッシュ`／`グリッド`。

### 为什么只做日文、不做韩文

在同一批 287 条官方名词上实测「逐字命中游戏文本池」的比例：

| 语言 | 直接命中简体原文 | 简→繁 | 简→繁→日新字体 |
|---|---|---|---|
| `zh_cn` | 65.2% | — | — |
| `ja` | 20.9% | 24.4% | **34.5%** |
| `ko` | 1.7% | — | — |

日文汉字与中文同源，转换后命中率翻 1.6 倍，说明「字形可迁移」成立；韩文几乎
全是谚文（心法→심법），汉字同源假设不成立，转换出来既不是官方译文也不如英文
自然，因此**韩文及其他 8 种语言保持英文回退**。

## 5. 游戏客户端容器的逆向进度

目标是「给一个游戏名词，直接取出 12 语言官方译文」。当前**未达成**，按已证实的
程度记录如下（引用具体条目时不要假定已可切分）。

### 已证实

| 层级 | 结论 |
|---|---|
| 文件 | `EF BE AD DE` + u32 版本(1) + u32 块数 + u32 保留 + u32[块数] 累积偏移 + 块区（9 字节头 + zstd 帧），24 个文件同构 |
| 块 0 | 纯 u32 索引数组，形如 `[总长, 0, 块数, 0, 1, 2, …, 块数]` |
| 数据块头 | 24 字节：`[u64 A][u64 B][u64 0x595896DC]`（末项是固定标记） |
| 槽表容量 | `A + ceil(A/16) + 1` 个槽，每槽 16 字节；文本池起点 = `24 + 容量 × 16` |
| 槽内字段 | 至少一部分槽是 `[u64][u32 offset][u32 length]`，offset 相对文本池起点 |
| `_diff` 文件 | 小块是干净的 16 字节表，可直接解出词条（已验证 13 条） |

### 未解决

- **大部分槽解不出完整字符串**：仅约 6–9% 解出「首尾完整」的串，其余解出的是
  同一段文本的**重叠子串**（例如同一句 `...not supported for the current quest.`
  被 5 个槽分别指向不同位置）。
- 该现象在 `_diff` 里同样出现（`Channel Activation Count` 与它的子串 `Activation`
  是两个不同条目、指向重叠位置），说明**字符串池是共享区，不是逐条拼接**，
  格式里还有一个「如何组合出完整串」的字段没定位到。
- 已排除的假设：6 种定长记录布局、7-bit varint + `0x80` 终止符、off/len 分离
  双数组、`0x80` 填充空槽、跨语言 u64 哈希对齐。

### 影响

| 需求 | 状态 |
|---|---|
| 取出全量文案（池化） | 可做（每语言约 94 MB 纯文本） |
| 按条切分并跨语言对齐 | 未完成 |
| 取某术语的 12 语言官方译文 | 未完成（依赖上一条） |

## 6. 未完成的工作

1. 容器槽表语义（上节）——解开即可一次拿到 12 语言全量官方术语。
2. 日文词组修正表可继续扩充，把残留 4.9% 中文功能字压下去。
3. 韩文若要做本地化，需要汉字→谚文读音表（可用 Unicode Unihan 的 `kKorean`
   字段离线生成），且要处理韩语玩家更常用英文借词的偏好。
4. 词表卫生：插件层仍有 252/231 条源码不再引用的 CJK 死键，由
   `tests/core/test_i18n_stale_keys.py` 的棘轮锁住，只许下降。
