# 自动调律决策与执行保护

> 最后更新：2026-10-09（基线 v0.13.14）。

本页定义实际处理链与执行保护；最终参数取当前基础规则组，行为配置的用户说明见 [三种处理配置](../../60-userguide/04.03-behavior-config.md)。

## 6. 调律决策编排 — 状态机三行为点


### 6.1 扫描处理（behavior.scan，进调律前）

扫描处理、材料处理、调律处理三个规则表的「添加规则」行最右侧均提供
「校验规则」按钮。结果区域默认隐藏；点击后只列出部位 × 金/紫品阶
完全没有启用候选规则的组合，按钮变为「清理结果」，再次点击隐藏结果。
切换规则组或编辑规则时清理旧结果。判定语义、评级、首词条数值和调律准入
门槛取决于实际装备与运行参数，不得被静态检查推断为必然命中。

#### 锁定与冷却状态前置保护

装备详情的冷却提示仅有以下四类文案，倒计时数值随剩余时间变化：

| 游戏文案示例 | `cooldown_kind` | `cooldown_state` |
|------------|-----------------|------------------|
| `重置调律冷却中：4天16小时` | `reset` | `cooling` |
| `词条转律冷却中：5小时59分` | `transmute` | `cooling` |
| `词条转律冷却完成` | `transmute` | `completed` |
| `重置调律冷却完成` | `reset` | `completed` |

冷却中的倒计时不带“后完成”后缀，“完成”只出现在完成态；测试不得把
“1小时后完成”等虚构文案当作游戏输入。OCR 缺字、截断或分段只作为独立
容错样例，不扩展游戏文案的种类。此处是装备详情提示，不是重置确认页的
`reset_check` 文案（见 §6.5）。

装备详情扫描必须区分 `重置调律` 与 `词条转律`，并保留“冷却中/冷却完成”阶段：

- 勾选“跳过锁定装备调律”（默认勾选）时，已锁定装备不得进入评级、调律、重置或回收；
- 词条转律无论处于冷却中还是冷却完成，都视为用户保留的转律意图，直接跳过；
- 无法确定冷却类型时按保护侧跳过；
- 重置调律冷却中时延期处理，不进入普通扫描处置；
- 重置调律冷却完成只表示“当前可以重置”，不是持久化的断点或特殊入口；
  装备仍按普通扫描准入和调律处理流程运行。

日志、实时调律进度和调律历史都必须记录扫描时的锁定/冷却状态、保护性跳过
原因以及“冷却完成 → 普通准入 → 调律处理 → 重置完成”的状态变化。重置前后在历史中
拆为两条装备事件时，重置前保留原冷却状态，重置后清除已消费的冷却状态。

```
对背包中每件装备：

1. 传入规则（运行期勾选的流派规则）判定潜力 → 预期评级上限。
   “仅识别首词条”默认勾选：门槛判定使用只保留首词条的临时副本，
   已有其他词条视为空槽；原装备数据不得改写。
2. 预期 ≥ entry_min_rating → 进入调律。系统「默认规则」组设为 `top`，
   「激进规则」组设为 `excellent`；模型缺省值是 `excellent`，实际运行以
   当前基础规则组为准
3. 未达门槛 → 按处置表决策：
   - 有序条件规则表首条命中 → 动作：回收 / 忽略（保留）/ 调满后回收
   - 无命中 → 默认保留
```

### 6.2 材料处理（materials，每轮调律开始前）

- **大律准石数量检查**：低于基准判材料不足，按配置的不足处理执行：
  - `skip` 跳过该装备：本件结束调律，继续遍历后续装备
  - `abort` 结束全部调律（默认）：阻断，全部退出
  - `ask` 询问是否继续：走 DSL `confirm` 弹窗询问用户，确认继续则本次运行不再检查
- **调律按钮就绪检查**：点击一键添加后扫描调律按钮文字，未变成「调律」说明添加失败，不盲点调律
- **狗粮检查与添加**：规则条件与扫描/调律处理统一，逐条包含部位、品阶、
  判定语义、判定结果和首词条初始百分比；材料规则的百分比比较固定为 `ge`（≥）。
  判定语义支持传入规则、全部规则、自选规则和自选词条，判定结果是具体档位
  集合，不再使用“最高期望评级 ≥ 某档”的独立阈值语义。
- 条件不命中时检查下一条；条件命中且库存充足时添加该狗粮并结束判定。
  条件命中但库存不足时按 `on_insufficient` 执行：
  - `skip`：跳过当前装备；
  - `continue`：本轮不添加狗粮，立即继续调律，不再检查后续规则；
  - `next`：顺延检查下一条规则，允许彩狗粮不足时降级为金狗粮。
- 全部规则不命中或顺延后仍无可用规则时，本轮不添加狗粮并继续调律。

### 6.3 调律处理（behavior.tune，进入调律前与每轮调律后）

```
装备通过扫描准入后，先用完整实际词条执行一次调律处理；
之后每轮调律结束后再执行一次：

1. 传入规则口径刷新预期评级（供狗粮决策与说明文档）
2. 有序条件规则表首条命中 → 动作五选一：
   - 继续调律或锁定（continue）：未满进入下一轮；已满时按配置结束并锁定
   - 重置调律（reset）：清空首词条以外的全部词条后继续调律
   - 回收（recycle）：退出调律页回背包后执行回收
   - 结束保留（skip）：结束该件装备的调律，留在背包
   - 调满后回收（tune_full_recycle）：后续跳过普通规则，调满即回收
3. 无命中默认：未满 = 继续调律；词条满 = 结束并保留，不自动锁定
4. 词条满为边界条件：continue 规则仍可命中，但转为锁定/保留动作
```

首次调律处理在装备详情页先完成纯决策：

- `skip` 直接保留，不进入调律页；
- `recycle` 直接回收，不进入调律页；
- 已满装备命中 `tune_full_recycle` 时直接回收；
- `continue` / `reset` / 未满的 `tune_full_recycle` 才进入调律页，
  并消费已得出的决策，不重复计算。

调律处理固定执行，不提供可选判定开关，也不保存额外的流程恢复状态。

#### 优秀及以上装备自动锁定

`behavior.tune.lock_qualified` 默认为 `true`。只有同时满足以下条件才自动锁定：

1. 本次运行中该装备至少完成过一轮实际调律；
2. 实际解析得到的词条已满；
3. 明确命中“继续调律或锁定”规则；
4. 传入规则对满词条装备给出的最终评级为优秀或顶级；
5. 返回装备详情页后，扫描状态明确为 `unlock`。

锁定按钮是布尔切换操作，因此幂等性优先级高于“跳过锁定装备调律”开关：
即使用户关闭锁定保护，已锁定装备也不得再次点击；锁定状态未识别时
保守跳过，防止误解锁。未发生实际调律的已满装备也不自动锁定。
词条已满但没有命中任何行为规则时只结束并保留，不能据此认定装备合格。
扫描处理和调律处理在未满词条时使用最大预期评级；该值只用于过程决策，
不能写入最终评级、调律历史结果或授权自动锁定。

### 6.4 判定语义（judge_scope，四选一，逐规则声明）

每条行为规则自行声明「评级 ≤ 条件用哪个规则集识别」或判定方式：

| 取值 | 语义 |
|------|------|
| `incoming` | 传入规则 = 运行期勾选的流派规则（缺省） |
| `all` | 全部流派规则 |
| `custom` | 自选规则（配 `judge_rules` key 列表） |
| `affix` | 自选词条（`ratings` 改存词条名集合，不跑潜力判定） |

**自选词条（`affix`）语义**：不跑潜力判定，直接按装备词条名匹配。典型场景：跳过带金色数值珍贵词条（如最大外攻）的紫色武器，避免误回收。

### 6.5 重置处理（reset 动作的执行）

调律处理命中 `reset` 后的完整流程。核心原则：**只有确定且永久的条件才允许
转处置（可能回收），任何"这一次没看清楚"都必须强制跳过。**

```
命中 reset
  ├─ 等级配置缺失                    → skip（异常，不转处置）
  ├─ 等级 allow_reset: false          → reset_exhausted_action（该等级永远不可重置）
  └─ try_reset_tune
      ├─ resets_used >= 1             → 打开重置页并开启提醒 → skip（冷却期内）
      ├─ resets_used >= max_resets     → reset_exhausted_action（本地次数门槛）
      ├─ 读 reset_tune 剩余次数
      │   ├─ 没读出明确数字            → skip + 记异常 count_unreadable
      │   └─ 明确读到 0                → reset_exhausted_action
      ├─ click reset_tune（桌面布局绑定为按键 R）
      ├─ 读 reset_check
      │   └─ 无「次数」               → 详情原先无重置冷却信息时开启提醒 → skip
      ├─ 读 reset_info 校验材料（按等级 min_material_count）
      │   ├─ 无「持有」               → skip（识别失败）
      │   └─ 持有 < 要求               → skip（传律石不够）
      └─ 两次确认
          ├─ ① 调律页 reset_confirm 读不到 → skip（尚未点击任何东西）
          ├─ click reset_confirm
          ├─ ② general_control.confirm 读不到 → **confirm 等用户处理**，复查一次
          ├─ click confirm
          └─ click close_btn → 重置成功，词条回到首条继续调律
```

开启提醒前必须在 `reset_notify` 区域识别到固定文案“提醒”，识别不到时记录
明确日志并退出，不盲点复选框。仅有两条路径允许点击这个切换控件：本轮已经
由程序成功重置过一次；或装备详情没有 `reset` 类型的冷却信息、进入重置页后
才发现正在冷却。装备详情已有重置冷却信息时，提醒可能已经开启，不得再次
点击；`transmute` 等其他冷却也不得作为重置提醒状态的依据。

#### 转处置的三个入口（其余一律 skip）

`reset_exhausted_action` 可配成 `recycle`，走到它意味着装备可能被回收，因此
入口必须收得很紧。够格的只有三个，共同点是**确定**（不经 OCR 或读到了明确
结果）且**永久**（重试多少次都一样）：

| 入口 | 为什么够格 |
|------|-----------|
| `reset_tune` 读到明确的 `0` | 游戏明确告知没有次数了 |
| `resets_used >= max_resets` | 用户配置的本地门槛 |
| 等级 `allow_reset: false` | 该等级的装备**永远**重置不了。改成 skip 反而有害：规则每轮都判它该重置、每轮都跳过，它永远留在背包里，回收是唯一出口 |

冷却期和材料不足虽然确定，但是**暂时**的，所以只 skip 不转处置。

#### 剩余次数：明确的 0 与"没读出来"必须分开

`reset_remaining()` 返回 `int | None`。按钮文案是 `重置调律(N)`，N ∈ 0-3。

没解析出数字（空串、`0` 被读成 `o`、弹窗尚未渲染完）**不是 0**，返回 `None`，
记异常态 `count_unreadable` 并跳过。若把它当成 0，一次 OCR 抖动就能让配了
`recycle` 的用户丢掉一件本来还有重置机会的装备。

#### reset_check 的判据为什么是「次数」

游戏原文两种：

| 状态 | 游戏原文 |
|------|---------|
| 可重置 | `当前装备剩余可重置次数:1` |
| 冷却期 | `6小时32分后可调律重置` |

判据取「**次数**」而不是直觉上的「可重置」。「可重置」不是冷却文案的子串，
却**是它的子序列**（`可`…`调律`…`重置`）——OCR 少认「调律」两字就得到
`…后可重置`，冷却中的装备被判成可重置，接着去点根本不存在的确认按钮。

「次数」两字与冷却文案没有任何字符交集，漏字漏成它不可能。反向的漏认只会把
可重置的装备当成冷却期跳过，落在安全的一侧。

> 这里匹配的是游戏截屏 OCR 文字，游戏本身只有中文，**绝不能过 `tr()`**——
> 英文界面下会拿翻译后的英文去匹配中文截屏。

#### 二次确认弹不出来：询问用户，不自己取消

点下 `reset_confirm` 之后**必然**弹二次确认。弹不出来通常不是识别问题，而是
账号开了安全锁需要先解锁，机器自己点不出来。

这里不走取消路径：取消要先退 `general_control` 模态、再退「确认重置」视图、
才回到调律页，中途任何一步没点中都会把游戏留在不确定的界面上。改为
`confirm` 等待用户处理现场，选择是后**复查一次**；仍读不到才关闭弹窗
跳过该装备。选择否则使用本次运行的结束标记停止，不在未知页面上继续点击。

自动调律的人工处理统一使用 confirm、choose 或 input，不使用异常 pause。
公共装备/调律导航也显式选择确认模式，避免无人值守把这些交互判为异常。
回收结果选择、材料询问和库存输入保留各自的业务结果与取消语义。

> ① 首次确认（调律页上的 `reset_confirm`）读不到时不需要暂停：那时还没点击
> 任何东西，游戏就停在调律页，直接退出即可。

#### 重置成功后固定点一次 close_btn

重置提交后游戏行为按等级不同：

| 等级 | 行为 |
|------|------|
| 105 | 直接回到调律页面 |
| 110 | **返还材料**，多一层提示需要关掉 |

代码不按等级分支，统一 `click [equip_tune_detail].[close_btn]` 一次：有提示就
关掉，没提示时落在调律页面上也无副作用，比按等级判断更稳。

**为什么是 `close_btn` 而不是 `general_control.blank_area`**：`close_btn` 本质
是一块安全的空关闭区（桌面布局同样绑定为 `SPACE`）；而 `blank_area` 在自动调律
的这几个弹窗上可能与按钮叠加，点下去会误触，也会干扰文字识别。

> **约定**：自动调律流程内，`blank_area` 只作识别区，不作点击目标；一切弹窗
> 关闭都用 `close_btn`。该约定只适用于自动调律——其他工作流（购买心法、
> 江湖日常等）的 `blank_area` 点击不受影响。

#### 狗粮返还弹窗：出字即命中，一个条件管两件事

加过狗粮的轮次，关掉调律结果弹窗后可能命中概率返还，再弹一个无边框弹窗。
不补关它会挡住「一键添加」，下一轮被误判成材料不足。

判据是底部提示区 `tune_tip` **非空**——只要真的返还，这块必然出字。**不做文本
匹配**，因为两端文案不同：

| 端 | 文案 | 可识别性 |
|----|------|---------|
| 安卓 | `点击空白区域关闭` | 8 字 |
| PC | `[space]继续` | `[space]` 基本 OCR 不出，只有「继续」两字能认 |

「出字」这一个条件同时决定两件事，**不能拆开**：

1. 补点一次 `close_btn` 关掉返还弹窗；
2. 置 `round_food_refunded`，调用方据此**跳过**本轮的狗粮缓存 −1
   （`auto_tuning.py`：返还时不消耗，相当于把扣掉的那个补回来）。

因此漏识别既会漏关弹窗、又会多扣一次缓存，两个后果同源，修一个就修两个。

> 原始文本按 `狗粮返还检查: tune_tip=...` 打进日志（命中与否都打），供排查两端
> 识别差异。

> 该点击带一条 `logger.debug`，游戏若改了这里的行为可从这条日志定位。

#### 冷却期不做正向识别

已经读到剩余次数 > 0，说明这件装备原则上可重置；此时没看到「次数」就是冷却期。
不需要再去正向匹配冷却文案：结论一样是 skip，安全且无副作用。

## 回收确认的实际结果

TuningRecycler 先沿用公共导航确认回收。确认未识别且已在背包页时保留并标记锁定；若仍停留在其他页面，交由用户确认真实结果。未知结果不能默认记为已经回收或锁定。
