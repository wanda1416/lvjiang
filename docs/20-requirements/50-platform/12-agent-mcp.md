# 外部 Agent MCP 接入与智能调律

> 状态：部分实现（2026-10-09，基线 v0.13.14）。桌面入口、本机服务、开发/发行共享文档、动态用户发现、采集/分析与新配置生成启动已实现；WorkBuddy GUI、Windows 安装和真实游戏闭环待实机验收。

## 1. 目标与范围

用户启动律匠后，在“调律管理”旁的“智能调律”启动 MCP 服务，导出接入配置到
外部 Agent。用户在 Agent 中讨论流派、玩法与培养目标，查询或采集装备，调用
领域计算，创建新的基础组和调律规则，然后启动既有调律流程。

律匠负责数据、计算、校验和执行，Agent 负责对话与推理。内置 AI 模型配置不是
MCP 的前提。首版仍是 PC 本机 Streamable HTTP，不含公网托管、Android 独立
服务、任意脚本执行或自动培养/换装。扫描范围沿用当前可见方案网格。

## 2. 页面与接入生命周期

页面只有三个操作：启动 MCP 服务、导出 MCP 接入配置、关闭 MCP 服务。
不增加独立用户下拉框、目标白名单、逐项权限勾选或生成结果编辑器。分析建议、
配置结果和启动动作在 Agent 对话中完成，执行进度仍在调律管理中查看。

服务绑定 127.0.0.1，系统分配空闲端口，每次启动独立 Bearer 令牌。导出连接只含
本机服务地址与令牌，不含固定用户、固定设备或模型 API Key。切换用户和设备
不改变连接，不需要重导配置。关闭重开服务、重启软件后重新导出。

多个实例互不抢占端口和令牌；Agent 同时连接多个实例时使用不同连接名称。
关闭服务不停止已经启动的游戏任务，原暂停/停止入口继续可用。

## 3. 动态上下文与用户选择

get_capabilities、list_users 实时返回 current_user 和本实例全部 users。
当前用户从现有 UserManager 读取，主界面切换立即可见，不在 MCP 建立时冻结。
工具 user 参数可指定任何已存在用户，单个任务启动后冻结执行用户与运行参数，
不因界面切换重新读取任务配置。不存在的用户报错，不自动创建用户。

list_targets 返回全部连接目标、当前目标以及 ready、selected、busy 状态。
扫描和调律工具接受可选 target_id，显式指定时沿用现有目标切换与执行器；
省略时解析调用当时的当前目标，不要求用户设置一个额外“授权目标”。
现有连接、图库、平台能力、用户执行锁和目标占用检查继续在调用时执行。

## 4. 工具与业务行为

| 能力 | 工具 | 可观察行为 |
|------|------|------------|
| 发现与文档 | get_capabilities、list_users、list_targets、list_docs、read_doc、search_docs | 当前用户、全部用户、设备及公开文档，schema 来自实际接口 |
| 用户数据 | list_plans、query_equipment、get_plan_context、get_tuning_config | 指定用户的数据；真实/模拟装备明确区分 |
| 公共事实 | get_game_config、list_graduation_schemes | 有效配置与可计算模型，不开放任意文件 |
| 采集 | start_scan_all_loadouts | 游戏切换方案，更新装备与基础属性，报告可见网格范围与逐方案结果 |
| 分析 | analyze_cultivation、search_best_combo、get_analysis_job | 真实毕业率、潜力、词条敏感度、转律与真实装备组合，返回假设与完成状态 |
| 新配置 | preview_generated_tuning、create_generated_tuning、list_generated_tuning | 完整校验后新建 local 基础组和规则，幂等请求与成套发布 |
| 用户选择 | update_tuning_config | 仅在用户要求保存时合并公开字段，修订过期拒绝 |
| 执行 | validate_auto_tuning、start_auto_tuning、get_task_status | 使用运行快照，明确用户/设备，可暂停恢复停止；人工提示仍需用户处理 |
| 复盘 | query_tuning_history、get_tuning_results | 指定用户的真实执行历史及逐件结果 |

基础组与规则的 key 由创建接口分配，不覆盖任何已有 system/remote/local 定义，
不提升 content_version，不自动启用禁用规则或 Beta 能力。目标摘要和私人数据
保存在生成结果中，不进入规则 YAML/key/文件名。失败发布清理仅本次创建的文件。
生成与启动均不改变持久化默认选择，保存默认是独立且显式的操作。

武学组合按无序匹配，玩法由实际武学决定。计算使用派生副本，保留原方案关联，
不改原方案、不装备物品、不执行培养建议。不足数据与未知材料返回原因，最大
潜力不当作概率，培养假设不当作已获得收益。

## 5. 调用时权限与限制

智能调律属于 Lv1。未开通时，所有 MCP 访问，包括初始化、发现、文档读取和
任何工具调用，统一返回“智能调律需要激活 Lv1，请在设置的「功能激活」中激活”。
门禁位于协议入口，已有连接的后续请求也复查当前激活状态。

启动 MCP 即开放本实例已有能力，不采用“先逐项授予再使用”的流程，也不把
一个用户或一个设备作为连接权限。服务关闭、功能未开通、用户不存在、设备
离线、平台不支持或目标/用户占用时，在调用时返回具体限制与恢复提示，由 Agent
向用户解释。切换处理对象只改变工具参数，不要求重新导出连接。

回收、重置、锁定和狗粮行为由生成配置定义，Agent 应按用户目标说明最终行为，
不要求用户再在智能调律页逐项勾选。当前页面没有额外动作权限开关；新增关闭
控制时应默认开放，并在调用时报告关闭原因，不能重新引入前置授予流程。

文件访问仍经专用领域工具，不开放任意路径、凭据、SQL、Shell、Python 或任意
工作流执行。数据节点和字段范围见[访问清单](13-agent-docs-access.md#4-配置与数据访问清单)。
开发环境同样新建到 local，不能因为开发模式将 Agent 输出写入 system。

## 6. 开发与发行一致的文档

文档按既有职责归档：10-game 收拢游戏机制，30-architecture 包含架构与 DSL，
60-userguide 指导软件操作，70-agent 描述 Agent 接入和调用契约。发行版完整
带上四层的 Markdown，保留相对路径与原正文，不因 AI 接入搬迁或另维护副本。

开发环境直接读 docs 中相同四层，编辑即生效，schema 动态生成，无需先打包。
list_docs 和 search_docs 可按 category 查询；read_doc 使用清单 ID，机制、
用户指南与 DSL 都可读取。其他源码、私人文件与文档层不自动纳入。

发行版按原路径复制到安装根 docs，加入 70-agent/manifest.json 和实际工具
schema，验证路径与哈希。独立 ZIP 同样保留 docs 下四层的完整目录。AI 根据
用户指南教用户操作，根据架构/DSL 文档解释脚本，实际调用遵循工具列表。

## 7. 状态与执行边界

执行用户、运行参数和方案数据在启动时冻结。主界面的当前用户、编辑对象、默认
选择、临时运行排序分别拥有各自状态，不为展示或发现执行持久化写回。
设备切换复用现有运行视图投影与草稿保存，运行中的其他任务不受影响。
幂等请求在会话及持久记录中校验内容，旧任务不自动重放。单条识别失败隔离并
保留可行动日志，部分采集失败不当作全部完成。

## 8. 已知验证范围

官方 SDK 的握手、发现、调用、Lv1 拒绝及多实例令牌隔离有本地验证。
WorkBuddy GUI 对本机 HTTP 的接受情况、Windows 打包和实际游戏全流程仍需
实机验收，不能用模拟数据宣称这些过程已通过。

## 9. 验收标准

| 场景 | 必须观察到的结果 |
|------|------------------|
| 源码检出后直接启动服务，没有生成文档包 | 文档可发现和读取，修改正文立即生效；工具 schema 来自当前接口 |
| 相同版本开发目录与干净发行目录 | 四层全部文档的 ID、相对路径与正文一致，游戏机制、操作指南与 DSL 可读取 |
| 主界面切换用户、Agent 指定另一个用户 | 返回新当前用户且全部用户仍可处理；连接地址和令牌不变 |
| 指定其他已连接目标 | 不要求额外授权或先手动选中，复用现有执行器；离线/忙碌时明确拒绝 |
| 未开通 Lv1、连接期间清除激活 | 所有协议访问返回激活提示，无工具/资源被调用 |
| 关闭 MCP | 后续访问拒绝，未执行桥接操作撤销，已启动游戏任务继续可停止 |
| 创建新配置、幂等重试、发布失败 | 不覆盖旧定义与用户默认，幂等返回原结果，失败不留半套可启动结果 |
| 配置或默认选择被其他操作修改 | 按修订拒绝陈旧保存/启动，不覆盖其他字段 |
| 扫描、分析与任务启动 | 明确真实数据、假设、覆盖范围和逐方案结果，用户/设备/参数在启动时冻结 |
