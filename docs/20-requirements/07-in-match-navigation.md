## 1. 背景与目标

部分局内任务在达成刷取目的后，直接等待对局结束或关闭客户端耗时较长。
例如渡尘墟花蕊织速刷、觉障林等玩法，都可以在进入对局后寻找最近撤离点，
主动移动到撤离区并完成撤离。

本需求不实现某个玩法的一次性坐标脚本，而是建立一套可被多个任务复用的
“局内地图目标导航”能力：

1. 打开地图并识别玩家位置、朝向和候选目标；
2. 按策略选择并锁定目标，首个策略为最近可用撤离点；
3. 短距离移动后重新观测，持续修正方向；
4. 靠近目标后切换为实景模板、颜色或文字判定，执行到达动作；
5. 识别失败、移动卡住或超时时安全停止，由业务工作流决定是否回退。

## 2. 范围

### 2.1 首批接入

- 渡尘墟：花蕊织速刷后寻找撤离点并主动撤离；
- 觉障林：完成任务目标后寻找撤离点并主动撤离；
- 后续具备“局内地图 + 可视目标点 + 到达交互”的玩法。

### 2.2 非目标

第一阶段不包含：

- 从任意地图图像自动推导全量道路网和最短路径；
- 复杂地形语义理解，例如自动区分楼层、攀爬点和不可越过的障碍；
- 通用战斗 AI；
- 长时间无观测的连续盲走。

第一阶段采用“短移动脉冲 + 重新打开地图定位”的闭环方案。
若玩法支持点击目标后生成小地图路线，可优先以路线色心方向作为导航观测。

## 3. 通用概念模型

通用导航层不得硬编码“渡尘墟”、“觉障林”或“撤离点”等业务名称。
它只处理以下概念：

| 概念 | 含义 |
|------|------|
| `navigation_profile` | 某类玩法的地图、检测器、移动及到达判定配置 |
| `player_pose` | 玩家地图位置、可选朝向及置信度 |
| `target_candidate` | 检测到的可导航目标，包含位置、类型和置信度 |
| `locked_target` | 已选中的目标，重新观测时优先继续跟踪 |
| `movement_pulse` | 有明确上限的一次短时移动，执行后必须释放输入 |
| `arrival_detector` | 地图距离较近后使用的实景模板、颜色、OCR 或组合判定 |
| `arrival_action` | 到达目标后的交互，如自动等待、点击、按键或长按 |

玩法差异通过 `navigation_profile` 和场景/布局绑定注入，不复制导航引擎。

## 4. 功能需求

### 4.1 进局判定

- 工作流必须以 HUD、地图入口或其他稳定画面标志确认已进入对局；
- 不得仅依赖固定等待时间；
- 等待超时必须返回结构化失败原因。

### 4.2 地图观测

- 支持通过布局绑定打开和关闭地图；
- 一次定位必须基于同一帧图像计算玩家与候选目标，避免动画期间跨帧错位；
- 支持颜色连通块、多点找色、单/多模板匹配及必要的组合检测；
- 检测结果必须使用画布归一化坐标，不与录制分辨率绑定；
- 支持连续两次或更多次观测一致后再接受低置信度结果；
- 无法定位玩家时严禁发出移动操作。

已确认的游戏机制（渡尘墟）：小地图**北朝上、箭头永远居中**，箭头是黄色内凹
（燕尾）形，尖端方向 = 人物朝向；视角另由箭头发出的光锥表示，**不需要识别**
（见 §4.4 的镜头反推）。大地图打开后可能不是整图显示、需要缩放，这是尚未解决
的部分（§10）。

小地图区域随地图走：每个玩法的 HUD 不同，所以每张地图自带一个 ``map_{key}``
HUD 场景（`minimap` / `minimap_center` / `open_map` + `full` 视图的 `full_map` /
`close_map`），坐标在布局层由场景编辑器标定。✅

### 4.3 目标选择与锁定

- 首个选择策略为地图距离最近；
- 距离计算必须考虑地图区域的宽高比，不得直接把归一化 X/Y 差值等权计算；
- 首次选中后建立 `locked_target`，后续重新定位优先继续跟踪它；
- 只有目标消失、明确不可用或新目标显著更优时才允许重选；
- 应使用滞回阈值防止在两个距离接近的目标间来回切换。

### 4.4 闭环移动

设计结论：**大地图只用来锁目标、取方位角；小地图高频观测朝向并持续修正；
镜头朝向不识别，从箭头反推。** 不存在任何需要实测的灵敏度常数。

三个角度的关系：摇杆推向 θ（相对镜头正前方）→ 人物朝"镜头朝向 + θ"的世界
方向跑 → 人物转身面向跑动方向 → 小地图箭头 = 跑动方向。于是
**镜头朝向 = 箭头方向 − 当前推杆角**，是一个观测量减一个已知量。

```
LOCK    开大地图 → 玩家位置 p、目标 t → 目标方位 b（世界系）→ 关地图
INIT    cam 未知时直推正前方 0.4 s，读箭头 h → cam = h
STEER   θ = wrap(b − cam)；move_steer(θ)（摇杆推到 θ，不抬手）
        每 0.3–0.5 s 读箭头 h：
            e = wrap(b − h)                 # 实际跑向与目标方位的误差
            cam = wrap(h − θ)               # 修正镜头估计（应对镜头自动跟随）
            |e| > 6° → 重算 θ，continueStroke 换方向
        每 N 秒或累计偏差大 → 回 LOCK 刷新 p、b
```

约束：

- `cam` 只在推杆角稳定 ≥ 0.5 s 后更新——人物转身有延迟，刚换方向那帧不能用；
- 箭头读不到 → `move_end()`，不盲走；
- 战斗锁定时人物横移，箭头 ≠ 跑动方向，导航前必须处于非锁定状态；
- 静止时箭头 = 上次跑动方向，与镜头无关，所以 INIT 必须真的推一下再读；
- 目标在镜头正后方（|θ| 接近 180°）时先推一小段让镜头跟随，或一次 `look_turn`
  粗转，再进入常规循环；
- 暂停或结束操作的最长响应时间不得超过一次观测周期；所有终止路径释放触点。

`look_turn`（视角拖动）在 v1 不进入主循环；若使用，其增益只能是**在线估计**
（每次转动后用箭头差值更新 EMA），配置里最多存一个粗略初值，不存"标定值"。

### 4.5 平台移动策略

#### 已实现：离散控制面 `general_move` ✅

控制场景拆出单视图场景 `general_move`，命名规则：`move_*` 是左屏摇杆的
**平移**（不改变视角，桌面绑 `W/S/A/D`），`look_*` 是右屏拖动的**镜头转向**
（不移动角色）。`turn_*` 这类会被误读为转向的名字不再使用。

| 实体 | 说明 |
|---|---|
| `move_center` + `move_forward/backward/left/right` | 摇杆中心与四个方向点，各带同名 arrow |
| `look_center` + `look_up/down/left/right` | 视角拖动起点与四个方向点，各带同名 arrow |

四个方向点到中心的**像素距离相等**（安卓 20:9、桌面 16:9 各按画布宽高比换算），
左/中/右同纵坐标、上/中/下同横坐标。DSL 直接可用：

```
drag [general_move].[move_forward] duration 0.3 hold 5.0 scale 3 exact   # 推满并保持（疾跑）
drag [general_move].[look_right] scale 2                                 # 视角右转两个臂长
click [general_move].[move_forward] hold 2      # 桌面：命中 activation_key → press W hold 2
```

`drag` 语法变更：中间过程时长必须写 `duration`；两点形态必须写 `A to B`；
`scale` 按倍数放大/缩小起点→终点向量（越界截断到画布边缘）；`exact` 关掉两端
抖动（默认两端都抖动，拖拽不能当精确依据，方向类拖拽显式 `exact`）。

各后端的 hold 语义已统一（见 `09-io-backends.md`）：a11y 两段 stroke 真正停住；
ADB Android 10+ 用 `motionevent DOWN→MOVE→sleep→UP`，更老系统退回匀速 swipe
并记警告；桌面 hold 期间响应停止。**时序敏感脚本以 a11y 通道为准。**

#### 待实现：连续控制（locomotion 原语）🔲

连续参数全部从 `general_move` 推导，不新增实体：摇杆圆心 = `move_center`，
推满半径 = ‖`move_forward` − `move_center`‖，视角单位距离同理。行动绑定是
**布局级**数据（与 `layouts.yaml` 的 `canvas` 同级），只引用实体 key 不复制坐标：

```yaml
locomotion:
  move: { kind: stick, scene: general_move, center: move_center, radius_from: move_forward }
  look: { kind: drag,  scene: general_move, center: look_center, unit_from: look_up }
# 桌面：move.kind = keys（读 activation_key），look.kind = mouse
```

按 `general_move` 命名约定可零配置推导，UI 只做显示/覆盖。原语（内置函数）：

```
move_begin(angle) / move_steer(angle) / move_end()    # 相对镜头，0=前 90=右
move_for(angle, seconds)                               # 脉冲封装
look_turn(delta_deg) / look_pitch(delta_deg)           # v1 不进主循环
```

安卓 stick 会话用 `continueStroke` 续段（单次 `dispatchGesture` ≤ 60 s，分段
50 s）；PC keys 按 8 方向量化，必要时先转镜头再按 W。任何 `_BreakSignal`/异常/
暂停都触发 `move_end()`，脚本不感知。a11y 支持多 stroke 同时进行（同时推杆 +
转视角），ADB 单指针做不到，这是后续选择通道的硬约束。

### 4.6 到达与交互

- 地图距离只用于进入“接近”阶段，不能单独作为完成证据；
- 接近后必须识别实景撤离区特效、交互按钮、提示文字或倒计时；
- `arrival_action` 支持自动等待、点击、按键、长按及玩法自定义过程；
- 执行交互后必须通过结算页、加载页、大厅或其他稳定标志确认成功；
- 未确认成功时不得将当前用户标记为任务成功。

### 4.7 防卡、超时与回退

- 连续多次移动后玩家地图位置几乎不变时判定为停滞；
- 停滞时可按配置执行侧移、跳跃、短距离反向或重新选择目标；
- 定位失败和停滞重试均必须有上限；
- 总导航必须有超时，超时后返回结构化失败，不得无限循环；
- 导航核心不直接关闭应用。关闭客户端、等待对局结束或转人工处理
  由调用方工作流决定。

### 4.8 日志与可诊断性

每轮观测至少记录：

- 导航配置 key、轮次和已用时间；
- 玩家位置、朝向及置信度；
- 候选目标数、锁定目标、距离和相对方位；
- 本轮移动角度、时长及平台实际输入；
- 重试、重选、停滞恢复和失败原因。

开发/诊断模式应能保存当轮原始帧和绘制了玩家、候选目标、锁定目标的覆盖图。
正常运行默认不持续落盘截图。

## 5. 架构边界

### 5.1 场景、布局与地图层 ✅

三层各司其职：

| 层 | 承载 | 编辑入口 |
|---|---|---|
| 界面场景 + 布局 | 屏幕系：`map_{key}` HUD 场景的 `minimap` / `minimap_center` / `open_map` / `full_map` / `close_map`；`general_move` 的移动与视角实体 | 场景编辑器 |
| 地图（`maps/{key}.yaml` + `base.png`） | 世界系：底图归一化坐标下的 POI、导航模式、朝向检测器参数、对 HUD 场景实体 key 的引用 | 地图管理 |
| 布局级行动绑定（待做） | 摇杆/视角/按键如何映射到 locomotion 原语 | 地图管理内的"行动绑定"区块（布局级，切换地图不变） |

地图管理**不做区域标定**，所有屏幕坐标只有场景编辑器一个入口；"标定 HUD…"
按钮跳转过去。打开大地图：PC 靠 `open_map` 的 `activation_key`（无坐标绑定），
安卓靠覆盖在小地图上的 `open_map` 区域。

地图定义示例见 `30-architecture/10-maps.md`。

### 5.2 视觉定位层

- 纯图像计算必须位于可离线测试的 Python 模块，不依赖 Qt 或设备；
- 现有 `find_icons()`、`find_multi_color()` 和 `color_vec()` 作为基础原语复用；
- 需要补充多模板检测、非极大值抑制、最近点选择与方位计算时，
  应优先实现为通用原语，不应新增 `find_duchenxu_exit()` 一类业务专用函数；
- 定位层返回结构化结果，不直接执行输入。

建议返回协议：

```json
{
  "player": {"x": 0.42, "y": 0.61, "heading": 128.0, "confidence": 0.93},
  "targets": [
    {"id": "candidate-1", "x": 0.71, "y": 0.23, "confidence": 0.88}
  ],
  "selected": {
    "id": "candidate-1",
    "distance": 0.47,
    "bearing": 35.0,
    "relative_bearing": 267.0
  }
}
```

`heading` 在地图无法稳定提取时可为空；此时只能选择不需要朝向换算的
路线跟踪策略，或安全失败，不得猜测方向。

#### 已实现诊断能力、待真机验收：小地图朝向 `recognizers/heading.py` 🟡

只依赖形状，不依赖模板：

1. 小地图中心附近按 HSV 取色（默认黄色 H 18–42），取离中心最近且面积足够的
   连通块；
2. 轮廓凸包 + 凸性缺陷：燕尾缺口是最深缺陷，缺陷两端的凸包顶点是两翼，
   **两翼中点 → 离它最远的凸包点（尖端）** 即朝向，基线是整个箭头长度；
3. 无明显缺口退化为"质心 → 最远凸包点"，置信度 ≤ 0.5；找不到返回 `None`。

角度约定：罗盘方位角，0° = 屏幕上方（北），顺时针为正。合成箭头 0–355° ×
三种缩放最大误差 2.1°，但合成图不能替代真机截图验收。HSV/搜索窗口/最小面积随地图保存
（`detectors.player_heading`），地图管理"小地图朝向"页可载入截图、按 `minimap`
区域裁剪、识别并叠加显示。

#### 待实现 🔲

- 大地图玩家标记、POI 标记检测器（模板 + NMS），以及视口→世界坐标变换；
- 大地图非整图显示时的缩放/平移匹配（§10）。

### 5.3 导航状态机 🔲

地图定义声明 `navigation.mode`，状态机按它分支，业务 WF 不感知：

- **pathfind**（大世界，游戏自带寻路）：开大地图 → 定位目标 POI → 点击/标记 →
  关地图 → 监视位置随时间变化 → 停滞超时则重新标记或失败 → 接近 → 到达判定。
  不需要朝向、不需要 locomotion 原语。
- **closed_loop**（渡尘墟/觉障林，无寻路）：§4.4 的 LOCK / INIT / STEER 循环。

```text
WAIT_READY
  → LOCK        开大地图 → 玩家位置、目标、方位角 → 关地图
  → [pathfind]  MARK → MONITOR
  → [closed]    INIT → STEER（小地图高频修正）→ 周期性回 LOCK
  → STALL       连续 K 次大地图位置几乎不变
  → APPROACH    距离阈值内缩短观测间隔、切实景检测
  → ARRIVAL_ACTION（被打断 → 回 APPROACH）
  → VERIFY_SUCCESS
  → SUCCESS | FAILED | TIMEOUT | CANCELLED
```

`ARRIVAL_ACTION → APPROACH` 的回边是必须的：撤离通常是站区域倒计时，被攻击或
走出区域会打断。

建议由 WF 负责业务起止、参数与回退，由 Python 导航服务/内置函数负责
定位、目标跟踪、方位换算和平台移动。不应把数学运算、置信度聚合和
平台触摸细节堆入业务 WF。

## 6. 与现有花蕊织流程的关系

当前 `weekly_huaruizhi.wf` 开始匹配后只等待固定时间即返回，
批量收尾随后通过 `finish_huaruizhi.wf` 关闭客户端。

接入通用导航后：

1. 花蕊织工作流增加“快速撤离”参数，试运行期默认关闭；
2. 开始匹配后等待真正的局内画面标志；
3. 调用通用导航并传入渡尘墟配置；
4. 只有撤离成功或明确进入业务回退后才结束当前任务；
5. `finish_huaruizhi.wf` 仍保留关闭客户端能力，但它只是批量调度的最终收尾，
   不应成为导航核心的内部行为。

觉障林接入时复用相同状态机，只增加对应的 `navigation_profile`、
场景/布局实体、视觉样本和到达交互过程。

## 7. 安全要求

- 定位置信度不足时不得移动；
- 任何正常、异常、暂停、结束和超时路径都必须释放输入；
- 地图未正常关闭时不得发出角色移动指令；
- 检测到结算、掉线、死亡或离开对局时必须立即停止导航；
- 单次失败不得修改用户的场景、布局、地图截图或业务数据；
- 远程下发的导航 WF 继续遵守远程脚本来源警告与只读约束。

## 8. 验收标准

### 8.1 离线图像门禁

- 每个接入玩法必须提供多张原始地图截图，覆盖不同出生点、目标位置、
  分辨率与必要的画质差异；
- 每张样本明确标注玩家位置、朝向和全部有效目标；
- 自动检测结果必须在标注容差内，且最近目标选择正确；
- 没有玩家或没有目标的负样本必须安全返回未命中。

### 8.2 状态机门禁

- 使用伪定位器和伪输入后端覆盖成功、目标消失、停滞、超时、暂停和结束；
- 验证目标锁定与滞回策略；
- 验证所有终止路径释放键盘和触点；
- 验证 Android 与 Windows 对相同相对方位产生语义等价的移动。

### 8.3 实机验收

- 先提供“只识别不移动”的诊断模式，验证多局随机地图；
- 导航期间不得出现长时间未释放的键盘或虚拟摇杆输入；
- 任何识别不确定、界面错位或用户结束都能安全停止；
- 渡尘墟和觉障林分别完成独立的现场样本与连续对局验证后，
  才能将快速撤离设为默认行为。

## 9. 实施阶段

1. ✅ **控制面与 DSL**：`general_move` 拆分；`drag duration / A to B / scale / exact`；
   各后端 hold 语义统一。
2. ✅ **地图管理**：地图实体、HUD 场景自动生成、底图导入、POI 标注、场景绑定。
3. ✅ **小地图朝向**：内凹箭头解析 + 对话框内测试页。
4. 🔲 **真实样本验证**：用实机截图在地图管理里验证朝向识别，调 HSV 阈值；
   收集大地图、接近撤离区、交互与成功页面截图。
5. 🔲 **locomotion 原语**：布局级行动绑定、`move_begin/steer/end`、a11y 连续
   stroke 会话、PC keys 量化；诊断 WF 验证 INIT（推一下读箭头）。
6. 🔲 **大地图定位**：玩家/POI 检测器、视口变换；解决非整图显示的缩放匹配。
7. 🔲 **闭环导航**：§4.4 循环、停滞检测、安全超时；先"只识别不移动"的诊断模式。
8. 🔲 **到达与撤离**：实景检测、撤离交互、成功验证；业务接入先渡尘墟（默认关闭）。
9. 🔲 **pathfind 模式与 Windows 完善**。

## 10. 待确认的游戏机制

每个玩法接入前必须确认：

1. ~~全地图是否始终正北朝上~~ → 已确认：小地图北朝上、箭头居中；大地图按
   `north_up: true` 处理，待实机复核；
2. 地图是否稳定显示玩家位置、朝向和全部可用撤离点；
3. **大地图打开后可能不是整图显示、需要缩放**——已确认存在，是当前最难的部分：
   需要决定固定缩放级别、拼接底图或做视口匹配；
4. ~~点击撤离点能否跟踪~~ → 已确认：大世界有游戏寻路（`pathfind` 模式），渡尘墟
   等特殊地图没有（`closed_loop` 模式）；
5. 地图上的直线方向是否在大多数出生点可行，以及常见障碍和楼层差异；
6. 到达撤离区后是自动倒计时，还是需要点击、按键或长按交互；
7. 撤离成功、撤离失败、角色死亡和掉线各自有哪些稳定画面标志。

上述机制在渡尘墟和觉障林之间可以不同，但不应导致导航状态机分叉；
差异应收敛在玩法配置、检测器和 `arrival_action` 中。
