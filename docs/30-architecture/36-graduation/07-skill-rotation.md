# 技能轴查看

毕业率方案只给出一个 DPS 数字，看不出「伤害来自哪个技能」。技能轴查看器
从原始的毕业率计算器 Excel 读取竞速轴，把 DPS 拆回到每个技能。

## 为什么必须回到 Excel

编译成方案 JSON 时**技能名会被丢弃**。以鸣金·虹为例，编译产物有 5690 个
节点，其中字符串常量只剩一个「期望」——`total_damage` 退化成一个 `sum`
节点加上一串匿名数值：

```
["sum", 1, 352, 352, 352, 471, 522, ...]
```

数值本身是精确的（用方案的 `baseline_attrs` 求值，`total_damage` 与
`reference` 完全一致），但无法还原技能身份。按子图常量做指纹聚类试过：
139 次命中聚出 110 组、其中 97 个是单例——不同 buff 层数、不同段数都会改
变常量组合，聚类不可靠。

**技能名在编译时的信息损失是不可逆的，只能回到源 Excel。**

## 数据来源

Excel 的「期望」工作表就是竞速轴本体，一行一次技能释放：

| 列（按表头名定位） | 含义 |
|---|---|
| `技能` | 技能名 |
| `次数` | 该行代表几次命中 |
| `期望` | 该行的伤害贡献，**已含次数** |
| `类型` | 剑 / 枪 / 群体奇术 / 心法…（部分表没有） |
| `外功倍率` / `属性倍率` | 技能倍率（部分表没有） |

`Σ期望`（不乘次数）恰好等于方案的 `reference.total_damage`。11 份表全部
通过总伤 + DPS 双项对账。

### 必须按表头名定位列

11 份表的**列位置并不一致**：技能列出现在第 17 和第 18 列，类型列在
33 / 34 / 35 / 38 / 39 列都出现过。只有第 1 行的表头名是统一的。
写死列号会在约一半的表上解析错位。

### 性能注意

用 `iter_rows` 按行读，不要用 `read_only` + 随机 `cell(r, c)`——后者在最大
的一份表（786KB / 314 行轴）上实测 **7.4 秒**，按行迭代只要 **80ms**。

## 模块

| 文件 | 职责 |
|---|---|
| `core/graduation/rotation.py` | 解析「期望」表 → `Rotation` / `RotationHit` / `SkillDamage` |
| `ui/loadout/rotation_dialog.py` | 只读查看器：伤害来源表 + 轴序表 |

## 入口

**「最优组合」对话框首行最右侧**的扁平「技能轴」按钮。

刻意**不放进备战方案主工具栏** —— 这是实验性功能：要用户自备毕业率计算器
Excel，且与备战流程无关，不宜直接开放。

> 放置位置踩过两次坑：`EquipStatusTab` 自己那排 `action_row` 在 LoadoutPanel
> 里被 `set_embedded_mode(True)` 整个隐藏，加在那儿用户根本看不到；
> 主工具栏（`loadout_panel.py` 的 `tools` 行）则过于显眼。

只读：伤害数值直取 Excel 已算好的 `期望` 列，不重算、不改表。

## 当前范围与边界

**只做查看，不做编辑。** 编辑轴需要重算伤害，而现有编译产物把轴烤成了
常量（`program.inputs` 只有 35 个属性字段，倍率与增益全是 `const` 节点），
改轴对已编译的 program 毫无影响。三条可行路径各有代价：

| 方案 | 代价 |
|---|---|
| 每次编辑重跑 `convert_workbook` | 实测 3.15 秒（鸣金·影，8151 节点），只能做「应用更改」按钮 |
| 把轴的倍率/增益列也绑成 program input | 输入数从 35 涨到数千；`ProgramCompiler` 的 bindings 目前是静态 `INPUTS` 字典 |
| 在 `excel_formula` 上加依赖追踪做增量求值 | 工作量最大，但唯一能做到实时更新 |

真要做编辑前还需先定产品边界：改次数和顺序是重排，改倍率等于改游戏数据，
那更接近模拟器而非编辑器。

## 一个未做的低成本增量

编译时把 `技能 / 次数 / 类型` 三列一并写进方案 JSON（约 30 行），毕业率
面板就能不依赖 Excel 直接显示伤害来源。当前 schema 里没有位置放它们。
