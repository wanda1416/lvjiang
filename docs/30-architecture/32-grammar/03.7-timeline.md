# timeline — 并发输入时间线

其余指令都是**严格线性**的：一条执行完才有下一条。`timeline` 用来描述"若干路输入
各自在时间线上何时开始、持续多久"，典型场景是**推住摇杆后退的同时跳三次**。

需求与边界见 [03-input-timeline.md](../../20-requirements/50-platform/03-input-timeline.md)。

## 一、语法

```wf
timeline
    @0.0  drag [general_move].[move_backward] duration 0.1 hold 2.4
    @0.4  click [general_combat].[tiaoyue]
    @1.4  click [general_combat].[tiaoyue]
    @2.4  click [general_combat].[tiaoyue]
end
```

- `@<秒>` 是**相对本块起点的绝对偏移**，不是间隔。并发的正确性只取决于各路何时
  开始；用间隔表达会让"第三路相对谁"变含糊。
- 条目按偏移排序执行（解析期排好），允许多条同偏移；同一时刻**先抬后按**，否则
  同键紧邻的 up→down 反过来会丢一次按键。
- 偏移接受固定秒数、`(min, max)` 区间与变量，与 `wait` 一致。

## 二、块内只允许输入类语句

允许 `click` / `drag` / `press`。

`scan` / `find` / `if` / `loop` / `call` / `wait` 一律**解析错误**（`env:` 守卫除外，见第三节），错误直接指向那
一行。识别要几百毫秒且时长不确定——允许它就等于承认时序会漂，而"看着严格、实际
漂移"比不支持更糟。

条目也不能带 `after wait`：时序由 `@偏移` 决定，写了不会生效，而"写了没生效"最难
发现。持续时长请用 `hold`。

`press ... down` / `press ... up` 同样被拒：时间线本来就用偏移 + `hold` 表达"从几点
按到几点"，再来一对裸 down/up 只会让释放时机没人管。

### 与 `hold` 的关系

`@偏移` 说的是**这一路何时开始**，`hold` 说的是**这一路持续多久**，两者正交。

## 三、跨端差异用条目级 `env:` 守卫

条目可以带环境守卫，复用单行守卫那串 token，写在**偏移之后**（时间列保持对齐）：

```wf
timeline
    @0.0  env:"desktop" -> press "S" hold 2.4
    @0.0  env:"android" -> drag [general_move].[move_backward] duration 0.1 hold 2.4
    @0.4  click [general_combat].[tiaoyue]
    @1.4  click [general_combat].[tiaoyue]
end
```

两端只有一两路不同时，共享的其余几路只写一遍。把整块复制两份也能跑，但复制正是
漂移的来源——调 `2.4` 这个数值时得记住改两处。

守卫是**编译期选择**：`run_env` 在块开始之前就已确定，过滤不消耗任何时间预算。这也
正是守卫能进块、而 `if` 不能的分界——后者的条件可以调 OCR。不匹配的条目根本不生成
步骤，整块原子性不受影响。

移动之所以非分不可：桌面按 WASD，安卓推虚拟摇杆，**不是同一个动作换绑定**。
`general_move` 的方向是 arrow，而 arrow 没有 `activation_key`，所以 `drag` 在桌面不会
转成按键。其余动作写 `[场景].[实体]` 即可两端通用——各端按 `activation_key` 自行决定
按键还是触点。

## 四、各通道支持情况

| 通道 | 支持的步骤 | 说明 |
|---|---|---|
| PC（SendInput / PostMessage） | 按键 | 按键与鼠标各有独立状态。触点类步骤明确拒绝——端游的移动是 WASD 而不是鼠标拖拽 |
| 设备端手势（a11y） | 触点 | 整块编译成**一个**多 stroke 手势下发。按键类步骤不支持：安卓侧 `keyevent` 是一次性的，任何路径都不可能真正保持 |
| ADB shell input / Shizuku | 不支持 | `input swipe` 单指，`input motionevent` 无法交错两个 pointer |

用到并发的脚本要声明能力，加载期即判定：

```wf
#% requires: [device_gesture]
```

见 [07.1-metadata.md](07.1-metadata.md)。

## 五、边界与限制

- **整块原子**：多 stroke 手势任一路失败，系统回调是整组取消。校验因此放在下发
  之前——宁可不执行，也不要留下"摇杆推住了、点击没落地而手指还按着"。
- **停止先释放**：执行期间按停止会先抬指/松键再返回。不放的话角色会一直往一个
  方向走，而用户以为任务已经停了。异常路径同样释放。
- **总长上限约 60 秒、同时最多 10 路触点**（系统手势限制），超限在下发前拒绝，
  不截断也不拆成多次下发——拆开就不是同一个手势，并发语义会丢。
- **设备端的推杆是"推到位 + 微动保持"**：`duration` 走完推进段，`hold` 期间手指贴着
  终点沿同一轴小幅往复（振幅几像素）。一条 stroke 按弧长匀速插值，真正的静止表达不
  出来；而零位移的触点对动态摇杆等于没给方向（实测会被游戏拿下一个触点猜方向）。
- **失败不吞**：设备端返回 `ok=false` 要向工作流传播，不能把未执行的手势当成功。
- **不做时长补偿**：实际耗时略长于声明总长是正常的（系统调度）；引擎不追赶、不补发，
  只在超出预期时记一行日志。
- **真实触摸会取消整组手势**：用户碰屏幕则本块失败并如实报错。

## 六、PC 侧的排程方式

PC 端不编译成手势，而是按偏移排程：以单调时钟为基准，到点下发对应的 down/up 或鼠标
动作，各路互不阻塞。因此「同刻先抬后按」的规则在 PC 端同样适用，且停止时必须先
释放已按下的键。
