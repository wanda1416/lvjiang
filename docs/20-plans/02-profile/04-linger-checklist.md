# 袅袅之音清单（linger）

> 状态：部分实现（2026-11-19）。第一版只有「记录」：清单、勾选、按用户落盘与云端同步。
> 入账到 profile、周期型来源、「记录不入账」开关见下文「未实现」。

## 1. 背景

攻略把国服当前版本可获得的长鸣资源「袅袅之音」整理成 219 枚常驻来源（8 个地区 +
通用），玩家需要逐条核对哪个途径还没拿。用「用户总览」的数值单元格记录这件事
做不到：单元格只有一个数字，看不出是哪一条途径、还剩哪些，而且手工 +1 的来源会被
写成配置里的第一个来源（`cell_editing.py` 取 `kd.sources[0]`），账本里全是错的归属。

## 2. 边界：谁是谁的事实

| 层 | 载体 | 事实归属 |
|---|---|---|
| 清单 | `config/system/yysls/lingering.yaml` | 游戏事实（地区 / 条目 / 枚数 / 来源文案），随版本下发 |
| 覆盖 | `config/local/yysls/lingering.yaml` | 用户对清单的新增 / 修改 / 隐藏；与 system 同名同结构的覆盖层 |
| 记录 | `users/<用户名>.linger.json` | 用户事实（每条已得多少枚），云端 `kind=linger` |
| 定义 | `config/session/profile.yaml` | key 及它的周期、上限，唯一来源 |
| 账本 | `profile.db` + 云端 | 入账后的事实；第一版尚未写入 |

三条硬约束：

1. **清单不出现 profile key。** key 是用户可改名、可改周期与上限的变量，把 key 名和
   当时的 `period`/`cap` 写进随版本下发的内容，等价于把变量值当常量：改个上限页面就
   报错，改个名字绑定就失效。绑定关系属于定义层（下一版用 key 上的标签收集），
   清单只描述游戏事实。
2. **周期型条目不进记录文件。** 每周/每月/半赛季/赛季的配额以 profile 的 quota 值为
   事实，读取时按周期派生、跨周期自动归零。记录里再存一份 `done` 会立刻造出第二份
   真相（周一 05:00 后 JSON 说 2/2、profile 说 0/2），而且历史周期无法回填。
3. **条目 id 稳定，label 只用于展示。** 记录键是 `<地区 id>/<条目 id>`，改文案不动 id；
   清单删掉条目不清理用户记录，页面应把它标成「清单已移除」。

## 3. 已实现

- `apps/yysls/core/linger/`：清单模型与校验、`config/system` 加载（坏文件逐份隔离）、
  每个用户一份记录的仓储（`user_write_access` + 线程锁 + `locked_paths` + 原子替换 +
  `revision` + `mark_dirty`）。
- `apps/yysls/sync/documents.py` 登记 `linger` → `.linger.json`：云端键是
  `(账号, 用户名, linger)`，服务端不校验 kind 枚举，网页文档页可直接看明文 JSON。
- `config/system/yysls/lingering.yaml`：一份文件 9 个地区（`regions` 按地区 id 索引），合计 219 枚，与攻略逐地区口径一致
  （清河 15 / 开封 26 / 皇宫 18 / 河西 30 / 不见山 37 / 青州 14 / 江南 30 / 未央城 19 /
  其它 30），已登记为版本化目录并进入 PC→手机配置白名单。
- 菜单「燕云 → 袅袅之音」打开非模态窗口：左栏地区进度，右侧条目表（地区 / 条目 /
  枚数 / 已得 / 编辑 / 来源 / 更新时间），勾选即写入，修改即落盘，顶部显示
  「已记录 N/219 枚 · 完成 M/101 条」。列宽按内容量出实际所需后再摊富余，不让
  单列吃掉全部空白。
- 条目类型（``kind``）：``single`` / ``roster`` / ``periodic``，一个字段同时决定「怎么记」
  和「能绑哪类 key」。``named: true`` 是旧写法，按 ``roster`` 读入。绑了 ``quota:``
  目标就会被判为 ``periodic``；声明周期却没绑配额 key 则降级为 ``single``，不留半周期
  半固定的状态。
- 周期型：已得 = 配额 key 本周期当前值（``profile_read`` 读时归零），改「已得」就是把
  差额写进账本，本地记录文件里一条都不存；219 那个分母与地区进度都只统计非周期条目。
- 子项（``kind: roster``）：以武会友这类「每一枚对应一个具体对手」的条目，记录里存
  ``slots``（``done`` / ``name`` / ``at``），已得枚数由勾上的子项推出。主表在这一行
  行首画折叠三角，**点行就地展开**成 N 个子行（第 N 位 / 已得 / 名字），再点收起；不另开
  窗口，展开后仍能对照上下条目。名字可为空，先记结果、之后补；填名字自动勾选。
- 入账：记录里每条形如 ``done`` / ``booked``；``done`` 变多时按差额写一条
  ``profile_action(…, delta=done−booked, source=条目来源, trigger_sync=False)``，成功才把
  ``booked`` 推到 ``done``。**先记录后入账**，账本写失败就留在「待入账」，不会出现
  账本有、记录没有。改小时先冲销（来源「撤销：<条目来源>」），冲销失败则这次改动不生效。
  `trigger_sync` 必须为假：`niaoniao` 挂着八音窍的账（`byq_countdown` 倍率 −1、
  `byq_jindu` 负向），触发同步会让每勾一枚都平白扣掉八音窍累计。
- 「同步记账」开关：**默认关闭**（勾选只写记录），按用户存在 `interface.json` 的
  `ui_state.linger_booking`（本机界面状态，不跨设备）。打开后只对之后的改动生效，
  不会补写历史；顶部同时显示「已入账 N/219 枚 · 待入账 M 枚」。
- 条目增删改：页面「新增 / 编辑 / 删除」经 `resolver.save_merged` 写 local 同名层
  （注册表增量：`regions.*.items` 按 `id` 原位替换，local 只存被改的条目）；system
  一个字节不动，版本升级新增的条目照常出现在合并视图。删除内置条目是打 `hidden`
  标记（合并层不允许删系统条目），记录保留；新增条目 id 为 `u<随机8位>`，改名不改 id。
- 入账目标分两层：固定/逐位条目统一用顶部「同步模型」（账号级 `default_target`，
  存覆盖文件），条目不再各存一份；周期型必须用自己的配额 key（`target: quota:...`）。
  表格只保留「类型」列（固定 / 逐位 / 周期），不再逐行显示目标。
- 批量绑定：多选行后统一绑到同一个配额 key（或解绑回固定），只改 `target`/`kind`，
  其它字段的用户改动保留。
- 批量绑定：多选行后统一绑到同一个配额 key（或解绑回固定），只改 `target`/`kind`，
  其它字段的用户改动保留。
- 分类对齐游戏内任务体系（主章/残章/探游/奇遇/侠迹/镇守/试炼）+ 途径本质分类
  （妙妙庙独立成类；兑换=代币兑换点如鲮货郎/琳琅/凭引；图鉴=收集册成就系统）。
  `label` 是简短任务名（不带卷号/上下这类冗余）；展示名 = `类型：条目`。
- 来源命名规范：`系统：区分词`——跨地区重复的系统用地区
  （`妙妙商店：清河`、`以武会友：河西`、`地图探索：开封`），地区内唯一的用任务名
  （`镇守：大散关`、`侠迹：奉敕不杀`、`宝箱：芙蕖苑`），账本已有既定词的沿用
  （`地图探索：尝草录`）。来源是对账 join key，不迁就旧词、不回改历史。
  2026-11 规范化后全表 102 条 / 217 枚（删与琳琅重复的捕猎马猴、探游拆条 1+1）。
- 分类对齐游戏内任务体系（主章/残章/探游/奇遇/侠迹/镇守/试炼）+ 途径本质分类
  （妙妙庙独立成类；兑换=代币兑换点如鲮货郎/琳琅/凭引；图鉴=收集册成就系统）。
  `label` 是简短任务名（不带卷号/上下这类冗余）；展示名 = `类型：条目`。
- 来源命名规范：`系统：区分词`——跨地区重复的系统用地区
  （`妙妙商店：清河`、`以武会友：河西`、`地图探索：开封`），地区内唯一的用任务名
  （`镇守：大散关`、`侠迹：奉敕不杀`、`宝箱：芙蕖苑`），账本已有既定词的沿用
  （`地图探索：尝草录`）。来源是对账 join key，不迁就旧词、不回改历史。
  2026-11 规范化后全表 102 条 / 217 枚（删与琳琅重复的捕猎马猴、探游拆条 1+1）。
- 详情：条目带 `detail` 多行文本，列表只显示摘要，双击「详情」列打开只读窗口；
  正文在编辑器里改（覆盖文件的 `detail` 字段）。单击任意列都是选中整行。条目名统一为「类别·对象」的短形式，长说明进详情。
- 网页文档页把 `linger` 显示成「袅袅之音」（`server/web` 的 `KIND_LABELS`，
  dist 需要下次构建才生效）。
- 测试：随包清单合计与条目键唯一性、坏文件隔离、记录的钳位与空写、子项推导与
  尾部空行裁剪、`booked` 不被改小抹掉且不超过 `done`、入账参数（`trigger_sync=False`）、
  开关按用户隔离、文档通道识别出 `(用户名, linger)`。

## 4. 未实现（下一版）

| 项 | 结论 / 约束 |
|---|---|
| 批量「补入账」 | 现在只能靠条目再次变化触发入账。要做批量入口，需先给出「将写入 N 条 / M 枚」的二次确认，并按 source 回查避免重复写 |
| 批量解绑的账本处理 | 批量改成周期/解绑只动配置，已入账的历史不回滚；如果某条之前是固定来源且已记账，切换类型后历史仍按原 key 保留 |
| 以武会友的 `ywhy_<地区>` 笔记 | 目前与新清单并存。计划一次性懒迁移 `x/y` 文本进 `done`，之后冻结旧笔记，不双写 |
| 入账目标可配置 | `stock:niaoniao` 目前是代码里的默认值；将来允许用户改绑（目标 key 是变量，不能写进清单内容） |

## 5. 验收

- 打开窗口应有 101 个条目、合计 219 枚；勾选/微调后 `users/<用户名>.linger.json`
  立刻出现且 `revision` 递增，重开窗口值不丢。
- 两个角色分别记录，互不影响；切换主界面用户时窗口跟随，开关状态也跟着该用户。
- 勾选一条后「用户总览」的袅袅库存同步 +1，历史里来源是条目自己的文案；
  打开「记录不入账」后勾选只涨记录、账本不动。
- 清单文件写坏只丢该地区，其余地区照常显示，日志一条 error。
