# 国际化需求与验收

> 状态：部分实现（2026-11-09，基线 v0.15.11）。

## 目标与范围

面向用户的界面、错误消息和配置显示名都必须能切换语言。界面与错误消息走 `tr()` 词表；
随包配置里的显示名写在配置自己身上（见下节），两者不混用同一张词表。缺失译文显示中文原文，
不显示空白；开发者日志和源码文档不要求翻译。

随包 12 种语言（`zh_CN`、`en_US`、`zh_TW`、`ja_JP`、`ko_KR`、`de_DE`、`fr_FR`、`es_ES`、`pt_BR`、`ru_RU`、`th_TH`、`vi_VN`），按来源分三档：

- **权威**：`zh_CN`（原文）、`en_US`（人工全译）；
- **同源生成**：`zh_TW` 由简体经 OpenCC `s2twp` + 区域校订生成；`ja_JP` 的**游戏术语**由中文经 `s2t` + 日本新字体 + 词组修正生成，其余文案仍英文回退；
- **英文回退**：`ko_KR`、`de_DE`、`fr_FR`、`es_ES`、`pt_BR`、`ru_RU`、`th_TH`、`vi_VN` 与 `en_US` 逐字相同——对这些语言，完成度指英文回退覆盖率而非本地化程度。

生成档词表可读但不是官方措辞，质量低于 `en_US`；各档完成度与生成方式见
[多语言词表现状](../../10-game/20-translation/08-i18n-language-status.md)。

## 用户行为

在设置选择语言，重启后生效；用户的语言偏好与模型、游戏截图文字和业务身份分离。游戏 OCR 文本匹配使用游戏原文，不能跟随 UI 翻译改变。

## 配置显示名的载体

软件自身的文案属于代码，配置项的显示名属于配置数据——两者的所有者、生命周期和
维护工具不同，不能塞进同一张词表。随包配置的纯展示字段可以直接写按语言取值的映射：

```yaml
envs:
- key: android
  name:
    zh_CN: 安卓
    en_US: Android
```

- 只有**纯展示**字段允许这种形态：`plan.name`、`envs[].name`、`delay_params.*.label`
  等。承担计算、OCR 匹配或作为稳定 id 的字段（`plan.id`、`schools` 的键、词条名、
  属性名）永远是单个字符串——把计算键换成随语言变化的实体，识别和判定会直接失效。
- 用户自建内容（自己的方案名、环境名、等待参数标签）始终是纯字符串：读写都原样，
  不随界面语言变化，也不会被升级成映射。
- 读侧统一解析成当前界面语言的一个字符串，回退链为「精确语言 → 同语种其他区域 →
  `en_US`（仅非中文界面）→ `zh_CN` → 首个非空值」；写侧「改了哪种语言就只改哪种」，
  未改动的条目原样写回，其他语言一个键都不丢。
- 非中文界面优先英文兜底：随包 8 种语言本身就是英文回退，配置名再掉回中文会与同一
  界面的按钮、菜单脱节。中文界面不插英文兜底，`zh_TW` 经同语种匹配拿到简体原文。
- 当前只落地 `app.yaml`（环境名、等待参数标签、方案名），其余配置仍是中文纯字符串，
  逐文件切换即可逐文件生效，不需要迁移脚本。
- 录入通路是**手工编辑 YAML**，软件里没有多语言编辑入口。随包配置缺少 `en_US` 时由
  `tests/core/test_config_localized.py::TestShippedAppYaml` 拦下，新增或改写系统显示名
  必须同批补齐英文，否则门禁失败。

约定与实现见 `src/lvjiang/core/config/localized.py`。

## 验收

默认中文、切换英文后重启、缺失翻译回退和切回中文均符合预期。新增翻译不能覆盖已有不同译法，内容检查应暴露遗漏或冲突。

配置显示名的双语写入必须能被读回：设置页保存一次之后，未被编辑的条目在另一种语言下
仍取到原译文，用户自建的纯字符串不会被写成映射。

代码里每句 `tr("字面量")` 都必须在每个随包语言查到译文（硬门槛为 0 缺口），新增文案与词表条目必须同批提交；词表值必须是字符串且不带冒号，见 [国际化架构](../../30-architecture/38-platform/08-i18n.md)。

实现见 [国际化架构](../../30-architecture/38-platform/08-i18n.md)，改造记录见 [过程归档](../../40-development/2026-10/2026-10-09-i18n-adoption.md)。
