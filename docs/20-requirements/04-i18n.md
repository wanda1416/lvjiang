# 国际化（i18n）支持框架

> **状态**：✅ 已实现（v0.2.5）
> **优先级**：P2
> **依赖**：无前置依赖

---

## 1. 背景与目标

燕云十六声有国际版，项目需要对律匠进行国际化改造，至少额外支持英语（en_US）。

### 1.1 现状统计

| 类型 | 数量（字符串 token） | 是否需要翻译 |
|------|---------------------|-------------|
| 文档字符串（docstring） | ~2,409 | 否，保留中文 |
| UI 字符串（按钮/标签/菜单/对话框） | ~955 | 是 |
| 日志消息（logger.*） | ~233 | 否，开发者日志保持中文 |
| 错误/异常消息（面向用户） | ~187 | 是 |
| 其他字符串（含 YAML 配置 label/name） | ~938 | 按需评估 |

### 1.2 目标

1. 建立全局 i18n 框架，支持通过配置切换语言
2. 首先支持中文（zh_CN）和英文（en_US）
3. 后续新增语言只需添加翻译文件，无需改代码
4. 所有面向用户的 UI 字符串、错误消息、配置显示名均走翻译通道

---

## 2. 技术方案

### 2.1 总体架构

采用 **YAML 翻译文件 + Python tr() 包装函数** 方案，不依赖 Qt 的 .ts/.qm 工具链。

```
┌─────────────────────────────────────────────┐
│              lvjiang.i18n 模块               │
│                                             │
│  init_i18n(language)  ← 启动时调用，加载核心层│
│  load_app_i18n(app_id) ← 插件加载时调用      │
│  tr(text)             ← 统一入口，不分 QObject│
│  set_language(code)   ← 运行时切换（重启生效）│
│  available_languages() ← 扫描核心层翻译文件  │
│                                             │
│  内部：核心层 + 已加载插件层合并成一张扁平表  │
│  查找以中文原文为 key；找不到 → 返回中文原文  │
└─────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────┐
│         config/i18n/ 翻译文件目录             │
│                                             │
│  zh_CN.yaml            ← 核心层中文基准      │
│  en_US.yaml            ← 核心层英文翻译      │
│  apps/{app_id}/zh_CN.yaml ← 插件层中文基准   │
│  apps/{app_id}/en_US.yaml ← 插件层英文翻译   │
└─────────────────────────────────────────────┘
```

**核心层 / 插件层是两份独立文件，合并到同一张查找表**：`init_i18n()` 启动时
只加载核心层 `config/i18n/{lang}.yaml`；`load_app_i18n(app_id)` 在插件加载
时按需加载 `config/i18n/apps/{app_id}/{lang}.yaml` 并**合并**进同一张
`_translations` 表——查表以中文原文为 key，同一句中文若在核心层和插件层
都出现（或插件层内部自己重复），后加载的会覆盖先加载的，核心层总是先于
插件层加载，所以插件层能覆盖核心层的同名条目。这不是设计上鼓励的行为
（见 `tests/core/test_i18n_consistency.py` 的重复源文冲突检查），只是
实现上如实允许，写文案时应避免让同一句中文在两处出现不同译法。
`tr()` 本身是单一入口，调用方不需要关心某个字符串来自哪一层。

### 2.2 翻译文件格式

翻译文件顶层 key 按"模块/文件"分层，各模块自己是一个平级 dict，
**不套一层 `ui:`/`messages:` 之类的大类包装**：

```yaml
# config/i18n/zh_CN.yaml
meta:
  language: zh_CN
  display_name: 简体中文
  version: 0.2.5          # 未接自动化流程，长期停留在这个值，不代表文件没更新

main_window:
  title: 律匠 - 通用视觉 RPA 引擎
  menu_general: 通用
  # ... 每个模块一个顶层 key，按需再往下分层

settings_dialog:
  title: 配置管理
  language_label: 界面语言

messages:
  err_layout_not_found: '无法加载布局: {name}'
  err_panel_not_defined: 布局中未定义 panel {scene}.{panel}

config:
  layout_default: Default Layout
  delay_step_wait: Step Interval

# 机器抽取的占位段：手工整理进具体模块之前的字符串先落在这里，
# key 直接就是中文原文本身。见 §3.3。
auto_strings:
  '未选择窗口': '未选择窗口'
```

`en_US.yaml` 结构完全一致，值替换为英文。

### 2.3 tr() API

**统一使用 `tr()` 函数**，不区分 QObject 内外。`tr()` 以中文原文为 key，在翻译文件中查找对应值；找不到则返回原文（中文 fallback）。

```python
from lvjiang.i18n import tr

# UI 字符串
settings_menu = menubar.addMenu(tr("通用"))

# 含变量的字符串
QMessageBox.information(self, tr("发现新版本"),
    tr("发现新版本 v{latest}\n当前版本: v{current}\n\n是否前往下载？")
    .format(latest=latest, current=current))

# 错误消息
raise WorkflowUserError(tr("布局中未定义 panel ..."))
```

### 2.4 语言配置

在 `session.json` 的 `settings` 节点存储 `language` 字段：

- `"zh_CN"` — 中文（默认）
- `"en_US"` — 英文
- `"auto"` — 跟随系统 locale

启动时读取该配置，加载对应翻译文件。语言切换后需重启应用生效。

### 2.5 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 翻译文件格式 | YAML | 项目已重度使用 YAML，团队熟悉 |
| 翻译 key 策略 | 中文原文作 key，找不到时返回原文 | 未翻译的条目不会空白，直接显示中文 |
| 日志消息 | 引擎日志保持中文，UI 面板日志走翻译 | 开发者调试不受影响 |
| 运行时切换 | 重启生效 | 避免热切换的 UI 重建复杂度 |
| 默认语言 | zh_CN | 当前用户群以中文为主 |
| 文档字符串 | 不翻译 | 面向开发者，保持中文 |

### 3.2 配置文件翻译

YAML 配置中的显示名通过 `tr()` 翻译：

- `config/system/scenes.yaml` — 场景分组名
- `config/system/layouts.yaml` — 布局名称
- `config/system/app.yaml` — 延迟参数标签

> 曾经还有 `config/system/workflows.yaml`——脚本显示名/参数一度写在这里，
> 已于 0.5.4 作废（写用户偏好会冻住出厂后续更新，见
> [05-config-layering.md §四](../30-architecture/05-config-layering.md#四用户偏好不进配置层)）。
> 现在脚本名走 `.wf` 文件的 `#% name:` front-matter，不再是一份集中的
> 翻译对照表。

### 3.3 auto_strings：机器抽取占位段 + 内容一致性棘轮

`tr()` 调用不会自动进翻译表——新增一句 `tr("新文案")` 后，如果没人手动
往 `zh_CN.yaml`/`en_US.yaml` 补对应条目，找不到翻译时会静默 fallback 回
中文，不报错也不会在 CI 里被发现。为此两份核心翻译文件末尾各有一个
`auto_strings:` 段，key 直接是中文原文本身（`'某句话': '某句话'`），
先把缺口占住，再逐步搬进具体模块分类。

`tests/core/test_i18n_consistency.py` 用 AST 扫描全部 `tr("字面量")` 调用，
和翻译表比对，跑两条棘轮（只许下调，不许上涨）：

- **missing**：代码用了、表里没有的字符串数
- **orphan**：表里有、代码已经不再 `tr()` 的字符串数

同时检查一条更隐蔽的错误：**同一句中文如果在不同 key 下配了不同译法，
后加载的静默胜出**（查表是纯粹的"中文原文 → 译文"扁平字典，见 §2.1）。
一次真实事故就是 `auto_strings` 里 52 条未翻译的占位条目盖掉了前面已经
写好的手工译文——这条一致性检查就是照着那次事故补的。

## 4. 验证标准

### 4.1 功能验证

1. 启动应用（默认 zh_CN），所有 UI 显示中文
2. 在设置中切换为 en_US，重启后所有 UI 显示英文
3. 未翻译的条目显示中文原文（不空白、不报错）
4. 切换回 zh_CN 时，翻译查找直接返回原文（零开销）

### 4.2 测试用例

```python
# tests/core/test_i18n.py —— 机制测试（回退、并行遍历、结构对齐、meta 跳过）
# 按场景分 class，以下摘录对应真实的类/方法名，非逐字引用全文

class TestTrZhCN:
    def test_returns_original(self):
        """zh_CN 模式下 tr() 直接返回原文，零开销"""
        init_i18n("zh_CN")
        assert tr("开始执行") == "开始执行"

class TestTrEnUS:
    def test_known_translation(self):
        """en_US 模式下 tr() 返回英文翻译"""
        init_i18n("en_US")
        assert tr("配置管理") == "Settings"

    def test_fallback_to_original(self):
        """未翻译的条目返回原文"""
        init_i18n("en_US")
        assert tr("这是一个未翻译的字符串") == "这是一个未翻译的字符串"

class TestAvailableLanguages:
    def test_contains_zh_cn(self):
        """可用语言列表至少包含 zh_CN"""
        langs = available_languages()
        assert any(lang["code"] == "zh_CN" for lang in langs)
```

`tests/core/test_i18n_consistency.py` 是内容层面的补充（见 §3.3）：机制测试
只保证"查得到就能查到"，不保证"该查到的都配了译文、没有互相覆盖"——这条
测试补的正是这一半。

### 4.3 CI 检查

- `ruff check` 通过
- `pytest tests/core/test_i18n.py tests/core/test_i18n_consistency.py` 通过
- 翻译文件 YAML 格式有效

## 5. 后续扩展

### 5.1 新增语言

1. 复制 `config/i18n/zh_CN.yaml` 为 `config/i18n/{lang_code}.yaml`
2. 翻译所有条目的值（保持 key 不变）
3. 在设置对话框中自动出现新语言选项（`available_languages()` 自动扫描）

### 5.2 翻译平台集成

后续可接入 Crowdin / Transifex 等翻译平台，只需将 YAML 文件同步到平台即可。

### 5.3 字符串提取脚本

待实现：`scripts/extract_i18n.py`，扫描所有 `.py` 文件中的 `tr("...")` 调用，生成/更新 `zh_CN.yaml` 基准文件，对比已有翻译文件报告新增/删除/变更条目。

### 5.4 热切换（可选）

当前方案语言切换需重启。如需热切换：
1. `set_language()` 加载新翻译文件后发射 `language_changed` 信号
2. 各 UI 组件订阅信号，重新调用 `tr()` 更新文本
3. 复杂度高，建议非必要不实现
