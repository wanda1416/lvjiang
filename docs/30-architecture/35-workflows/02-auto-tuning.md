# 流程：自动调律（Auto Tuning）

## 目标

自动遍历装备背包的八个部位，对需要调律的装备执行调律操作，评估装备价值并决定是否调律或回收。

## 依赖场景

| 场景 | 用途 |
|---|---|
| `bag_equip_detail` | 装备背包主界面（含 bag_grid 面板） |
| `equip_weapon_detail` | 武器详情面板（OCR 识别装备属性） |
| `equip_armor_detail` | 防具详情面板（OCR 识别装备属性） |

## 执行步骤

### 1. 概述

用户配置决定当前调律目标（八个装备部位，武器部位需考虑勾选的流派）。

#### 1.1 遍历流程

1. 分别遍历装备背包的八个部位，根据传入参数决定是否执行该部位调律，不调则跳过。
2. 对于每个装备部位，根据传入的 `cols` 和 `rows` 决定当前部位调律策略（不同布局可能并非固定 3×6）。
3. 单个部位遍历策略：
   - **第一步**：对于前 `cols` 行，直接采用双重 for 循环遍历，不需要滚动。每次处理完写指纹到滚动管理器：`write(col, row, hash)`。
   - **第二步**：当确定 `(cols, rows)` 还有装备，意味着装备还有，则需要开始滚动步骤。转第 5 步。
4. 单件装备调律策略：
   - 单件装备需要评估是否需要调律和值得调律。
   - 对于不需要调律的装备（比如已经满词条，或者初始词条不符合要求的），直接跳过，或者后续决定是否自动回收。
   - 对于被回收的装备，下一件装备会自动前移到当前位置，前面装备不会变化，不用担心错乱。
   - 对于需要调律的装备，收集装备信息和调律要求传入单件装备调律模块，执行。执行完毕后重新读取装备，生成指纹。

#### 1.2 装备指纹生成方式

```
部位 + 等级 + 品阶 + 是否承音 + (词条名 : 数值)
```

示例：
```
冠+110+purple+承音+会意率:6.6+势:72.2+最大外功攻击:114.1+会意率:6.6+劲:72.2:转
```

对该字符串做 MD5 取前 8 位 16 进制结果，解析装备信息时直接写入 `_extra.hash` 字段。

---

### 2. 滚动状态判定

#### 2.1 状态图示

```
1 2 3 4 5 6        实际序列
1 2 3              滚动管理器维护的指纹，下面为实际
  2 3 4        <-  正常情况                        返回 0
  3 4 5        <-  滚动过头，需要 down 0.2          返回 -1
  1 2 3        <-  没有滚动，需要 up 0.2            返回 1
```

#### 2.2 变量定义

| 变量 | 含义 |
|---|---|
| `row_index` | 当前处理过的行数 |
| `last_real_row` | 当前实际出现的行数 |
| `first_real_row` | 当前识别的第一行实际所在的行数 |
| `fps` | 各逻辑行首列指纹（0 起始索引） |

---

### 3. 初始扫描

初始循环三行：
- 记录每一行第一个装备的指纹：`fps[0]`、`fps[1]`、`fps[2]`。
- 结束后：`row_index = last_real_row = 3`，`first_real_row = 1`。

---

### 4. 正常滚动循环

#### 4.1 滚动校验流程

为了正确处理新行，需要确保正常步进一行。

1. 滚动一行。
2. 读取滚动后的 `grid[1][1]`（即第一行装备的指纹）`nfp`。
3. 三向比较：
   - `nfp == fps[first_real_row]`：正常步进，`first_real_row += 1`。
   - `nfp == fps[first_real_row - 1]`：滚少了（首行没移走），小步补滚 0.25，`first_real_row` 不变。
   - `nfp == fps[first_real_row + 1]`：滚多了（跳过两行），小步回滚 0.25，`first_real_row` 不变。
4. 小步修正期间 `first_real_row` 不变，比较对象也不变，直到 `nfp` 匹配 `fps[first_real_row]` 才推进。
5. 连续 4 次判定"滚少了"→ 到底（内容不再移动）。
6. 连续 4 次判定"滚多了"→ 抛异常（不应发生）。

#### 4.2 滚动后的两种情况

我们必须意识到每次滚动，即使判定正常一行，也会出现两种情况：

| 情况 | 含义 | `last_real_row` |
|---|---|---|
| 新区域只有两行 | 滚动过短，没能将原来的首行彻底挪走（可容忍） | `first_real_row + 2 - 1` |
| 新区域有三行 | 完美滚动了一行距离 | `first_real_row + 3 - 1` |

由于确定滚了一行，每一轮 `first_real_row` 必定 +1。每一轮：
```
last_real_row = first_real_row + real_rows(grid) - 1
```

#### 4.3 步进容忍度

我们必须容忍新区域只有两行或者三行，因为我们不能确保滚动一定是完美的，虽然可以考虑算法精调。

**但是我们必须意识到，基于触摸滑动本身就是不精确的，所以一定要算法策略上处理这种不精确！所以不要考虑任何算法精调！**

#### 4.4 新行处理

每一轮滚动后，判断 `row_index` 和 `last_real_row`：

- `row_index == last_real_row`：没有出现新行，本轮不需要处理。
- `row_index < last_real_row`：区域出现了新行，直接处理 `real_rows(grid) - 1` 行即可（第三行或者第二行）。

#### 4.5 步进不足场景分析

假定实际步进只有 0.8，这将导致：

1. 第一次滚动后：`first_real_row = 2`，`last_real_row = 3`，`row_index = 3` → 不必处理。
2. 第二次继续滚动一行，此时还是必然 grid 实际只有两行可见：
   - `first_real_row = 3`，`last_real_row = 3 + 2 - 1 = 4`
   - `row_index < last_real_row` → 立刻处理当前区域的 `real_rows(grid) - 1 = 2` 行，这就是新行。
   - 处理完毕以后，对 `row_index` 执行累加：`row_index = 4`。
3. 由于这种步进不足一行，必然意味着误差累计，后面必然出现 `nfp == fps[0]`，导致小幅步进，修正误差。

因为我们只有处理完新行以后，才会更新 `fps[row_index]` 的指纹信息。所以实际上每次滚动后都是拿 `grid[1][1]` 的 `nfp` 和之前的比较。

---

### 5. 步进区间约束与 fps 数据完整性证明

#### 5.1 命题

每次确认步进后，fps 中 `row_index` 的下一行数据永远不为空。

#### 5.2 证明

**1. 步进上界 = 1 行：**

如果滚动 > 1 行，行 2 可见度 < 95% → 被过滤 → `grid[1][1] ≠ fps[target]` → 触发回滚 → 直到 ≤ 1 行才确认。所以确认步进的实际距离 `d ∈ (0, 1]`。

**2. 步进下界 > 0：**

距离 = 0 → 内容不动 → `nfp = fps[target-1]`（首行仍在）→ 判定"滚少了" → 补滚。所以有效步进 `d > 0`。

**3. 确认步进后：**

`first_real_row` 从 N 变为 N+1。此时实际滚动距离 `d ∈ (0, 1]`。

**4. 行 N+2 的可见性：**

行 N+2 原来在位置 2，滚动 d 后到位置 `2-d`。因为 `d ≤ 1`，所以 `2-d ≥ 1` → 行 N+2 仍在可见区域内。

**5. 行 N+2 在 grid 中的位置：**

行 N+1 在位置 `1-d`。因为 `d > 0`，所以 `1-d < 1` → 行 N+1 有 > 95% 可见 → 通过过滤 → grid 第一行 = 行 N+1。行 N+2 紧随其后 → 是 grid 第二行。

**6. fps 覆盖范围：**

- `visible_rows ≥ 2`（行 N+1 和行 N+2 都可见）。
- `last_real_row = (first_real_row+1) + visible_rows - 1 ≥ N+2`。
- `row_index` 最大 = 旧的 `last_real_row ≥ N+1`。
- 所以 `last_real_row > row_index`，新行永远可处理。

#### 5.3 结论

`d ∈ (0,1]` 保证至少 2 行可见，`fps[row_index]` 对应的行一定在可见区域内，不为空。

## 输出

- 遍历完成的装备指纹列表（`fps`）
- 需要调律的装备信息（传入单件调律模块）
- 调律/回收决策结果
