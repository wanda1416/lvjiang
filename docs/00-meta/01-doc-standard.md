# 文档规范

本文是文档体系与写作纪律的**唯一来源**。导航与层职责见
[文档中心](../README.md)；本目录的 [README.md](README.md) 只做索引与治理说明。

## 一、目录本身就是生命周期

核心研发文档只走一条单向线：**20-plans → 30-design → 40-reference**，60-guide 只收
普通用户必须点击操作的部分。

| 目录 | 唯一职责 | 进入条件 | 绝对禁止放进去 |
|------|----------|----------|----------------|
| 20-plans/ | 纯计划：调研、提案、方案对比、全局待办 | 尚未开始写代码，或只停留在想法/调研阶段 | 已落地的接口手册、操作步骤 |
| 30-design/ | 概念与实现设计（`01-architecture/` 架构、`02-decisions/` 取舍） | 开始落地代码（首版切片/原型即可） | 未落地提案、过程踩坑记录 |
| 40-reference/ | 稳定参考规格：契约、DSL 语法、数据模型、CLI/配置 Schema | 实现完毕且接口稳定，要被反复精确查阅 | 需求动机、过程记录 |
| 60-guide/ | 用户必知指南：安装、日常使用、必要排障 | 面向正式用户、不看就用不了的已发布功能 | 开发者调试开关、源码路径、内部协议、未发布实验特性 |
| 10-domain/ | 游戏客观机制事实 | 与律匠实现进度无关 | 程序实现细节 |
| 70-agent/ | 外部 Agent / MCP 接入契约 | 仅放对外暴露的入口与工具契约 | 重复正文、未开放能力 |
| 50-releases/ | 各版本发布说明 | 发版时新增，之后冻结 | 现行操作手册 |
| 80-history/ | 历史归档与按月开发日志 | 归档只读，由 `docs_index.py` 索引 | 现行规格 |
| 00-meta/ | 文档规范与极少量项目治理 | 仅治理调整时修改 | 业务提案、随业务提交顺手改动 |

**流转判断只看一句话**：还没写代码 → 20-plans（且只动这 1 个文件）；写了代码、有概念
和实现 → 30-design（原草案用 `git mv` 过来演进，不再两边各维护一半）；做完定型、要给
AI 或用户精确查字段/语法/命令 → 提炼契约进 40-reference；只有普通用户必须操作的部分才
补进 60-guide。

## 二、三条硬规则

1. **目录即阶段，不再双写状态**：纯计划只写 20-plans 里的单篇文档 + 在
   `20-plans/README.md` 挂一行链接；禁止顺手改动 00-meta、`01-backlog.md`、30-design、
   40-reference、60-guide。进入实现后把文档移入 30-design 演进；定型后再沉淀精确契约
   到 40-reference。
2. **禁止写时间戳与版本号废话**：活跃文档不写 `> 最后更新：…`、`（基线 vX.Y.Z）`；
   版本与修改日期一律以 Git 历史为准。`50-releases/`、`80-history/` 是冻结存档，不改。
3. **60-guide 严格面向终端用户**：只有普通用户不看就无法操作的正式功能才允许写入；
   开发工具、内部开关、调试 CLI 一律留在 30-design 或 40-reference，严禁复制粘贴进
   用户指南。

## 三、每份文档要有形

- **一个一级标题，且标题后必须空一行**：文件名之外不要再起第二个 `#`；`# 标题` 与下一行
  实际内容之间必须有空行（`# 标题` 紧接 `> 状态：…` 会把渲染与纯文本阅读都挤在一起）。
  代码块的「文件路径标注」不要用 `#` 当标题。
- **同一事实只在一层写全，其它地方只链接**。写完后自问「这条结论三个月后由谁来改」——
  答案不在本层，说明放错了地方。
- **需求文档写验收**：plans 的文档至少交代边界与验收标准，不能只有一段描述。
- **相对链接**：一律用相对路径，禁止写死绝对路径与行号；引用源码写符号名，不写 `L123`。
- **归档只读**：`archive/` 与 `80-history/` 下的文档不再改写结论；引用的文件名变了可以
  改链接。

## 四、目录与编号

- 层目录统一 `NN-name/`；层内文档统一 `NN-name.md`（两位数，从 `01` 起）。
- 子层目录用 `NN-name/` 且与层内编号不混用；子层内的文件从 `01` 重新编号。
- 同一目录内编号必须唯一；`03-` 与 `03.1-` 视为不同编号，但不要同时混排两套风格。

## 五、编目自动化（不要手工维护索引）

| 脚本 | 职责 |
|------|------|
| `python scripts/docs_check.py` | 死链与页内锚点、孤儿文档、入口可达、一级标题、目录内编号冲突与前缀、层索引是否登记了同目录全部文档 |
| `python scripts/docs_index.py --check` | 按月归档的开发日志、发布说明索引是否与目录一一对应 |

两个脚本都接在 `.github/workflows/ci.yml` 的 `Docs check` 步骤上；改动文档后本地先跑
一遍。门禁只保「链接和索引不烂」，不检查日期、基线或状态行。索引行的人工列（主题 /
说明）由脚本只在**新增行**时填，已有行不会被覆盖。

## 六、发布与迁移

- **发布时**：只更新版本文件、`releases/` 索引与版本说明；其他文档仅在内容确实需要
  变更时修改。不把开发期内部修正写成用户可见修复项。
- **迁移时**：历史日志不改写事实；若引用的文件名变了，允许把链接改成新路径，但不要
  改写当时的结论。

## 七、禁止事项

- 不在文档里写真实姓名、账号、API key、`config/session` 内容等私人设定。
- 不把未实现的能力写成「已可用」；未开放的能力要么明确写未实施，要么不写。
- 不用文档描述另一套与代码并行的流程；代码、需求、架构、用户指南四者冲突时，以代码
  与配置为准，并修正文档。

## 八、跨仓库与发行文档

主工程维护客户端使用说明，admin 维护签发、管理密钥、云端部署和发布协议。
跨仓库链接只用于主工程下检出 admin 的开发环境；客户端使用指南不得依赖私有 admin 正文。
admin 可以保留导航页，但操作正文不复制维护两份。

发行文档收录范围以 `apps.yysls.core.agent.documents.DOCUMENT_DIRECTORIES` 为准。
指向源码、配置或未随包交付文档的引用，在链接后标注“（仅源码检出）”；随包文档之间的
链接必须真实可达，不能用该标注跳过校验。

除原检查外，维护者从主工程根目录执行：

```bash
python scripts/docs_check.py --admin
python scripts/build_agent_bundle.py --output <新的临时目录>
python scripts/docs_check.py --bundle <上述临时目录>
```

admin 模式复用链接、标题、编号和索引检查。没有 admin 检出时明确报错，不把缺失目录当作
检查成功。发行包检查在 CI 构建临时文档后执行。
