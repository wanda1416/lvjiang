# Dev Log: 批量执行卡住 UI —— Earley 解析的 GIL 饥饿

> 日期：2026-10-06
> 涉及模块：`src/lvjiang/workflows/grammar/parser/api.py`、`src/lvjiang/workflows/engine/core.py`
> 关键词：GIL 饥饿、Earley 解析、批量执行、py-spy、卡顿现场采样

## 问题描述

「刷花蕊织」任务在**安卓 App 重启阶段**卡到不可用：主窗口 UI 几乎点不动，
用户总览刷不出来，连输入法打字都卡。用户提出的疑问是：明明只跑了一个工作流
（一个批量任务），为什么会把整个程序拖住？

## 排查过程

先用当次新增的采样脚本对运行中的律匠进程做旁路采样（脚本见
`scripts/diagnostics/python_process.py`，报告落 `config/local/diagnostics/`，
不进主仓库历史）：

```powershell
python -m pip install psutil py-spy
python scripts/diagnostics/python_process.py --pid 1234 --duration 180
```

本次现场（`process-28556-20261006-093253-1824`，72 秒 / 每 1 秒资源 + 每 5 秒全线程栈）：

| 观测项 | 数值 |
|------|------|
| 进程 CPU | 均值 67.7%，峰值 691% |
| 系统 CPU | 均值 25.8%，单核最高 88.4% |
| 线程数 | 98 ~ 120（每 1~3 秒批量新增 15 个，震荡 22 次） |
| 工作流线程 | 累计占进程 CPU **60.3%**，27 秒起连续 25 秒稳定在 81%~102%（吃满一个核） |
| UI 主线程 | 累计仅 **2%**，15/15 份栈快照均为 `idle`，栈顶是 `run_app`（Qt 事件循环） |
| 栈状态分布 | idle 83 / active 2 / **`active+gil` 5** |
| 工作流线程栈 | `batch_runner._run_locked → engine._execute_dsl → _exec_body → _exec_stmt`（`Wait`）`→ wait_seconds → precise_wait` |

关键判读：**UI 主线程不忙（2% CPU）却一直动不了**，说明它不是算不过来，而是
**排队拿不到 GIL**；同一时刻工作流线程有 1/3 的采样点正持有 GIL 执行 Python。
另外程序装了 `pynput` 全局键盘钩子，钩子回调同样要排队拿 GIL，所以连**系统级**
的键盘输入也被拖慢——这解释了「输入法打字都卡」这个看起来超出本程序的现象。

## 根因分析

CPU 尖峰出现在批量执行开始之后（第 27 秒），而工作流线程的栈里长期停在语句
执行与过程调用上。顺着调用方查下去，问题在**脚本加载**：

`parse_file()` 原本每次调用都无条件跑一遍 Earley 解析：

```python
def parse_file(path):
    ...return parse_text(text, source=str(path))
```

而批量执行会在**每个成员、每一轮、每次 `load_subcalls()`** 都重新加载同一批
`.wf` 文件。Earley 解析是纯 Python 的 CPU 密集计算，**全程持有 GIL**，于是：

- 工作流线程持续吃满一个核并长期占用 GIL；
- UI 主线程每次重绘、每个鼠标事件只能挤进几毫秒（Python 默认 GIL 切换间隔 5ms），
  16ms 一帧的刷新被拖成几十上百毫秒，观感就是「卡」；
- 全局键盘钩子同样排队，观感就是「打字卡」。

这也回答了两个疑问：

- **「只有一个工作流为什么不卡」**：一个工作流 ≠ 不卡。工作流跑在独立线程里，
  和 Qt 主线程**共享同一把 GIL**，它 CPU 打满就等于 UI 拿不到解释器。
- **「为什么只有 App 重启阶段特别明显」**：那一段是密集的加载 + 短等待 +
  反复识别，正是解析开销最集中的时刻。

## 解决方案

`c36895b8 perf(workflows): 复用未变化脚本的解析结果并隔离语法树`：

- `parse_file()` 按**规范绝对路径 + 实际文本**缓存解析结果（`lru_cache(maxsize=128)`），
  每次返回 `deepcopy` 的独立 AST，并加 `RLock` 避免并发 miss 重复解析；
- `load_subcalls()` 改走该公共入口；
- 不按 mtime 判断，因此同大小/同时间戳的修改、删除与热更新语义都保留。

修复后同一操作再采一次（`process-56380-20261006-095624-8860`，50 秒）验证：

| 指标 | 修复前 | 修复后 | 变化 |
|------|------|------|------|
| 进程 CPU 均值 | 67.7% | 30.8% | −54% |
| 进程 CPU 峰值 | 691.2% | 427.6% | −38% |
| 系统单核最高 | 88.4% | 56.9% | −36% |
| 线程数范围 | 98 ~ 120 | 79 ~ 94 | 少约 20 |
| 最热线程 CPU 占比 | 60.3%（一枝独秀） | 35.0%（其余 13.6/7.3/7.2/7.1/6.9） | 集中度大幅下降 |
| **栈状态 `active+gil`** | **5 / 15 份** | **0 / 11 份** | **采样中无线程持 GIL 跑 Python** |
| 批量新增线程次数 | 22 | 8 | −64% |

其中「`active+gil` 归零」是最直接的判据：采样瞬间已没有线程在持 GIL 执行
Python，UI 与键盘钩子不再排在它后面。用户实测同步确认不再卡顿。

两份报告（修复前后各一份）已归档在 `config/local/diagnostics/`，可随时复查。

## 教训

1. **「只有一个任务」不等于「不会影响 UI」**：只要工作负载与 UI 同进程、同 GIL，
   它打满一个核就等于 UI 卡住。判断这类问题时，先看 UI 线程是**忙**还是**等**——
   本次它只有 2% CPU 却全程 idle，一下子把方向从「UI 逻辑太重」纠到「GIL 被谁占」。
2. **架构性问题不要靠调等待精度或钩子来掩盖**：`precise_wait` 尾部 2ms 忙等、
   全局键盘钩子这两处同样是 GIL 竞争者，但它们是既有契约（等待精度、全局热键），
   本次刻意不动，只用解析缓存解决根因。
3. **性能问题要留现场证据**：这次从「感觉卡」到「定位到解析」靠的是可复现的
   旁路采样（资源 + 线程栈 + 当时的操作描述）。没有这组数据，「卡顿」很容易
   被归类成玄学而反复重查。
4. **缓存只解决重复加载**：首次解析、缓存淘汰后的解析仍会争用 GIL，这是已知
   边界，不承诺消除（已写入架构文档 `docs/30-architecture/32-grammar/07-subworkflows.md`）。
