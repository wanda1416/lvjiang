# 18. 批量的状态分层

> 状态：✅ 已实现

## 1. 问题

批量原来只有一个扁平的 `BatchConfigItem`，「批量配置」窗口和主页面批量页都直接
改它，划分依据是哪个界面方便，而不是语义。后果：

- 主页面的一次临时勾选、拖拽、轮数调整**全都写回配置组**（`batch.json`），于是
  `selected_*` 同时是"上次运行的勾选"和"下次打开的初始值"，说不清"恢复默认"
  该恢复到哪；
- 任务页的拖拽顺序落盘，用户页的拖拽顺序不落盘——同一个窗口里两种语义；
- `execution_unit_key` 这种**决定可见性与生命周期契约**的定义级设置长在主页面，
  而依赖它的「单用户直通」勾选框长在配置窗口，于是出现一个"灰着、勾着、在本窗口
  里找不到任何理由"的控件；
- 配置窗口保存时要"读盘再把主页面拥有的 7 个字段搬回来"，这段反向合并代码的存在
  本身就是所有权没划清的证据；
- 启动时 `window.py` 重新读 `batch.json` 取活动组，而用户名与脚本来自页面控件——
  执行快照由两个可能不一致的源头拼出来。

## 2. 四种状态

| 状态 | 对象 | 存放位置 | 谁能改 |
|---|---|---|---|
| 配置组定义 | `BatchConfigItem` | `batch.json` | 只有「批量配置」窗口 |
| 配置编辑器草稿 | 对话框内部 `_cfg` | 内存 | 对话框自己，点保存才落盘 |
| 本次运行草稿 | `BatchRunDraft` | `session.json` 的 `ui_state.batch` | 只有主页面批量页 |
| 执行快照 | `BatchRunSpec` | 内存（并进执行历史） | 点「开始」时冻结，之后不可变 |

两阶段的用户流程因此成立：**先定义配置组，再准备本次执行，点开始后冻结为不可变
计划。**

## 3. 字段归属

### 3.1 定义层

可见任务与初始顺序 `task_ids`、可见用户与初始顺序 `usernames`、默认勾选
`default_task_ids` / `default_usernames` / `default_units`、调度单元
`execution_unit_key`、Profile 排序键与方向、五个生命周期 wf 及其
`workflow_params`、`skip_lifecycle_for_single_item`。

- **可见与默认勾选是两件事**，所以配置窗口里一行两个勾选框（可见 / 默认执行）。
  只有一个勾选框时它必须同时表达"出现在主页面"和"默认要跑"，那正是旧版把主页面
  的临时选择写回配置组的根源。
- **默认勾选只是集合，不承载顺序。** 初始顺序由 `task_ids` / `usernames` 决定；
  `default_*` 回答的只是"首次加载或恢复默认时勾哪些"。
- **调度单元属于定义**：它决定主页面候选列表的内容、生命周期契约（多出
  `batch_unit_key` 等变量）、条目准备 wf 的合法性（`#% batch_unit_prepare`），
  以及生命周期能不能跳过。这些都不是"本次启动"级别的决定。
- **Profile 排序键定义的是"能力"**，不代表已经排过；排完的实际顺序属于运行草稿。

### 3.2 运行草稿

本次勾选与实际顺序（任务、用户或属性单元）、本次轮数、本次是否无人值守，以及
主页面当前配置组 `active_group_id`。

- 顺序与勾选**分开存**（`BatchSelection.order` / `checked`）：合在一起的话，取消
  勾选就会丢掉条目的位置，重新勾上只能落到末尾。
- 草稿按**稳定配置组 ID** 隔离。用名称做 key 的话，重命名要搬迁状态，删掉再建
  同名还会继承上一个组的草稿。
- 存在 session 里是为了"应用重启后恢复上次页面状态"，但它仍然是运行草稿，**不得
  因此反写定义层**。

### 3.3 定义变化与草稿的协调

配置组保存后不能清掉用户刚调好的本次顺序。`BatchSelection.reconcile`：

1. 已不在候选里的条目丢弃（配置组删了，或该属性值不存在了）；
2. 仍在候选里的条目保留草稿中的勾选与顺序；
3. 新出现的候选按定义层顺序追加，勾选状态取定义层默认值；
4. 只有用户点「恢复默认」才完整重建（`from_defaults`）；
5. 切换配置组只换对应草稿，不修改任何定义。

空草稿走同一条路径，所以"配置组第一次使用"不需要第二套代码。属性单元的候选是
从用户资料动态生成的，适用同一套规则。

### 3.4 执行快照

`BatchRunSpec.build(定义, 草稿)` 在点「开始」时合成。调度器只认它：运行期不再读
`batch.json`、不读 session、不看控件。启动之后改配置、改用户资料、在主页面重新
勾选，都不影响正在跑的这一批。

`unattended` 存的是**有效值**：草稿勾了无人值守、且定义层确实配了异常恢复 wf，
才为真。这个与运算只做一次，调度器不必重复判断前提。

## 4. 不兼容切换

`batch.json` 升到 version 2：按稳定 ID 索引配置组，`active_group` 移出，
`selected_*` / `rounds` / `unattended` 不再是定义层字段。

读取 v1 时一次性转换：补一个 ID、`selected_*` 读进 `default_*`（只保留"初始值"
这一半语义）、`rounds` 与 `unattended` 丢弃（它们属于运行草稿）。写出去只有新
格式，所以这是单向读取，不是常驻兼容层。用户感知到的变化是：**本次勾选、执行
顺序、轮数、无人值守不再跨配置保存在 batch.json 里，而是按配置组记在本机会话
状态里；首次打开按配置组的"默认执行"列勾选。**

## 5. 实现位置

| 关注点 | 位置 |
|---|---|
| 定义层模型与持久化 | `core/batch_config.py` |
| 运行草稿、协调规则、session 读写 | `core/batch_run.py` |
| 执行快照 | `ui/batch/batch_runner.py`（`BatchRunSpec`） |
| 定义层唯一入口 | `ui/batch/batch_config_dialog.py` |
| 运行草稿唯一入口 | `ui/batch/batch_tab.py` |

一个可以直接检查的结构性证据：`batch_tab.py` **不再导入** `save_batch_config`，
`batch_config_dialog.py` **不再有**任何读盘反向合并。
