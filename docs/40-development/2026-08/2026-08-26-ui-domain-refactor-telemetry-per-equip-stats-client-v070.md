## 一、ui/ 分层重构（三步，纯移动无行为变更）

### 1.1 按业务域归档平铺模块（`852e74ea`）

`ui/` 顶层从 26 个平铺文件降到 13 个，按业务域收进三个子包（与既有 `batch/`、`scene_editor/` 的分包方式一致）：

- `ui/scripts/` — 录制、编辑、调试工作台、指令面板、清单配置
- `ui/ocr/` — 识别测试对话框与可框选画布（含取点变体 `pick_canvas`）
- `ui/notices/` — 公告 / 更新 / 关于 / 反馈 / 隐私同意，同属启动链与帮助菜单

`ui/macros/recorder.py` → `core/macro_recorder.py`：它不含任何 Qt 依赖，依赖（`win32_keyboard` / `input_trace` / `pynput_patch`）全在 core，属于无头采集引擎，与 `core/screen_recorder.py` 同层。v0.3.1 曾以「仅 UI 层使用」为由把它移入 `ui/`，但 `screen_recorder` 同样只被 `ui/capture_ops` 调用却留在 core——**按依赖方向而非调用方归位**更一致。

`settings_dialog` 与 `user_manager_dialog` 保持独立：应用配置和用户管理各自是独立业务域，不并入通知类子包。

### 1.2 拆分 main_window（`240f2a75`）

`main_window.py` 887 行（原 1587），抽出三块职责独立的混入：

| 模块 | 职责 |
|------|------|
| `startup_ops.py` | 启动检查链：公告 → 更新 → 统计同意 → 上报，四步串行 |
| `menu_ops.py` | 菜单栏、主题按钮与全部对话框入口 |
| `ui_state.py` | `session.json` 的 `ui_state` / `daily` 两节点持久化 |

同时把原本平铺在 `ui/` 顶层的四个 MainWindow 混入（`run_control` 1100 行、`window_ops` 992 行、`capture_ops`、`tray_ops`）与 `main_window` 一起收进 `ui/main/`：这 2500 余行本就是 MainWindow 的实现，不是可独立使用的模块。`ui/` 顶层至此只剩 8 个文件。

**需要注意的测试改动**：`test_plugin_injection` 里 `_setup_menu` 的两个用例改打 `menu_ops` 模块的 `get_registry`——方法搬家后模块全局也跟着换了模块，仍打 `window` 会打空。

### 1.3 `reference_manager` 子包更名为 `reference`（`996372fc`）

包内 6 个文件都没有 `reference_` 前缀，改名不产生 `reference.reference_xxx` 这类重复。以下三类同名文本**保持不变**：

- `session.json` 的 `ui_state` 节点键 `"reference_manager"`（含迁移用的旧扁平键）——那是已落盘的用户数据，改了会让存量 session 里保存的窗口尺寸失联；
- `ReferenceManagerDialog` 类名与 `_open_reference_manager` 方法名——它们描述的是「图库管理器」这个东西本身，不是文件路径。

`scene_editor` 不动：包内 `layout_ops` / `script_ops` / `recognition_ops` 与 `scene_ops` 平级、并非场景的下属概念，`editor` 才是承重词。

## 二、遥测事件粒度改为「一件装备一条」（`6af1e896`，破坏性变更）

原来一条事件 = 一轮调律，且刻意不带装备标识，于是**事件之间没有任何关联字段**。后果是要改进规则真正需要的两类问题永远算不出来：条件概率（已经有会心了，再洗出破防的概率是多少）和规则验证（为什么结束这件装备，判得对不对）。

新粒度是一件装备从进调律页面到离开：

```
initial_affixes[]  进页面时已有的词条，下标即槽位（宫商角徵羽解析序）
rolls[]            逐轮产出，下标即轮次（跨重置连续），各带 slot/food/resets
stop_reason        七个固定值，从循环的实际退出点推导，不是自由文本
final_rating       junk/normal/excellent/top
```

`roll_index` 字段删除——它就是 `rolls` 的下标 +1。

### 2.1 隐私边界的取舍

完整词条组合此前列在 `PRIVACY.md` 的「不收集」里，理由是「对这个问题不提供额外信息」——**那句话对条件概率是错的**。功能尚未发布（master 上没有 telemetry 目录，最新 tag 是 0.6.0），没有任何用户依据旧文案做过选择，所以这是**发布前定稿而非事后扩大范围**。装备名与装备指纹仍然不收。

守住的那条线是词条名白名单：parser 匹配成功时赋的是白名单条目本身而非 OCR 原文。**任何一轮不合法则整条会话作废**，不是只丢那一轮——序列里挖个洞会让下游把第 4 轮误读成紧跟第 2 轮。

### 2.2 同时修掉两个独立缺陷

1. **spool 改为产出即落盘**。原先事件攒在内存、凑够 50 条才写文件，不足一批的尾巴随进程退出一起消失，缺的恰好是每次运行最后那段。现在 append 即写 `pending/`，攒够才封口进 `ready/`；进程被杀时数据仍在 `pending/`，下次启动由 `_adopt_orphans()` 认领。
2. **上报改为按信封体积分多次 POST**，而不是缩小批次。批次大小同时决定 D1 行数（一批 = `roll_batch` 一行），缩批次会让行数成倍上升，正好加重要解决的额度问题。**批次是存储粒度，请求是传输粒度。**

### 2.3 服务端不再逐字段校验调律语义

业务枚举的真源是客户端的 `game_config.yaml`，服务端没有也不该有；抄一份过去意味着每加一个字段都要同步部署、而同步前新字段完全裸奔。改为与字段无关的结构闸门 `sanitizeEvent`（深度 / 键名 / 数组长度 / 数值有限性 / 字符串两种形状），未来字段自动受保护。

`06-telemetry.md` 顺带订正一处错误结论：原文称写入量「可以撑到约 4~5 万 DAU」，实际是每 50 条事件一行、与件数成正比，按代码常量重算约 5,500 DAU（轻度用户约 1.6 万）。选 D1 而非 KV 的结论不受影响。

## 三、按件上报遗留缺陷的逐条修正（`45934f8f`）

上一版改粒度后有几处取值点没跟着改，且服务端与 rollup 仍按旧结构写。

**客户端**

- `mode` 改在 `end_session` 取当前值。`equipment_session.mode` 会在会话中途被判定改写（切进调满后回收 / 强制调律），开场取到的一律是 `NORMAL`，等于把这两类会话全部错记成普通调律。
- `cap_pct` 算不出上限时**省略字段**，不再兜底成 0。0 是合法取值，兜底会把「未知」伪装成「最差」，在数值分布低位堆出一根假柱子，而低位形状正是判断有无下限保护的依据。
- **零轮会话照常记录**。初始判定即跳过 / 回收的装备一轮都没调，早先以「没有统计价值」为由丢弃，结果是 `stop_reason="judged_before_tuning"` 这个枚举值永远不可能出现在数据里。
- 信封每次都带 `app_version`。心跳每 UTC 日只发一次，同一天第 2..N 次上报没有心跳可取。

**服务端**

- 批次内 `install_id` 必须全一致，混合即整批拒收。只取 `events[0]` 会让伪造批次把别人的 `install_id` 顶在行上。
- 非预期内部异常改回 **503**：数据没落库却回 204，等于收下之后悄悄扔掉且客户端以为成功。熔断与单 install 日批次上限维持 204——那两个是有意的静默丢弃。
- 新增事件类型 + schema 版本白名单。这与「服务端不认识调律字段」不冲突：**写死的是事件类型不是字段**。

**rollup.sql**

- 改双层 `json_each`。事件粒度是一件装备，`affix`/`food`/`slot`/`cap_pct` 在 `rolls[]` 数组里，原来的单层展开让这些字段全部取到 NULL。
- 修正 `app_major`：SQLite 的 `instr()` 只有两参数形式，没有 from-index 重载，原写法会让整条语句直接报错。

**分析脚本**

- 条件概率按 `resets` 分段重建「已有词条」集合。重置会把装备清回只剩首词条，跨重置继续累加等于拿早已不存在的词条去算条件。

`dropped_events` 端到端移除：丢弃按文件 mtime 进行、与事件内容无关，对按 roll 估计的概率分布不产生偏倚，只损失精度，而精度已经由样本数 n 表达。理由记在 `spool.py` 的模块 docstring。

## 四、词条分布分析：方法论与工具

### 4.1 分析指引与脚本（`10b00547`）

此前没有任何文档告诉开发者这些调律数据该怎么分析。新增 `docs/10-game/20-affix-analysis/README.md`，核心内容是**已知系统性偏差清单**——这是本文存在的主要理由。

新增 `scripts/analyze_telemetry_rolls.py`（只用标准库）：样本体检、`P(词条|部位,材料)`、`cap_pct` 分布、保底检测、转律对比五节。

分析口径上的几个判断：

- 用 **Wilson 区间**而非正态近似——词条分布是「几十个词条各几个百分点」，n 小 p 小，正态近似会给出负下界；
- **不给 p 值**：格子数以千计且没有预注册假设，逐格检验必然量产假阳性；
- 默认排除 `is_transferred`（机制不同）；`cap_pct` 一节排除 `game_config_customized`；
- **保底检测在「部位 × 材料」层内分桶**——高 `roll_index` 桶只含「前面都没中」的会话，构成与低桶不同。现有 `roll_pity_check.sql` 不分层，文档里已注明它只能当粗筛。

### 4.2 拆分为 `telemetry_analysis` 包（`b6ad96b4`）

分析逻辑平移到 `scripts/telemetry_analysis/`（`loader` / `metrics` / `sections` / `render_md`），CLI 改为薄壳。目的：让 `ops/stats-client` 能直接 import 这份分析引擎，不必 subprocess 调用 CLI，也不用复制一份。已用合成数据跑过拆分前后的 diff，**字节级一致**。

### 4.3 stats-client 本地统计控制台（`0ef7212e`）

仅本机运行的 FastAPI 网页（独立 `pyproject.toml`/uv venv，不影响主项目依赖），替代手工 `wrangler d1 execute` + 导出 JSON 再跑分析脚本的流程：

- **配置向导**：只读（D1:Read）Cloudflare Token，`SELECT 1` 校验连接，Token 走系统密钥环，不支持密钥环的平台退化为本地 0600 文件；
- **总览页**：DAU/WAU/MAU、今日新增、90 天趋势图（本地打包 ECharts，不接 CDN）、版本 / 平台分布、周 cohort 留存；
- **调律分析页**：直接复用 `scripts/telemetry_analysis`，数字与 CLI 逐字一致；
- **本地 SQLite 增量缓存**：三种不同节奏的 keyset 游标；**刻意不长期镜像 `installs` 表**，避免累积可关联的 install 级别本地数据。

MVP 范围，结构化结论卡 / 交互筛选联动 / 报告快照对比留待后续迭代。

## 关键设计决策

1. **模块归位按依赖方向而非调用方**：`macro_recorder` 无 Qt 依赖即回 core。
2. **遥测事件粒度 = 一件装备**：没有关联字段就永远算不出条件概率和规则验证，这是改进规则真正需要的两类问题。
3. **批次是存储粒度，请求是传输粒度**：信封过大分多次 POST，不缩小批次。
4. **服务端只做与字段无关的结构闸门**：业务枚举的真源在客户端，抄一份过去会让新字段在同步部署前裸奔。
5. **词条分布用 Wilson 区间、不给 p 值、保底检测分层**：三条都是为了不产出假结论。
6. **入口可达性测试必须按可见性断言**：`findChildren` 找得到被隐藏的控件，断言恒真。
