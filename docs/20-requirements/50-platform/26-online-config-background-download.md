# 在线配置后台下载与下次启动安装

> 状态：部分实现（2026-11-07，基线 v0.15.11）；下载、暂存、下次启动安装与线程退出已落地，
> 断网启动与中途退出的实机验收未做。

## 目标

把在线配置的联网下载从启动同步段移到后台线程，消除弱网时「窗口出现前多等约 20 秒」。
下载只落暂存区，安装时机不变：仍然只在下次启动、加载插件与场景之前安装。

## 边界

- 启动同步段只保留 `recover_installation()`（回滚未提交事务、撤下失效会员层）。
  它只动本地文件，不得联网。
- 下载与安装分离：后台线程只下载候选并登记暂存；安装点是唯一的
  `prepare_startup_configuration()`，必须在加载插件与场景注册表之前。
- 运行中的进程永不安装、永不替换 `config/system`。安装会让正在跑的任务读到半新半旧的内容。
- 后台下载不参与任何 UI 刷新，不重建场景注册表，不刷新 OCR、模板或插件缓存。
- 后台下载失败只记日志，不弹窗、不阻断启动，也不改变「保留当前磁盘配置」的语义。

## 线程生命周期

- 单线程，`daemon=True`，配模块级 `stop_event`；**必须在拿到单实例锁、确认自己是主实例之后启动**，
  否则第二个实例也在下载。
- 退出路径挂在 `QApplication.aboutToQuit`：`stop_event.set()` 后 `join` 至多约 2 秒，
  超时直接放弃等待。用户「启动后立刻关掉」不得让进程卡在退出上。
- 下载必须可中断：分块读、每块约 2 秒超时，并在每块之间检查 `stop_event`。
  只靠「整包 10 秒超时」不算可中断。
- 写入一律「临时文件 + `os.replace`」：线程被强杀最多留下 `.tmp`，下次启动清理。
  这里不做事务性安装，只保证不产生半成品。

## 暂存与安装的衔接

- 暂存候选必须登记到 `UpdateStore` 的 state（例如 `pending_selection`）。
  `prune_archives()` 目前只保留 `state` 与 `previous_selection` 引用的归档，
  未登记的候选会在下次启动被当成垃圾删掉，等于白下载。
- 需要补公开包的归档写入口：现有能力只有 `cache_member()`，会员包有暂存、公开包没有。
  归档按 `r{revision}/{manifest_sha256}` 寻址，同修订重发不同内容不互相覆盖。
- 下次启动的安装段读暂存内容直接安装，不联网；暂存缺失、损坏或版本不匹配时才回落到联网判断。

## 可见性

- 设置页的在线配置一栏显示两种状态之一：已下载待安装的修订号（「下次启动生效」），
  或本次未获取到更新。否则用户会以为开关没生效。
- 日志给出可行动的结论：下载了什么修订、是否命中本地已有修订、失败原因（不打印整包 JSON）。

## 验收

1. 断网或慢网启动时，窗口出现时间与联网无关（此前最多多等约 20 秒）。
2. 后台下载完成后本次不安装；下次启动读取配置前安装完成。
3. 下载中途关闭应用，进程正常退出且不留下半成品配置。
4. 连续启动两次，第二次的 `prune_archives()` 不会清掉第一次下载的暂存。
5. 运行中的任务不会因为后台下载或安装读到混合配置。
6. 暂存缺失或损坏时回落为联网判断，不报错、不影响启动。

## 不做什么

- 不做运行中安装，也不提供「立即安装」按钮。
- 不为下载失败引入重试队列或后台服务；下一次启动自然会再试。
- 不改变修订号仲裁与 `config/local` 优先级。

## 实现现状

- 落点：`core/config/remote.py`（后台线程、暂存、离线安装）、`core/config/update_store.py`
  （`pending` 登记、公开包暂存、prune 保活）、`core/config/member_download.py`
  （暂存密文的授权解密）、`app.py`（窗口出现后启动、`aboutToQuit` 先停线程）。
- 已用单元测试钉住：下载不安装、启动不联网、候选缺失保留原配置、prune 不回收候选、
  关闭开关下次启动恢复预置。
- 会员链路用桩环境跑通了整条路径（`tests/core/test_member_staged_install.py`：HTTP 与授权
  接口打桩在模块边界，其余走真实实现）——密文暂存不含明文、下次启动只取一次授权且不重下
  整包、授权请求失败保留候选并可在下次装上、授权被拒清候选不装、暂存清单被改坏时拒绝安装、
  本地授权过期不装。
- 真实服务器核对（2026-11-07，`scripts/one_off/check_member_key_reuse.py` 与
  `check_member_staged_flow.py`）：同一激活码连续 3 次 `/v1/key` 全部通过（约 0.9 s/次），
  服务端没有重复授权限制；完整链路在临时客户端根目录实跑一遍为「下载 2.6 s、1 次授权 →
  下次启动安装 0.9 s、0 次下载、1 次授权」，安装 28 个文件、暂存清空、暂存区无明文。
  带序列号的 `bind=claim` 码（本机已认领）走了完整分支：3/3 次授权通过且服务端签名回执
  校验为 `active`；同一条码的完整链路为「下载 3.0 s → 安装 1.1 s、0 次下载」。
- 尚未验证：真实包在两次请求之间被轮换后的表现、断网/慢网下的启动耗时、
  下载中途退出的进程行为（这几项需要人工制造环境，脚本模拟不了）。
