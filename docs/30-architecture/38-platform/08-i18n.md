# 国际化模块与翻译查找契约

> 最后更新：2026-11-09（补 `tr_in()` 与「配置显示名写在配置里」一节）。

## 2. 技术方案

### 2.1 总体架构

采用 **YAML 翻译文件 + Python tr() 包装函数** 方案，不依赖 Qt 的 .ts/.qm 工具链。

```
┌─────────────────────────────────────────────┐
│              lvjiang.i18n 模块               │
│                                             │
│  init_i18n(language)  ← 启动时调用，加载核心层│
│  load_app_i18n(app_id) ← 插件加载时调用      │
│  tr(text)             ← 统一入口，不分 QObject│
│  tr_in(text, language) ← 按指定语言查，不改语言│
│  set_language(code)   ← 保存语言偏好（重启生效）│
│  available_languages() ← 扫描核心层翻译文件  │
│                                             │
│  内部：核心层 + 已加载插件层合并成一张扁平表  │
│  查找以中文原文为 key；找不到 → 返回中文原文  │
└─────────────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────────┐
│         config/i18n/ 翻译文件目录             │
│                                             │
│  zh_CN.yaml            ← 核心层中文基准      │
│  en_US.yaml            ← 核心层英文翻译      │
│  apps/{app_id}/zh_CN.yaml ← 插件层中文基准   │
│  apps/{app_id}/en_US.yaml ← 插件层英文翻译   │
└─────────────────────────────────────────────┘
```

**核心层 / 插件层是两份独立文件，合并到同一张查找表**：`init_i18n()` 启动时
只加载核心层 `config/i18n/{lang}.yaml`；`load_app_i18n(app_id)` 在插件加载
时按需加载 `config/i18n/apps/{app_id}/{lang}.yaml` 并**合并**进同一张
`_translations` 表——查表以中文原文为 key，同一句中文若在核心层和插件层
都出现（或插件层内部自己重复），后加载的会覆盖先加载的，核心层总是先于
插件层加载，所以插件层能覆盖核心层的同名条目。这不是设计上鼓励的行为
（见 `tests/core/test_i18n_consistency.py` 的重复源文冲突检查），只是
实现上如实允许，写文案时应避免让同一句中文在两处出现不同译法。
`tr()` 本身是单一入口，调用方不需要关心某个字符串来自哪一层。

### 2.2 翻译文件格式

翻译文件顶层 key 按"模块/文件"分层，各模块自己是一个平级 dict，
**不套一层 `ui:`/`messages:` 之类的大类包装**：

```yaml
# config/i18n/zh_CN.yaml
meta:
  language: zh_CN
  display_name: 简体中文
  version: 0.2.5          # 未接自动化流程，长期停留在这个值，不代表文件没更新

main_window:
  title: 律匠 - 通用视觉 RPA 引擎
  menu_general: 通用
  # ... 每个模块一个顶层 key，按需再往下分层

settings_dialog:
  title: 配置管理
  language_label: 界面语言

messages:
  err_layout_not_found: '无法加载布局: {name}'
  err_panel_not_defined: 布局中未定义 panel {scene}.{panel}

config:
  layout_default: Default Layout
  delay_step_wait: Step Interval

# 机器抽取的占位段：手工整理进具体模块之前的字符串先落在这里，
# key 直接就是中文原文本身。见 §3.3。
auto_strings:
  '未选择窗口': '未选择窗口'
```

`en_US.yaml` 结构完全一致，值替换为英文。

### 2.3 tr() API

**统一使用 `tr()` 函数**，不区分 QObject 内外。`tr()` 以中文原文为 key，在翻译文件中查找对应值；找不到则返回原文（中文 fallback）。

```python
from lvjiang.i18n import tr

# UI 字符串
settings_menu = menubar.addMenu(tr("通用"))

# 含变量的字符串
QMessageBox.information(self, tr("发现新版本"),
    tr("发现新版本 v{latest}\n当前版本: v{current}\n\n是否前往下载？")
    .format(latest=latest, current=current))

# 错误消息
raise WorkflowUserError(tr("布局中未定义 panel ..."))
```

### 2.3.1 tr_in()：按指定语言查表，不切进程语言

```python
from lvjiang.i18n import tr_in

# 用户刚把界面切成英文、还没重启：用英文告诉他重启才生效
hint.setText(tr_in("重启应用后生效", "en_US"))
```

`tr()` 查的是**当前进程**的表，保存语言偏好后进程仍跑在旧语言下。凡是「即将生效
但尚未生效」的提示都必须走 `tr_in()`，否则用户看到的是自己正要离开的那种语言。

只加载核心层词表（`config/i18n/{language}.yaml` 与 `{language}/` 目录），插件层
不参与——这类提示属于软件自身文案，不属于任何插件。词表按语言缓存，与
`init_i18n()` 一样，配置内容变更仍需重启。门禁
`tests/core/test_i18n_literal_coverage.py` 把 `tr_in("字面量", …)` 与 `tr()` 同等
对待：缺条目同样静默回退中文。

### 2.4 语言配置

在 `session.json` 的 `settings` 节点存储 `language` 字段：

- `"zh_CN"` — 中文（默认）
- `"en_US"` — 英文
- `"auto"` — 跟随系统 locale

启动时读取该配置，加载对应翻译文件。语言切换后需重启应用生效：词表在启动时一次性
加载，进程内切换不会重建已构造的界面。

设置页保存时会比对「刚保存的语言」与「进程实际加载的语言」，不一致就在保存按钮右侧
用**目标语言**提示「重启应用后生效」（走 `tr_in()`，见 §2.3.1）。没改语言时不显示；
改回当前语言后收起。语言下拉框按**已保存**的 `language` 回填而不是进程语言，否则
改过语言但没重启时再次打开设置会把待生效的选择改回旧值。

### 2.5 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 翻译文件格式 | YAML | 项目已重度使用 YAML，团队熟悉 |
| 翻译 key 策略 | 中文原文作 key，找不到时返回原文 | 未翻译的条目不会空白，直接显示中文 |
| 日志消息 | 引擎日志保持中文，UI 面板日志走翻译 | 开发者调试不受影响 |
| 运行时切换 | 重启生效 | 避免热切换的 UI 重建复杂度 |
| 默认语言 | zh_CN | 当前用户群以中文为主 |
| 文档字符串 | 不翻译 | 面向开发者，保持中文 |
| 配置显示名载体 | 写在配置自己身上，不进词表 | 软件文案属于代码、配置显示名属于配置数据，两者所有者与生命周期不同（见 §2.6） |

### 2.6 配置显示名：写在配置里，不进词表

软件自身的文案属于代码，配置项的显示名属于配置数据——两者的所有者、生命周期和
维护工具不同。让一个配置字段的措辞去改翻译表、12 种语言和覆盖率校验，等于把两份
互不相干的内容绑在一起。因此随包配置的**纯展示**字段直接把多语言写在配置自己身上：

```yaml
# config/system/app.yaml
envs:
- key: android
  name:
    zh_CN: 安卓
    en_US: Android
```

读写约定实现在 `src/lvjiang/core/config/localized.py`：

- **读** `resolve_localized(value, language)` 归一成当前界面语言的一个字符串。
  回退链：精确语言 → 同语种其他区域（`en_GB` → `en_US`）→ `en_US`（**仅非中文
  界面**）→ `zh_CN` → 映射里第一个非空值。中文界面不插英文兜底，`zh_TW` 经同语种
  匹配拿到简体原文；非中文界面优先英文，避免同一界面一半英文按钮、一半中文名字。
- **写** `preserve_edited` / `preserve_sequence` / `preserve_mapping_field`：
  内容没变就原值原样写回（多语言键一个不丢），变了且原值是映射则只覆盖当前语言
  那一项，原值是纯字符串（用户自建）则写回纯字符串，不会被升级成映射。
- 归一化只发生在**消费点**（`load_available_envs`、`parse_delay_params`、
  `Plan.from_dict`、`save_app_config`），不放在读-改-写全量的合并视图上——否则
  保存一次设置就会把随包的中英双语抹成单语言。

**只有纯展示字段允许这种形态。** 承担计算、OCR 匹配或作为稳定 id 的字段
（`plan.id`、`schools` 的键、词条名、属性名、`affix_caps` 的键）永远是单个
字符串——把计算键换成随语言变化的实体，识别和判定会直接失效。插件层的游戏术语
仍留在 `apps/{app_id}/{lang}.yaml` 词表里按中文原文查表（见下文「翻译内容一致性」）。

当前落点只有 `config/system/app.yaml`：`envs[].name`、`plans[].name`、
`delay_params.*.label`。其余配置（`scenes.yaml`、`layouts.yaml`、`scenes/*.yaml`
的区域名、`yysls/**`）仍是中文单字符串，逐文件切换即可逐文件生效，不需要迁移
脚本。录入通路是手工编辑 YAML，没有多语言编辑入口；随包配置缺 `en_US` 时由
`tests/core/test_config_localized.py::TestShippedAppYaml` 拦下。

需求与验收见
[01-i18n.md §配置显示名的载体](../../20-requirements/50-platform/01-i18n.md#配置显示名的载体)；
合并与覆盖语义见
[04-config-layering.md](../../30-architecture/30-overview/04-config-layering.md)。

## 语言清单与回退策略

`available_languages()` 扫描 `config/i18n/*.yaml`，当前随包 12 种语言：
`zh_CN`、`en_US`、`zh_TW`、`ja_JP`、`ko_KR`、`de_DE`、`fr_FR`、`es_ES`、
`pt_BR`、`ru_RU`、`th_TH`、`vi_VN`。

其中只有 `zh_CN`（原文）和 `en_US`（人工译文）是完整翻译；另外 10 种由
`a3256c76` 按 en_US 骨架生成，**非游戏内容一律以英文回退**（宁可显示英文也不
给非中文用户显示中文），游戏术语由插件层 en 批次覆盖。因此对这 10 种语言，
"完成度"指的是英文回退覆盖率，不是本地化程度——它们的词表值 99% 与 en_US
逐字相同，只有零星几条被单独本地化。

## 翻译内容一致性

`tr()` 调用不会自动进翻译表——新增一句 `tr("新文案")` 后，如果没人往
`zh_CN`/`en_US` 两侧补条目，运行时不报错也不写日志，界面直接静默回退中文。
词表按模块拆分到 `{lang}/*.yaml`（19 个模块文件 + 主文件只留 `meta`），每个
模块文件内按源文件命名段落（`settings_dialog:`、`scene_editor:` 等），`zh_CN`
侧必须是 `en_US` 每个键的同名自映射，否则路径配对取不到原文、翻译静默失效。

守门测试分两组：

`tests/core/test_i18n_literal_coverage.py` —— 用 AST 扫描源码里全部
`tr("字面量")`，走运行时入口（`init_i18n` + `load_app_i18n`）装载每个随包
语言，逐语言断言：

- **查不到的文案数必须为 0**（硬门槛，不是棘轮）：查不到就是非中文界面出现
  中文，用户能直接看到；
- **en_US 的每个键路径都要以同一段落出现在该语言里**：配对是纯路径配对，段落
  名或键路径错位就整条跳过、静默回退中文。10 个新语言曾把 zh/en 的 `yysls`
  段（709 条游戏术语）整段生成进 `auto_strings` 段，235 条因此在 10 个语言里
  显示中文，而两边的条目总数看起来还都对得上；
- **词表叶子必须是字符串**：`是: Yes` 这类裸写在 YAML 1.1 里是布尔 `True`，
  配对器只认 `isinstance(str)`，条目会静默失效；
- **会被 `tr()` 命中的译文不得自带冒号**：冒号由 `tr_label()` 追加，自带会让
  界面显示成 `Materials:: `。
- **英文回退语言的插件层必须与 en_US 逐条相同**（非 ASCII 值视为本地化，放行）：
  10 份词表本质是 en 的副本，副本会腐烂——曾停在 `dd4ca53f` 之前的快照上，
  336 条术语与 en 分叉（`Dingyin`/`Attunement`、`Cap Value`/`Maximum`、
  `Loadout`/`Equipment Builds`），同一个游戏概念在不同界面语言下叫法不同。
- 新增语言文件后自动纳入检查，不需要改测试。

`tests/core/test_i18n_stale_keys.py` —— 词表卫生：含 CJK 的死键（核心层按
**全段落**硬性归零；插件层还有 252/231 条存量，用棘轮锁住只许下降）、
zh/en 键集按文件全段落对齐，以及**同源两译棘轮**（同一句中文在不同段落配不同
译法时，扁平查表由后加载者静默取胜，数量只许下降）。

插件层那 252/231 条不能照着"源码里没有就删"处理：插件词表里有相当一部分是
**插件层的游戏领域值**（流派、词条、武学名等），由 `tr(变量)` /
`apps/{app_id}/ui/domain_labels.py` 在渲染时查表消费，而配置可以来自在线下发层（见
[远端配置与 i18n 闸门](../../40-development/2026-08/2026-08-27-remote-config-core-decoupling-i18n-gate.md)），
本地仓库里查不到不等于运行期用不到。要清理得先确认条目来源，或让下发内容自带
译文。

注意这里指的是**插件层**的游戏领域值。核心层随包配置的纯展示名（`app.yaml` 的
环境名、方案名、等待参数标签）不走词表，而是写在配置自身的多语言映射里，见 §2.6；
那类字段缺译文由 `TestShippedAppYaml` 拦下，不表现为词表死键。

模块位置为 src/lvjiang/i18n，核心和插件翻译由同一入口合并；用户语言选择属于设置，
切换后重启生效，设置页会按目标语言提示这一点。
