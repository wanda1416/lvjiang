# 识别帧历史调试与异常诊断包方案

> 状态：规划（2026-11-23，基线 v0.15.19）。详细实施提案，尚未实现；本次仅编写文档。
> 代码核对基线：主仓 `3beec58a`、独立server `5fad0fb6`。拟议类型、接口、配置与目录均非现有API；实施前复核。
> 合并依据：吸收外部《工作流帧调试记录（黑匣子 / Flight Recorder）详细执行方案》v1.1的动作时间线、离线查看和校准方法；未实施。

## 1. 背景、目标与交付范围

现有脚本可在失败处保存最近识别帧，但单帧无法解释此前从哪个页面返回、操作前后发生了什么。
本方案增加可选 debug 模式：平时在内存保留最近识别图及有界输入动作时间线，人工介入或任务失败时冻结现场，后台导出本地诊断包。
“回放”仅指离线查看画面、识别与动作记录，不重放设备输入。

产品承诺应是：**保存最近最多 100 张成功留存的识别帧，并受总字节限额约束；立即确定异常现场的截止边界，异步完成诊断包。**
不承诺每张恰好 100KB、任意小字都清晰、完全无丢帧、固定覆盖时长、总额外 RSS 只有 10MB，或 ZIP 瞬时写完。
100KB 是待真实画面验证的压缩软目标，不是图像格式保证。

首版建议范围：

- 桌面宿主运行中的一个显式执行目标：Windows 窗口或 ADB/scrcpy Android 目标；不因平台不同另造采集链。
- 组件可随程序存在，轻量任务元数据照常维护；重截图/编码不默认常驻，必须主动开启本次任务或本次批量的调试记录。
- 支持中途开启但不能追溯过去画面；支持手动导出、失败/人工介入前留证，以及用户主动反馈时自动准备对应证据。
- 一个进程同时只记录一个选定执行目标的一次任务；后续任务重新建作用域，不自动混入其他角色。
- Android App 端侧常驻历史、并行多目标同时记录不在首版交付；核心保持无 Qt 依赖，后续须另测内存再接入口。
- 与 [AI 异常恢复方案](29-ai-exception-recovery.md) 独立，无模型调用、无自动上传；未来 AI 按用户授权选取少量帧消费，不默认发送整个包。

非目标：连续录像、复刻录屏器、云端图库、数据库索引平台、自动修游戏状态、改变无人值守策略、重写任务结果/账本。
诊断不能代替确定性 bug 修复，也不自动点击确认、重试购买或领奖。

运行上下文依据（仅源码检出）：[execution_runs.py](../../../src/lvjiang/ui/main/execution_runs.py)：`ExecutionRunContext`；
[batch/models.py](../../../src/lvjiang/core/batch/models.py)：`BatchContext`。
这些现有类型当前没有本文 recorder 字段；实施时只加可选依赖，不把 UI 类型引入 core。

公共层只接收通用帧、操作信息和事件。插件若要补诊断原因、声明敏感阶段或将既有领域识别标为消费帧，
只能声明通用 hook，由宿主装配；core/UI/workflow 不知道插件名、业务资源路径或“货运”常量。

任务可中途主动开启，使用新的capture_scope，不能追溯此前帧；完整规则与身份复用见第15节。

## 4. 配置入口与候选预算

### 4.1 用户入口：主动开启，不记住“永远开启”

在任务运行区提供“调试记录”，启动前或运行中都能明确开启；在批量启动区提供“本次批量调试记录”。
设置页只放画质、容量与保留策略等偏好，不把持久化`enabled=true`带到下次启动。

- 默认不记录；进程重启、单任务结束或本批量结束后均解除开启状态。不因曾经打开设置页/提交反馈而自动开启。
- 单任务开关只影响指定task_run_id；批量开关只影响指定batch_run_id后续实际执行的子任务，子任务各自隔离。
- 运行中开启从下一次识别消费开始，不额外capture，显示“从此刻开始，无此前画面”；停止/重开生成新capture_scope。
- 运行态落盘策略统一为`always`或`on_issue`：主动调试默认always，便于排查“返回成功但实际漏做”；
  可明确选“仅异常/人工介入留包”降低磁盘输出，正常结束后将无历史图可补报。策略随本次任务/批次复位，详见第15节。
- 任务区显示“未开启 / 记录中 / 部分记录 / 已停止 / 不可用”，与任务执行成功失败分开展示；详见第16节。
- “导出当前历史”与“停止本次记录”是运行态动作，不改批量长期配置、角色配置或任务排序。
- 停止记录先拒绝新准入，对已收集历史请求一次非阻塞封口再释放图环，保留包与覆盖摘要；不能一按停止就丢掉此前记录。
  若用户明确选“停止并丢弃未封口记录”才直接清空。已排定本地导出不等于自动撤销，取消导出另有明确动作。
- 告知文字：`调试记录仅保存在本机，不自动上报；中途开启无法补回之前的画面。`
- 反馈页提醒：**请自行检查截图是否包含敏感信息。** 提供查看/移除；点击“提交反馈”一次性授权发送清单内附件，
  不再要求单独安全审批、强制打码或额外风险勾选。记录/构包本身不授权后台上报。
- 不能记录时给非阻塞原因；没有WebP时可用经过一次能力探测的JPEG降级，两种都不可用/目标占用也不阻止任务。
  没有图仍可提供该任务日志，不拿其他任务图补齐。

拟议 `settings.debug_frame_history` 仅保存本机容量/画质等偏好，缺省安全值；**开启状态只在当前运行上下文**。
如实现时复用enabled字段，它也只能是本次运行字段，不能保存为跨重启自动采集开关。
复用UserConfig/load_user_config/save_settings作偏好装配、字段级更新，明确排除云端同步；不读写游戏业务参数。

现有入口（仅源码检出）：[models.py](../../../src/lvjiang/core/config/models.py)：`UserConfig`；
[config/__init__.py](../../../src/lvjiang/core/config/__init__.py)：`load_user_config`；
[session.py](../../../src/lvjiang/core/config/session.py)：`save_settings`；
[settings/dialog.py](../../../src/lvjiang/ui/settings/dialog.py)：`SettingsDialog`。
这些入口尚无本文调试选项；运行区动作也须新增，不能把现有“反馈与建议”误认为已有任务证据入口。

### 4.2 工程候选值，不是性能承诺

下表是可开始实现和写边界测试的**候选起点**，除用户提出的 100 帧/约 10MB 方向外，其余数值均为待实测工程建议。
先作为单一配置模型/常量维护，不把全部参数暴露成普通用户设置；真实样本验收后冻结默认值。

| 参数（拟议） | 候选值/策略 | 意义 |
|---|---|---|
| 本次运行 `enabled` | `false`，不跨重启持久化 | 主动开启后才采集；组件存在不等于后台记录 |
| `max_frames` | `100` | 编码帧数量上限，不保证填满 |
| `max_encoded_bytes` | `10_000_000 B` | 压缩载荷硬上限；十进制10MB，约9.54MiB |
| `target_frame_bytes` | `100_000 B` | 单帧软目标；不以破坏小字强达标 |
| 编码并发/待处理 | 1 worker、最多1 pending | in-flight 单独计入原图所有权 |
| `max_owned_raw_bytes` | `32_000_000 B` | 包含pending、in-flight、复制预留、worker缩小副本、冻结关键帧持有；不是RSS上限 |
| 元数据 | 总量 `1_000_000 B`；单帧最多32条观察/动作关联明细（合计）；单文本最多1024 UTF-8字节 | 越界截断/聚合并明示，不保留无界OCR和事件列表 |
| 编码策略 | 开启时一次WebP实编码探测；不支持则JPEG；两者候选q75，单图固定一次 | 实际格式写manifest与扩展名；JPEG也是有损，需独立验收 |
| `max_edge` | 首版基线不缩放；候选1280/1080/960px由第14.3节校准后选择 | 只缩诊断副本、保留原尺寸与变换；不承诺1280一定清楚或低于100KB |
| `finalize_timeout_ms` | `1000`，候选待测 | 截止帧收尾等待上限；不含强制中断原生codec，不承诺文件1秒内写完 |
| 日志/包大小 | 摘录最多 `256_000 B`；ZIP最多 `12_000_000 B` | 输出也有硬限；优先省略可选日志/缩短索引，不破坏manifest闭合 |
| 磁盘保留 | 最多10个完成包且合计不超 `100_000_000 B` | 按更早到达的上限淘汰本功能旧包；值待使用场景确认 |

每条元数据中的 ROI 数组、嵌套值、事件理由列表也必须有限，不能只限字符串和图像。
原始像素与 `nbytes` 在复制前检查；超过 raw 限额不做昂贵的同步缩放，标 `raw_budget_exceeded`。
若单图即超过全部编码预算，不能先清空全环再发现仍放不下：首版直接舍弃并标原因。
固定q75结果只超过100KB软目标、但能容纳于总预算时可正常入环；不为了追软目标再编码。
待真实样本确定最低可读质量后，才固定一套max_edge/quality档位；若再提供指定第二次降级，也须单独验收和有界，
不根据文件大小无限搜索质量。所有重采样在编码worker的独立诊断副本上做，不把resize挪到识别主路径来“省原图内存”。

质量优先：单图大于100KB但未超总预算可入环，淘汰老帧，因此保留量可能少于100。
需严格100KB时只能选择缩小、降质或舍弃；应作为另一次明确取舍，不暗中把关键小字压到不可读。
异常帧优先保留并不允许突破硬限；超预算仍必须 missing/降级，不能“特批无限大”。

### 4.3 内存账必须分项

1080p BGR单图是 `1920 × 1080 × 3 = 6_220_800 B`，约5.93MiB。
一份 pending 加一份 in-flight 原图已约11.87MiB，另有最多约9.54MiB编码载荷，尚未计入下列项：

- 入队复制时的预留/暂存，源捕获缓存与后端自身buffer；不同尺寸不得只按张数估算。
- WebP原生编码临时空间、输出numpy buffer转bytes时的短暂双份、Python对象/锁/队列开销。
- 有界OCR/事件元数据、日志摘录、ZIP输出缓冲、索引生成与冻结引用。

raw 预算按对象所有权记账，引用共享不重复计，但旧job尚被线程持有时不能提前退还额度。
压缩环按不可变bytes实际长度记账，元数据序列化/生成索引也不能先构造无限对象再截断。
这些限制约束可控缓存，不等于可以强制保证整个进程RSS；codec临时内存与真实峰值要测。

## 5. 拟议类型与接口

以下是命名示例，实施可合并成更小的内部类型；不是新增 DSL 指令或已开放 API。

| 类型 | 必要字段与约束 |
|---|---|
| `RunScope` | `run_id`复用现有单次`task_run_id`；附已有`batch_run_id`（若有）、target_alias、任务稳定ID/阶段；`capture_scope`复用recorder_generation，不再造一套任务ID |
| `FrameKey` | `run_id`、`target_alias`、`engine_epoch`、`frame_seq`；engine_epoch由宿主显式分配，不能用跨运行不稳定的对象地址作公开ID |
| `FrameStamp` | 新capture时采样的墙钟/单调钟、原尺寸/字节、source、fallback；元数据新增不改变已有缓存语义 |
| `ActionEvent` | action_id/event_seq、scope/engine、前一消费帧key及帧龄、动作/按键模式、请求坐标空间与几何快照、派发状态；不含输入文本 |
| `Observation` | 递增event_seq、op_id、frame_key或null、消费时间、识别类型、场景/ROI、预期/实际值、命中/失败、仅真实存在的置信度 |
| `EncodedFrame` | key、不可变bytes、codec/扩展名、编码尺寸/比例/质量、字节数、编码耗时、受限observations/actions引用；不携带原图 |
| `Trigger` | incident_id、分类/原因、时间/最后消费key、步骤/阶段、是否业务失败；人工确认不能伪装成failed |
| `FrozenBundle` | 截止event_seq/帧范围、不可变编码引用、有限待收尾key、缺失统计与reason；不读取后续活环 |

建议最小内部接口：

```python
# 拟议接口：仅展示已开启分支；显式上下文，不寻找active user/device。
token = recorder.begin_observation(frame_key, frame_stamp, frame, operation_meta)
try:
    result = existing_recognition()  # 原始图、识别流程与返回值不变
except Exception as exc:
    recorder.end_observation(token, sanitized_failure_meta(exc))
    raise
else:
    recorder.end_observation(token, bounded_result_meta(result))

# 只快速确定边界、排定后台工作，不在控制线程写ZIP。
ticket = recorder.request_bundle(trigger, last_consumed_key)
recorder.stop_recording()  # 运行态停止，不改持久化偏好
```

上述 `sanitized_failure_meta` / `bounded_result_meta` 也是提议适配，不允许直接 repr 任意异常对象、变量表或返回对象。
诊断回调自身所有失败在诊断边界内隔离；它抛错不能替换原识别结果、业务异常或 return。
token只含关联信息，不长期持有borrowed图像；准入成功后原图由受限job所有，完成即释放。

### 5.1 帧与观察的关系

- 记录“识别尝试所用图”，包括正常未命中、预处理后执行失败；不是仅记录成功命中。
- 同一 seq 的多次 from-last / 多 ROI 消费只编码一张，追加受限观察；capture-only、UI预览不自动入环。
- seq不连续未必是背压丢帧：未被识别消费的新截图也会增seq。记录资格过滤、编码丢弃与engine边界分别统计，不靠编号差估算dropped。
- 新 capture 即使像素相同也代表新的观察时间，不做逐像素/全图hash去重；编码后可按需算内容校验和。
- 彩色判定、模板匹配、面板图像校准与领域识别直接使用 last 的入口也需显式通知消费；不依赖source字符串猜测。
- `wait stable`内部取样不接入首版历史，不为记录改变其缓存/seq语义；纯截图/校准预览不自动当识别消费。
- 原图保存一次；ROI、清洗前后必要值和坐标空间放sidecar，不为每块ROI另存图片或在OCR原图上涂字。
- 捕获层现仅有获取后的单调计时；拟增墙钟字段必须在capture处成对采样，不冒充设备原始采集时间。
- 多次复用分别记录消费时间与帧龄，不能用最后一次识别时间重写原capture时间。
- 抓图返回空/抛错时保留无图事件，旧帧即使仍在历史中也不得冒充当前失败帧。

### 5.2 输入动作时间线：看清“识别后做了什么”

吸收附件的画面—动作—日志三线关联，但不把输入记录塞进任意“当前队尾帧”。
每个动作有独立event_seq，action_id可直接复用开始event_seq而非再建UUID；与识别观察共用时钟/作用域；关联最近实际消费的`pre_frame_key`、帧龄和之后第一次消费的`post_frame_key`。
若前后图未保留则标missing/null，动作不能挪到另一个旧帧上。动作不主动capture，坐标计算完成不等于已经派发成功。
冻结只取截止时已知的动作及状态；派发结果/后继图晚到也不能回写封口元数据，pending要如实显示。

最小记录：click、drag、控制按键press/down/up/hold，带受限控件label、开始/结束相对时间、requested/dispatched/failed或cancelled。
`dispatched`只说明调用已交给后端/后端返回，不证明游戏收到或页面已改变；异常或停止要保留真实结果。
拖拽先记录端点/模式/时长，不录每个插值点；首版不收集逐像素鼠标轨迹、全局用户按键或剪贴板/粘贴/输入文本。

- DSL `_send_click` / `_send_drag`与BaseWorkflow `click_region` / `click_at` / `drag_between`不能各报一遍同一输入；
  在公共派发边界装配一次通用观察，或在高层分配action_id并由下层补派发结果，避免双计。
- 当前InputBackend.click_screen允许后端random_offset；首版高层记录应标`requested`及offset标志，不能叫“真实落点”。
  后端若已有或新增实际派发回报，再以明确capability补actual；不能为debug重算随机数、关闭偏移或改变点击。
- 坐标明确标capture_px/window_client/screen/device等空间；保存当时目标几何/缩放映射，能可靠转换才在图上画点。
  几何缺失、目标移动或旧帧不匹配时显示unmapped/帧龄，不能画一个貌似准确却错误的红点。
- 所有动作也计入原1MB元数据总预算/有界事件明细，重复丢弃用聚合计数；不因无新帧而无限追加动作数组。
- 动作后的下一次**本来就要进行的识别消费**标after_action并优先准入；不过预算时仍可missing，不额外抓图或等待。
  若以后启用相似分组，动作边界、预期/结果变化必须强制分组，不能把“点了没反应”抹掉。

首版仍仅做同key去重，不采纳MAD阈值丢图：32×18缩略图可能忽略标题/数字/浮层小变化；
无输入动作也会发生动画、网络回包或业务刷新。若后续实验相似帧分组，必须保留每次frame key、时刻和观察，
不得把seq区间假装成连续完整记录，不得突破现有元数据上限；先作为查看器辅助，不作为采集丢图依据。

## 6. 稳定副本、编码与背压流程

1. 关闭时直接跳过诊断分支，不启动worker、不抓新图、不读取用户日志，不改变PNG路径。
2. 开启时构造受限操作摘要；用短锁检查scope/generation、seq是否已准入及预算，预留raw容量。
3. 已有该frame job或编码结果则只关联观察，不再copy；没有则获得独立连续BGR副本。
   backend没有统一不可变所有权保证，单设numpy只读标志不足以阻止其他alias修改。
4. copy在读取当前帧有效期间完成；不持全局数据锁进行大图copy。失败或代次改变要撤销预留并丢弃该job。
5. 单pending已满时优先替换较旧pending，保留越近越有用的图；动作后首次消费可提高准入优先级但不得等编码，记录原因/seq缺口；
   in-flight不能被原地改写。没有可用raw额度就舍弃，不等待worker。
6. 仅在明确开启时做一次8×8合成图编码能力探测并检查结果；WebP失败才探测JPEG，记录所选codec，不能每帧反复探测。
   worker在锁外对稳定副本编码；若启用已验收max_edge，先预留缩小副本空间再resize，原图与缩小图短暂共存也计raw预算。
   码流/扩展名/manifest一致，不能把JPEG字节命名为webp；不循环搜索质量或极限缩小。
7. 完成时以短锁检查generation/冻结状态，按捕获顺序入环，更新count/bytes，FIFO淘汰至双限满足。
   后续观察可能晚于编码完成，按key关联且仍受元数据预算约束。
8. 被丢图/淘汰图释放图像和所属明细；仅保留有界缺失事件与按原因聚合计数，不能每丢一帧再永久加一个对象。
9. 编码失败、超大图或无可用WebP/JPEG告警/累计一次状态并降级，不反复刷屏；JPEG能力降级可info提示，不当业务失败。
   两者均不可用时保留现有同帧PNG退路，不悄悄改存100张大PNG。

“不等待编码”不等于“没有成本”：准入copy、元数据和CPU竞争仍可能影响自动化。
不能通过修改全局OpenCV线程数、降低识别质量、改变脚本等待时间来掩盖debug成本。
验收达不到性能门槛时先减少记录/丢帧、关闭功能或调整待测参数，而不是让自动化线程等编码。
因此文案必须允许丢帧，并显示 admitted/encoded/dropped/pending 与实际覆盖起止时间。

## 7. 生命周期、锁边界与冻结导出

### 7.1 生命周期

`OFF → RECORDING → FROZEN/EXPORTING → RECORDING 或 CLOSED` 为拟议诊断状态，绝不是业务任务状态。

- 新任务：仅在用户开启本次任务/本次批量时冻结诊断偏好、绑定显式target/task_run_id，建立新scope与空环；否则只记轻量“未开启”状态。独立engine有独立epoch。
- 中途启用同样是显式运行命令；新capture_scope从当刻开始，不能把此前最新预览当作过去已记录的历史。
- 同一任务的前置导航若要入包，必须由任务上下文明确传递recorder并标stage；不能把上一角色的登录帧当作当前任务历史。
- task/target切换：旧scope关闭，后续回调不能串入新scope；旧包可后台收尾但仍占预算。批量授权可作用到本批次下一子任务，但图环不能跨子任务继承。
- 所有图像cache清空与frame_seq延续遵守原引擎契约；不要为了debug重置原计数器。
- 已主动开启且策略always的任务完成时，若本scope尚无覆盖最终观察的包，后台封口一次final历史包；已有适用异常包则复用。
  on_issue仅在本scope无留证事件且正常结束时不自动导图，记录policy_no_issue后释放环；已有incident不因最终成功被删或改成无异常。
  手动导出/反馈、明确停止保留、异常/人工交互触发不被该策略挡掉。
  未开启的任务不因此补图或自动开启。完成包受原磁盘限额，可被清理；历史显示已过期/缺失而非假装仍可取。
- 用户停止本次记录：拒绝新准入，按user_recording_stop封口已有历史再释放；主动选择丢弃才不构包。
  已在C编码中的图仅在有效导出票据期限内收尾，其他迟到结果丢弃并释放预算；不写下一任务，不影响自动化stop。

### 7.2 触发当下冻结什么

在确认等待、异常传播或恢复动作之前，固定：incident、触发时间、截止event_seq、最后消费key及当时已知观察。
短锁内只做状态切换、引用快照/移交与统计；不压图、不写磁盘、不调用Qt、不等待条件变量。
不可变bytes可共享引用，不深拷贝整环；但共享仍会保活内存，必须计入预算。
元数据也必须移交/生成有界不可变摘要，不能让冻结包继续引用可变observations列表。
只纳入截止event_seq前已知观察；开始了但尚无结果的识别标pending。收尾允许补对应旧key的编码图，
不把触发后的新观察/结果悄悄改写成“触发时已知”；若另收补充结果，必须显式标记其晚到时间与性质。

首版选择简单策略：**导出期间暂停debug新准入，自动化继续；完成/失败后若原scope仍在运行且未停止，再恢复空环采集。**
暂停包括新图/观察/动作明细，仅保留有界空档计数与同incident触发合并，不能偷偷把新动作追加进冻结集合。
记录该空档；不为“连续”另填一份10MB活环。若任务已经退出不恢复，不把下一任务帧追加进旧包。

### 7.3 in-flight与异常关键帧

1. 已编码关键帧直接引用；已在编码中的同key job可作为有限收尾项；pending同key保留。
2. 若关键帧未准入/被背压跳过，只有调用方仍能提供**同key的真实消费帧**时才允许在raw预算中优先复制，替换普通pending。
   不能用“现在再capture一张”补位，也不能无校验使用已更新的last。
3. 无法取得稳定副本、尺寸过大或预算不足时直接记录missing；不能为了“最后一帧一定在”突破内存上限。
   关键帧补入也执行100帧/编码总字节双限，必要时移除最老候选；截止不变但最终入包名单可在收尾期确定。
   最终名单封口后再写ZIP；旧集合不得在别处保留待淘汰bytes引用。未接纳的编码输出暂存另计，不能以此声称总RAM仅10MB。
4. 在候选收尾deadline内等待有限job，不等所有未来任务。到时对仍未完成key写 pending/missing，导出可用帧和原因。
5. 活环generation与冻结导出ticket分开：关闭活环后，原in-flight仅能在有效ticket与收尾deadline内归入指定旧包，
   绝不能写下一任务；停止采集不等于取消旧包。导出封口/取消则ticket失效，其后完成只释放资源。
6. 编码器是不可强制中断的原生调用；超时只停止等待/拒绝其迟到入环，不声称杀掉了编码。
   仍被worker持有的raw/输出额度直到返回才可释放；不可为下一任务不断新建替代worker。
7. 超时/故障若使单worker持续不可用，本次进程停用历史编码并提示，现有自动化和PNG机制继续。
   单独导出作业可用已压缩帧生成partial包，不被卡在编码线程后方。

### 7.4 重复触发、日志与退出

- 同一scope、没有新有效观察/动作的同一截止现场，显式PNG/confirm、pause/UnattendedInterrupt/外层失败合并为一个incident；
  reason列表有上限。已完成包不可变，后续重复事件只在日志引用既有incident，不反复重打同一包。
- 恢复后出现新有效观察/动作再失败可成为新incident；仅frame_seq未变不等于现场没变。
  去重依据scope+截止观察/动作边界，不因重复trigger自身刷新边界；导出忙时记busy/缺失，不排无界队列，保留PNG退路。
- 不同run/target不能合并；旧导出尚占预算时新任务可暂不记录并显示原因，不能偷偷开第二环。
- 所有文件写入和有限等待在后台。控制线程/Qt主线程不能 `join` 编码或等待ZIP。
- 正常退出只做有限flush；超时可丢未完成包并清理本作业临时文件。kill、OOM、原生崩溃无法保证导包，
  不为此在MVP加持续落盘spool或崩溃服务。

## 8. 诊断触发矩阵与货运例子

| 入口/事件 | 诊断动作 | 不能改变的语义 |
|---|---|---|
| 明确业务失败、顶层负数/failed dict | 退出前请求包，标业务失败，保留当前scope | 用`return_failure_message`，不扫描所有局部负值/合法哨兵 |
| pause | UI回调或native等待之前冻结 | 人工模式仍等待；无人值守仍按既有逻辑退栈/恢复 |
| confirm | debug首版在入口请求“人工交互现场”，与同帧现场合并 | 普通确认不是failed；保持原是/否与等待行为，不自动回答 |
| UnattendedInterrupt | 在上游pause已冻结时仅关联incident；缺入口时在恢复前补请求 | 不改成“从中断指令继续”，不保留已退出调用栈 |
| Python/DSL/ExpectedError失败 | 最内层可行动处请求；外层去重 | 不吞错、不改错误类型/返回值；WorkflowAbort路径不能只依赖语句报错函数 |
| 普通OCR miss、轮询false、可选弹窗缺席 | 只入历史与观察 | 不逐次导ZIP、不报假错误 |
| 用户主动stop | 业务沿用stopped；若曾主动记录则后台封口已有历史、释放环 | 不是业务异常，不自动恢复或产生新的等待 |
| 手动“导出当前历史” | 明确manual事件，不受on_issue成功丢弃策略影响 | 不操作设备，不捕获额外实时图 |

confirm的兼容留证覆盖既有“异常分支却使用confirm”的代码，manifest分类必须是interaction。
若实测正常业务确认产生太多包，再由调用方通过通用hook显式区分异常原因；
不先为此改所有脚本、不解析中文提示、不新增游戏专用内置函数。磁盘限额和同帧去重仍适用。

当前批量仍有“没有抛异常就标成功”的收尾路径。阶段B必须核对其修复进度：
若尚未修复，先单独修正/验收业务结果归一化，再接统一退出观察；诊断也可独立读取既有判定函数发失败事件，
但不得反写业务状态或宣称旧问题已经解决。只有异常传播或现有completed回调的hook都不够。
货运中任意局部`back=-1`也不能直接判任务失败，应由明确异常入口或顶层协议拥有语义。

货运场景仅用作验收用例，不写入公共层常量：

1. 识别货运页、进入物资商店、购买前后、返回导航各自消费的图依次入环。
2. 返回后目标识别未命中，若脚本仍在正常重试，仅留观察，不立刻导包。
3. 重试耗尽、准备“未确认页面，等待手动处理”时，在confirm/pause之前冻结，保留预期标题、实际OCR和ROI。
4. 等待半小时没有新识别，就没有新帧；manifest显示真实起止时间与最后帧龄，不冒充半小时录像。
5. 人工继续/无人值守恢复可以照常运行；旧包截止不变，恢复后帧不挤掉原现场。
6. 包只提供证据，不重复补货、不确认购买、不领奖、不调用完成记账。误报完成、返回导航等确定性问题分别修复。

## 9. ZIP结构、关联数据与人可读索引

每个incident只生成一个可独立解压的本地包；下例为WebP，JPEG降级时文件扩展名与manifest同步改为jpg：

```text
diagnostic_<time>_<random-incident>.zip
  manifest.json
  index.html
  frames/
    0001_e1_f154.webp
    0002_e1_f155.webp
  steps.log
  task-tail.log          # 可选，有界、脱敏，非整份任务日志
```

文件名由程序生成，不带账号、设备序列号、任意OCR或源文件绝对路径。
`index.html`统一作为离线查看入口，含静态摘要与渐进增强查看器，不再并列另一份viewer.html竞争入口。
基础可读，增强支持左右键逐帧、Home/End首尾、Space播放/暂停（默认暂停），按键仅控制查看器，绝不操作设备。
图片只使用程序生成且通过白名单校验的包内相对路径；元数据/有限日志直接内嵌，不用fetch读取file://下的manifest/log，也不需本地HTTP服务或外部CDN。
内嵌JSON必须安全序列化/转义`<`等可闭合script的字符；OCR/日志只用textContent呈现，不能直接拼进脚本/innerHTML，
不把文本中的URL当外部图片/活动链接。不得执行用户输入、请求AI或自动上传。无需另生成100份缩略图。

查看器叠加ROI、请求/已知实际点击标记及拖拽端点箭头，原图bytes不修改；图例明确“请求坐标不等于实际落点”，
按编码尺寸和原尺寸转换，geometry不可信时只显示动作文字。显示当前frame key、时间/帧龄、实际OCR、前后动作与缺失提示。
结构化steps事件按完整frame key精确联动；任务原始文本日志仅frame_seq时只能在可确认的engine范围内做辅助搜索，
同任务多个engine重复seq不能靠全局正则高亮冒称精确关联。无匹配日志要显示未关联，而不是按时间猜一行。
离线查看器不得变成执行脚本/视频编辑平台；无JS或增强失效时仍能从索引/manifest及图片阅读现场。

拟议manifest字段：

| 分组 | 字段内容 |
|---|---|
| 包 | `format_version`、`app_version`、可得时的`source_commit`、`incident_id`、export_policy、状态complete/partial及原因 |
| 作用域 | `run_id`、`target_alias`/kind、任务稳定ID、stage、recorder_generation；不导出原始用户/设备标识 |
| 触发 | kind、sanitized reason、带偏移墙钟时间、run相对单调时间、cutoff_event_seq、last_consumed_key |
| 覆盖 | 最早/最晚捕获时间、触发时帧龄、实际帧数/编码字节数、丢弃与截断计数、暂停采集区间 |
| 每帧 | key、相对文件名、capture source/fallback、codec/扩展名、原/编码尺寸、缩放比例/坐标变换、质量、字节数、校验和（若生成） |
| 每次观察 | op/event_seq、类型、消费时间与帧龄、有限场景/ROI、expected/actual、matched/status及真实置信度 |
| 输入动作 | action_id/event_seq、pre/post_frame_key、帧龄、请求坐标及空间/几何、若真实可得的实际坐标、受限label/控制键/模式、派发状态；不含输入文本 |
| 缺失 | 明确key或有限序号范围、dropped/encoding_error/pending/raw_budget_exceeded等原因；大规模缺口用聚合而非无限数组 |
| 输出 | 文件清单/字节、日志摘录采集时点/截断状态、诊断器告警；不包含manifest自身递归摘要 |

字段命名只是提案；先为格式定一个内部版本即可，不引入全产品协议版本系统。
墙钟统一记录带UTC偏移的ISO时间，查看索引可显示上海时间（UTC+8）；时序优先按event_seq/相对单调钟，
不能因墙钟校正导致图片排序错误。不记录不存在的设备原始采集时间或虚构OCR置信度。
UTF-8、中文不转义、两空格JSON、末尾换行，实际写出后再按字节计算摘要。

`steps.log`从有界诊断事件生成，包含阶段、识别摘要、触发和缺口，不拷贝完整DSL/变量表。
可选`task-tail.log`只从显式传入的当前TaskRunSession日志路径读取有界尾部并脱敏；
不能扫描整天日志或session目录。摘录在后台采集，标明采集时刻，不能声称它与冻结图像原子同步；
如含触发后条目须标明或按可靠时间边界裁除。获取失败只省略此可选文件。

## 10. 安全落盘、限额与失败降级

- 建议默认输出到客户端根目录`logs/diagnostics/`，不引入安装目录外隐藏存储；手动另存为只复制用户选中的完成包。
- 保留包count与bytes同时受限；开始前预留包上限，清理本功能自有最旧完成包至有空间。
  不把压缩环10MB当作ZIP总大小，需计入索引、manifest、日志与ZIP目录开销。
- 只允许一个活动`.part`，临时文件也计入磁盘预算；写入时计数，预计越界先截短可选日志/索引明细，
  实在放不下则失败降级，不产出manifest引用缺失文件的伪complete包。
- 流式写文件，不在BytesIO里先复制整个ZIP；WebP/JPEG项用ZIP_STORED即可，文本按需DEFLATED。
- 唯一随机incident名、独占创建、不覆盖已有包；同目录临时文件完成后安全原子转正。
  Windows与中文路径用bytes文件写入，别依赖cv2路径编码或系统默认文本编码。
- 清理只操作诊断器自己生成的文件，不跟随目录符号链接误删别处，不碰活动包、用户另存文件、现有logs/image或所有日志。
  启动后可在有界扫描中清理本功能遗留临时文件，不创建无上限恢复队列。
- 磁盘满/只读/权限/路径错误：删除本作业临时文件、记录一次可行动状态，释放可释放的引用；
  原任务照常失败/恢复，已有显式PNG照常保留。可用同帧PNG能力降级，但不得重新capture冒充异常图。
- 无图也能输出说明原因的metadata-only partial包；若包写不出来只输出诊断失败日志，不再抛业务异常。

实现借鉴（仅源码检出）：[history/transfer.py](../../../src/lvjiang/core/history/transfer.py)：`export_history` 的manifest/路径校验，
但不要导出其数据库记录或把诊断环加入history同步通道。

## 11. 隐私与非上传边界

开启调试只授权本地记录，不等于授权后台上报；本功能不会在故障发生时自行发网络请求。
用户从任务入口主动打开反馈后，系统可自动选择该任务的日志和诊断包；清单可查看/移除，点击提交即授权发送所选整包，
不要求逐帧确认、二次安全审批或必须先打码。提醒“请自行检查截图是否包含敏感信息”即可。

- 保存识别当时实际拿到的目标帧，不额外截整桌面；from-screen/fallback可能包含遮挡窗口，不能承诺图里永远只有游戏。
- 不额外枚举/打包程序持有的密码、token、剪贴板、完整变量/参数dict、会话文件、数据库、用户配置正文。
  这不代表系统能识别并删尽截图中的敏感像素；画面由用户自行检查，不作自动完美脱敏承诺。
- 不为“脱敏”删掉页面名、ROI、预期/实际OCR、游戏内角色/物品等必要诊断信息；用户主动上报时允许保留这些画面/上下文。
  仅继续排除程序已知的密码/token等秘密字段；不自动模糊原图。业务可通过通用hook标记不宜记录的输入阶段，但不强制用户逐图审核通过。
- 图像不是自动脱敏的。文本regex不能保证屏幕秘密被遮住，不能宣称开启debug后分享天然安全。
- [feedback/redact.py](../../../src/lvjiang/core/feedback/redact.py)：`redact_text` 与
  [feedback/logtail.py](../../../src/lvjiang/core/feedback/logtail.py)：`read_excerpt` 可复用脱敏/限量思路（仅源码检出），
  不为了脱敏额外读取账户凭据；测试必须传合成身份或隔离来源。
- 现有[反馈限制](../../../src/lvjiang/core/feedback/limits.py)（仅源码检出）是最多10张截图、12附件，单件gzip后900,000B；
  本地100帧ZIP不是已支持的反馈附件。仅缓存阶段不动通道；本轮新增主动反馈阶段须按第18节联动改造，不能默默丢包或自动发送。

| 100KB软目标、quality与最低尺寸 | 授权Windows/Android目标的真实中英小字、复杂背景，人工读图并对照原ROI | 单一配置默认与现行参考；不只看PSNR |
| raw预算与多尺寸覆盖 | 测目标分辨率、copy耗时、编码临时峰值、总RSS增量及稳定长跑 | 支持范围/安全默认；不承诺总RSS10MB |
| 编码负载与背压比例 | 相同任务debug开/关配对测量、固定环境；统计p50/p95、CPU与dropped原因 | 量化接受门槛，未达标默认不启用 |
| 收尾deadline | 慢编码/真实异常帧与停止测试；确认partial准确、停止不等codec | 候选1000ms可调整，不能许诺ZIP总耗时 |
| 包磁盘上限与保留策略 | 实际单包总bytes、频繁异常/confirm噪声和磁盘受限测试 | 设置说明与清理常量 |
| 敏感内容边界 | 场景样本/操作参数白名单审查、用户可见告知、包人工检查 | hook与隐私说明，不宣称自动完美脱敏 |

性能门槛必须在真实样本阶段给出并记录，不能把“不会拖累识别”写成未测的绝对保证。
首要硬验收是不等待编码、缓存有界、原识别结果不变、停止/恢复行为不变；其余质量与开销以配对实测决定是否交付。
当前可先按候选值写单元边界测试，未验证真实平台前维持规划/测试态、默认关闭，不擅自改为生产默认开启。

### 14.3 吸收附件的校准方法，不转录未经复核的实测结论

外部v1.1自述316张游戏截图、平台体积均值/峰值与耗时，但本次附件未附原始图/测量日志；
本轮没有打开本机真实session截图复测。它们是第三方陈述，不能替换第14.1节已有Linux合成测量，
也不能据此声称“12MB总RSS、旁路P99<8ms、整任务增幅<3%”已达标。

采纳其可执行实验矩阵：隔离授权样本按目标平台/分辨率/文字密度分层，比较不缩放基线与长边1280/1080/960，
WebP q75/q65及JPEG q75。参数组合是候选，不是同时提供多套运行流程；校准后选一个默认档位。
报告编码/copy/resize/准入的独立耗时分布、P50/P95与有足够样本才报告的P99、字节分布、队满丢弃率、
冻结到本地文件就绪耗时、稳定长跑的RSS峰值/CPU，以及debug开关的配对整任务耗时。
旁路P99<8ms和总耗时增幅<3%可作为附件建议的候选验收目标，必须先确认硬件/样本/统计方法；
编码线程耗时不混作主线程开销，原图/缩小图/待编码/冻结/上传缓冲也不混作“仅10MB”。

小字质量由人工检查关键ROI，并用同版本OCR/清洗配置离线比较；原始OCR本身可能错，必须有人工核对的关键文本/数字真值，
分别报告召回/误读与不可读样本，不以“压后还能跑OCR”或原OCR一致就声称可读。
如缩放不达标，优先保分辨率并接受少于100帧，不强制把所有图压到100KB。
压测脚本按一次性验证管理，可在scripts/one_off中实现但不是本轮产物；不读取/写入真实配置或承诺附件中的开发工期。

## 15. 主动开启范围、身份与跨重启关联

### 15.1 常驻的是能力与轻量任务记录，不是截图

关闭时，已有任务历史/任务日志照常工作，并可写一份很小的“未开启”诊断摘要；不copy图、不编码、
不维护OCR/动作明细环、不启动截图worker。普通任务日志属于既有能力，不因debug关闭而停写。
因此on_issue的“正常不导图”仅指不生成图像ZIP，不是整任务零磁盘I/O；SQLite摘要/任务日志仍正常写。
运行态`export_policy`取always（默认）或on_issue：后者仅无留证事件且正常结束才清空图环、记policy_no_issue；已有包保留。
异常、人工交互、用户手动导出/反馈和明确停止保留都可触发on_issue留包；不是另一套采集/队列流程。

| 用户动作 | 范围与结束条件 | 记录起点 |
|---|---|---|
| 启动前开启“本次任务调试记录” | 仅这次task_run_id，结束即解除 | 首次实际识别消费 |
| 启动前开启“本次批量调试记录” | 明确的batch_run_id；各子任务独立建环，批次结束解除 | 每个实际执行子任务开始 |
| 运行中开启单任务 | 当前指定task_run_id，建立新capture_scope | 开启后的下一识别，不补录 |
| 运行中开启本批量 | 当前子任务从此刻起，后续本批次子任务从开始起 | 各自独立标记；此前已完成子任务仍未记录 |
| 停止后再次开启 | 同task_run_id下的新capture_scope | 新一段，不拼成连续全程记录 |
| 重启程序 | 一律未开启；已完成本地包仍可从原任务查找 | 不自动恢复图环或后台上传 |

用户取消某子任务的记录不应解除整个批次的后续授权；停止“本批量记录”则当前和后续子任务都停止。
UI文案区分两种操作，不把它们写回批量配置组。无图/中途开始/丢帧/导出暂停区间都是覆盖信息，
不是自动化业务失败。批次勾选跳过的任务目前不会创建TaskRunSession，不为debug伪造执行历史。
开启时可选落盘策略也只作用于本次范围，不写入批量配置组或跨重启恢复；未来CLI仅可把同一运行选项传入，
不能单独建第三套逻辑。现有[task_cli.py](../../../src/lvjiang/core/task_cli.py)尚无本文开关（仅源码检出），CLI适配非首版前置。

### 15.2 身份只保留必要层级

| 身份 | 权威与用途 | 不新增什么 |
|---|---|---|
| `task_id` | 脚本/功能稳定ID，只说明“哪种任务” | 不能拿它定位某次日志 |
| `task_run_id` | 既有TaskRunSession的一次执行主键；诊断`run_id`只是其别名 | 不再另造随机diagnostic_run_id |
| `batch_run_id` | 既有BatchRunSession批次主键，可为空 | 不把整批的外层运行占用ID冒充每个子任务ID |
| `capture_scope` | 本task_run_id内第几段主动记录，复用recorder_generation | 无需新的全局UUID服务 |
| `engine_epoch + frame_seq` | 该段内不同引擎及捕获身份 | 不把seq=1跨引擎合并 |
| `incident_id` | 同次触发/冻结/包的关联；一任务可以多incident | 不代表业务attempt |
| `feedback_id` | 正文被服务器接受后返回的编号 | 不能用本地包ID冒充已上报 |

同名任务重复执行、下一轮批量、人工重新运行均已有独立task_run_id；内部有限重试仍属于原task_run_id，
事件中可带现有round/run/script序位方便阅读，但首版不新增独立attempt主键/表。
单次运行已把ExecutionRunContext.task_run_id传给TaskRunSession；批量每脚本生成自己的TaskRunSession。
如果任务历史写入失败，先分配/保留本次运行ID供UI与诊断共用，再尝试持久化；标history_unavailable，
不因记录失败阻止业务，也不能宣称不存在的历史行/日志已保存。

依据（仅源码检出）：[daily.py](../../../src/lvjiang/core/history/daily.py)：`TaskRunRecord`、`BatchRunRecord`、
`TaskRunSession`、`try_create_task_run`；[run_control.py](../../../src/lvjiang/ui/main/run_control.py)：单次历史创建；
[scheduler.py](../../../src/lvjiang/core/batch/scheduler.py)：按脚本创建子任务；
[daily_history_dialog.py](../../../src/lvjiang/ui/daily_history_dialog.py)：按record.log_path显示日志、按batch_run_id下钻。

### 15.3 复用现有历史库，只加最小本地摘要

建议在既有task_runs添加一个`diagnostic_summary_json TEXT NOT NULL DEFAULT ''`，并在TaskRunRecord末尾加缺省字段，
按现有_MIGRATIONS显式升一个版本；这是既有历史模型的增量，不是新建诊断数据库/录像数据库。
只存录制状态、覆盖起止/缺口、最后构包状态、相对本地索引路径、最近反馈编号/上传摘要；不存图像、逐帧OCR、ticket或原始设置。
按启停/冻结/导出/提交等状态变化写，不能每帧写SQLite。

旧行空值显示“旧记录：无调试信息”，不能一律猜成“用户未开启”；新版未开启任务显式记not_enabled。
新增列不改已有列含义；新客户端兼容旧记录是必测项，降级旧客户端的读写能力需定向测试确认，不能仅因SQLite允许加列就承诺任意回退。
实现时同步检查历史导出/导入，不能把本机包路径伪装成云端可用附件。
本机诊断摘要/回执不自动走账户同步；如历史导出保留摘要，必须去除本地路径/凭据并标附件未随行。

开启后另有确定性本地目录建议：`logs/diagnostics/tasks/<task_run_id>/record.json`与同目录incident ZIP。
record.json只索引本任务scope/包相对路径、大小/哈希、状态与缺失原因，原子替换；不根据任务名/时间全盘搜索。
历史摘要只指向这个小索引；上传回执另存反馈本机运行态位置，不混入诊断包。
先完成ZIP转正，再更新record.json，最后写历史ready摘要；读取端必须验证索引/文件存在才显示可取。
崩溃在中间时显示incomplete/missing，允许在本任务自有目录有限修复，不拿孤立.part当完成包。

普通包清理后仍保留受限历史摘要/缺失原因，显示expired而不是“没有开过”。旧任务无摘要/目录时不借最近其他任务包。
跨重启只恢复已完成索引/反馈草稿引用；此前RAM历史永远补不回来。

### 15.4 日志绑定、线程与封口

现有TaskRunSession.capture_logs使用logger.contextualize(task_run_id,target_id等)，sink按task_run_id过滤。
WorkflowWorker.run在QThread内部进入该上下文，批量在执行每脚本时进入；这些线程的日志已经有独立log_path。
新增编码/导出/QThread/线程池工作不能假设自动继承此上下文：每个job携带不可变scope并显式进入对应日志上下文，
Qt信号也传明确task_run_id/incident_id，不从当前选中行补归属。

任务日志sink在capture_logs退出时移除。任务结束后异步构包的信息写入该incident的steps/索引并带task_run_id；
不能假设还会自动追加到已经关闭的任务日志，也不能为等它而阻塞任务结束。
主任务日志快照注明截至时间/截断状态；恢复阶段/批量准备阶段若不在子任务日志上下文里，只能单独标“阶段日志”，
不得把整批或整天混合日志伪装成该子任务日志。控制台看见的缺失信息必须真实。

## 16. 四种状态正交，任务行如何显示

| 维度 | 建议状态/来源 | 改变它的事件 |
|---|---|---|
| 业务执行 | 沿用running/completed/failed/interrupted/stopped/skipped等实际模型 | 既有执行器/结果协议，不由诊断器写 |
| 调试记录 | not_enabled、recording、stopped、unavailable；另带partial覆盖原因 | 用户启停、队满/不可用、任务结束 |
| 本地诊断包 | build_state为none/building/ready/failed/expired或missing；ready另带completeness=complete/partial | 本地导出和保留清理；可用但不完整与构建失败分开 |
| 反馈发送 | not_submitted、preparing、submitting、body_received、uploading、received、partial/unknown/cancelled | 用户提交和服务端回执，不等同本地文件存在 |

UI可用例：`失败 · 调试部分记录（中途开启，42帧） · 包已就绪 · 未上报`；
`已完成 · 调试已停止 · 包已就绪 · 正文已收，附件待补传`。
recording结束后历史显示“已记录/部分记录”的覆盖摘要，不把“停止记录”显示成任务停止。
manual confirm标人工交互并可有包，不能因此把任务判失败；有包/上传成功也不能把失败判成功。

本地ready只说明文件可读取；反馈received须正文有feedback_id且选中附件都收到确认。
包部分帧缺失和网络部分上传是两个不同partial，分别显示原因，不用一个颜色/布尔值合并。
无图场景至少区分：未开启、开启前已出错、中途开启、策略正常不落盘、无识别帧、背压丢弃、编码失败、历史已清理、日志不可用。
批量行可按batch_run_id聚合“含M个可用诊断包的子任务”，不在batch_runs复制包路径；过期/缺失需单独计数，展开后定位具体task_run_id。
任务历史/失败行加“反馈此任务”入口时，必须携带这行task_run_id及已知incident_id；从整批入口先选出实际子任务，
不按失败文案或任务名查“最近一次”。

## 17. 用户主动反馈：自动准备，提交才发送

### 17.1 现有通道与真实缺口

现有FeedbackDialog构造只有parent，没有task_run_id上下文；它支持手工贴图/选图，日志来自按日期选择的主日志尾部。
任务历史已有精确log_path，但目前未连接到这个对话框；`ui/execution/feedback.py`只是执行按钮旁的说明标签，不是上传接口。
因此“从任务直接自动带上日志+包”是待做增量，不是已存在能力。

现有反馈匿名也可提交、回复邮箱必填，保持这两个既有条件，不新增登录门槛。
现有提交先POST正文获得id/ticket，再按附件序列逐件POST attach；按(feedback_id,seq) UPSERT支持同一清单补传。
当前清单/失败附件只在对话框内存；草稿保存文字，不保存附件、任务关联或提交后补传回执；提交时还不能关闭/取消。
这些都需要补齐，不能把现有“补传附件”按钮当跨重启可靠恢复。

依据（均仅源码检出）：
[FeedbackDialog](../../../src/lvjiang/ui/notices/feedback_dialog.py)：`__init__`、`_refresh_log_state`、`_attachments`、`_submit`、`_retry_attachments`、`_save_draft`、`reject`；
[反馈客户端](../../../src/lvjiang/core/feedback/client.py)：`submit_feedback`、`upload_attachments`；
[日志摘录](../../../src/lvjiang/core/feedback/logtail.py)：`read_excerpt`。

### 17.2 推荐交互链路

1. 用户在失败行/任务历史点击“反馈此任务”，传入拟议FeedbackContext(task_run_id,batch_run_id?,incident_id?)，
   从TaskHistoryRepository.get_task_run取得精确日志与诊断索引；不自动打开浏览器/发网络。
2. 后台准备对应任务日志快照和包。默认选择指定失败incident；只有任务ID时选择该任务最近完成包并在清单写清。
   同任务有多包则列出供选择，首版一次反馈默认一包，不能把“取了最新一份”描述为已带上全部现场。
3. 如果任务仍运行且调试已开启，冻结当前scope并生成manual_feedback包，任务继续；若已有适用故障包可直接使用。
   如果未开启，提示“没有历史画面，可附此任务日志”，不偷偷开启调试或用当前截图冒充出错前历史。
4. 构包中显示准备状态。原提交按钮等待所选包就绪；用户可明确选择“仅提交日志/现有附件”，
   此时移除待构建包后再提交，不能在后台包完成后擅自补上传未列出的内容。准备失败/超限显示原因并给同样选择。
5. 清单逐项显示所属任务、scope/截止时间、帧数、大小、本地完整度/截断、包是否已过期；提供查看/移除入口。
   显示固定提示“请自行检查截图是否包含敏感信息”。不强制逐图打码/二次授权，不隐藏或故意模糊关键OCR/游戏画面。
6. 用户点击“提交反馈”：冻结本次清单与内容哈希，**一次点击授权随正文发送所选日志与完整诊断包**。
   用户未提交前的自动收集仅本地；故障触发、开启debug、打开反馈页都不授权后台上报。
7. 逐项显示正文已接收、附件上传进度、完整收到/部分收到。失败保留本地文件与补传引用；重试只由用户发起，
   不因下次启动程序或连接网络而自动发出。

任务日志默认有界摘录（候选256,000B）并明确“日志已截断”；允许在总预算内选择完整任务日志，
超限必须说明并允许另存/明确降级。不能默默退回最新一天的混合日志。
包内含相同task-tail时可避免重复大附件，但清单需说明日志位于包内；单独日志便于阅读时也须合计字节。
只自动取该任务证据，不额外搜集密钥、session配置、完整参数dict或用户数据库。
通用“反馈与建议”入口不传上下文时继续普通反馈；可增加“关联任务（可选）”选择器，列有限条近期失败/有包任务，
必须用户选中后才按该task_run_id准备证据，不默认把最近失败当本次问题。使用运行时冻结的环境/布局/起止与错误摘要预填，
不能拿当前全局布局覆盖历史上下文；反馈类别用户仍可改。切换关联任务仅替换此前自动附件并明确归属，避免残留旧任务包。
对应任务没有日志就明确missing；不要自动回退到当天2000行混合日志。全局日志如确有需要，只能由用户另选并标“额外全局日志”。

### 17.3 本地固定清单、pin与重试记录

- 准备/预览/上传时pin对应完成包与日志快照，清理器不能删除它；running日志必须先取有界不可变快照。
- 提交后按文件hash固定附件序列；不在补传时重新抓最新图/日志，不从失败子集重新enumerate成seq=1覆盖原附件。
- 草稿增加task_run_id/incident_id与本地引用，不能恢复另一反馈草稿后覆盖本次入口任务。
  提交后另存job回执：feedback_id、固定seq/分块清单与哈希、确认/失败状态、授权凭据的受保护本机引用。
- ticket/幂等随机key属于反馈上传凭据，不写到任务历史、诊断包或日志；沿用本机受限草稿/凭据保存方式并显式排除Git/云同步/历史导出。
  不建立新账号体系，不读取用户其他账户凭据。
- 本地job采用临时文件原子替换。正文/附件得到回执后再推进状态；进程退出/响应遗失记unknown，重启后仅显示“可继续补传”。
- 关闭未提交对话框可保存本地草稿并释放会话pin；已失败包保留本地待用户重试，仍受明确保留期限/容量约束。
  若清理后不存在，显示expired，不能自动换成其他包；如提供“保留待补传”，它也必须受同一总磁盘配额约束，
  满额时提示用户处理旧记录，不静默删正在上传包或无上限积累pin。
- 上传取消是“不发后续请求”：现有HTTP调用只能靠其超时结束；已到服务器的正文/块不能说已撤回。
  显示部分已收/结果未知，保留原job供用户重试；不要为取消增加删除服务端反馈的隐含动作。

## 18. 完整诊断包传输：必须改现有容量契约

### 18.1 不能直接上传的代码事实

独立server的[src/feedback.mjs](../../../server/src/feedback.mjs)现限定：总12附件、截图10、日志1、diagnostics体检文本1；
单件存储payload最多900,000B，MIME仅PNG/JPEG/WebP/text/plain，**不接受ZIP**。
[src/worker.mjs](../../../server/src/worker.mjs)对attach请求上限1,800,000B，对submit清单262,144B；
[src/console.mjs](../../../server/src/console.mjs)按件取payload；
[ConsoleView](../../../server/web/src/views/ConsoleView.tsx)对非image按文本展示，不能直接显示二进制包。
均仅源码检出，server是独立仓；本轮未改server。这些是项目当前限制，不代表本轮已核实的平台最大额度。

12MB ZIP不能一次塞进900KB单件，WebP再gzip也不能保证足够变小；把100帧当100个screenshot也会超过数量限制。
现有diagnostics种类是体检报告占位，不是“已能上传诊断ZIP”；不能伪装text/plain绕过MIME，更不能默默少传后报成功。

### 18.2 建议首选：复用现有D1附件行，有界分块

不新增数据库/R2/通用大文件平台。仅为主动反馈扩展既有submit/attach与控制台，先服务端后客户端联动发布。
候选契约（未实现，所有容量均待实测确认）：

- 允许一个`diagnostic_bundle_manifest`（application/json），描述zip总字节/整体sha、task_run_id/incident_id、固定chunk顺序/长度/sha。
- ZIP按最多800,000B切成`diagnostic_bundle_chunk`（application/octet-stream），包上限12,000,000B意味着最多15块；
  块直接传、gzipped=0，避免对ZIP无谓二次gzip。每请求base64约1.07MB，仍在当前attach请求上限以内。
- 保留原截图/日志/体检限制；新种类上限分别1/15，总数候选28，另外增加所有附件合计候选24,000,000B硬限。
  “清单28件”不等于“用户要管理28个附件”：UI仍显示一份逻辑包，内部处理分块。
- 清单、单块、合计、包总量分别校验；服务端不能只限制单件而放任任意块数。普通主日志也计总量。
- 在既有feedback表增存受限的声明清单（建议attachment_manifest_json），复用feedback_attachment的(feedback_id,seq)，
  新块只接受声明的固定长度/sha/类型，校验收到的实际字节sha；同seq同内容可重试，不同内容拒绝，避免误覆盖。
- 当前仅保存attachment_declared总数、不保存逐项声明，也不核验payload与声明sha一致；这些是待补契约，不能凭当前计数判断完整包。
- 不在Worker解压ZIP。逐块校验后可判断“声明的块已收齐”，控制台重组再校验整体sha并生成ZIP下载；
  缺块/整体校验失败就不能显示“完整诊断包可用”。服务端回执需明确已收/缺失seq或同等可验证信息。
- 控制台不自动下载所有大附件：打开详情只取元数据，用户点下载包后逐块获取、校验并按顺序重组；不能用TextDecoder解码ZIP。
- 客户端用文件引用/offset流式取块，不把全包变成多份bytes/base64常驻内存；每块暂存和网络缓冲另计，不挪用10MB图环承诺。

服务端现有反馈正文没有定期清理；新增大附件必须同时决定诊断块保留期/每反馈与总体存储预算，
否则即使每件合规，反复上报也会持续增长。优先仅对诊断块到期清理，保留正文/任务引用与“附件过期”标记；
天数/总量由实测和运营容量确定，未决定不能宣称全量上报链路已可长期上线。
不编造Cloudflare存储/读写费用或把减少请求数当唯一收益；记录实际块数、总字节、上传耗时与失败率再决定默认策略。

如果服务端尚未联动上线或拒绝新kind，完整包发送应明确失败，不自动只发正文。
可提供用户明确选择的降级：“关键帧（最多10张）+对应任务日志”，并在反馈正文/清单标明“非完整历史，原包留本机”。
选择/缩减必须发生在本次提交清单封口前；不能用同一个已提交seq换成另一张图。
可吸收附件的关键帧挑选思路：优先最后连续现场，再补前面动作后的首个保留帧，按key去重和时间排序，
总数仍受10张限制。缺失项写到明确的excerpt说明；不能把引用100图而只附8图的manifest标完整，
也不能保证固定960px/q65会满足900KB或声称“90%以上现场最后10帧就能定位”。

另一候选是小于单件限额的摘录ZIP，但它同样需要新MIME/kind、客户端与控制台二进制下载适配，
不是“保留现有校验就零改动”。首版显式降级统一采用现有图片+任务日志，不并列一套伪装diagnostics文本的ZIP协议。
当前方案完整包主路径仍是第18.2节有界D1分块；如暂不扩展传输，首版只能明确标为关键帧降级。
附件提出的R2可减少大量BLOB存储，是日后容量增长的可选后端，但需要新绑定/存储保留/鉴权下载/控制台改造，
不作为本次前置，也不保留与D1分块同时默认启用的两套上传状态机。只有实测容量/成本证明需要时另立迁移决策。

### 18.3 提交响应遗失与补传幂等

当前客户端submit会重试网络失败，但server每次新生成id/ticket，不能保证正文不重复。
已拿到id/ticket后的附件同清单补传则已有UPSERT基础；需要保留完整seq，不能只传失败子集后重新编号。

建议新任务反馈增加一次性的客户端高熵`submission_key`，复用既有ticket_hash去重，而不是另建认证系统：
同一次用户提交固定正文/清单与key，server可用sha(key)唯一约束查找/创建一次，回同id及该key对应上传ticket。
重复key必须核对冻结正文与声明清单相同；不同内容拒绝。无新字段的旧客户端仍走原路径。
只保存该key的hash于server；本地按上传凭据保护，不能写进包。同key成功重试不再占新的反馈条数，
但附件仍受固定声明/容量限制；不得通过重试改变内容。实现需用临时SQLite验证并发/重试唯一性，
不简单地“查一下再insert”而遗漏唯一约束。不确定是否创建成功时记unknown，通过同key重试确认，不再生成新key盲目重报。

取消/超时后重试同id/同seq/同bytes；服务端已有接收的块可重复确认，未接收的继续补传。
当前对话框QThread没有取消入口，需在每次请求前后检查停止标记，当前请求受既有超时限制；
UI可以关闭/保留job但不能销毁仍运行的QThread，晚到回执只更新同一job，不改下一条反馈。
只有正文和所选逻辑附件全部确认才显示received；部分上传、取消、凭据过期都保留本机并说明下一步，绝不后台自动恢复发送。

必须新增/补充的定向验收：

- 关闭/重启不采图；主动作业/批次开启、中途开启停止重开无追溯；always/on_issue成功收尾唯一一致，on_issue明确无包原因。
- 动作后无变化/标题仅变一字/无输入但网络回包：首版不因MAD相似丢证据，动作、前后帧与坐标来源可解释。
- 批量各角色与轮次task_run_id不混，跳过不伪造执行；聚合包数按子任务现有ID，不拿批次路径代替。
- 旧历史空摘要能读；新摘要写失败不影响任务，包封口/索引/历史更新中断不假ready；清理后反馈入口能解释expired。
- 工作线程、编码/导出线程、Qt回调传递相同任务关联；两个角色并行及异步晚到不串日志；sink关闭后构包日志仍有incident关联。
- 成功/失败/人工confirm与包状态正交；关闭图记录仍能从任务精确取得日志，不回落到别的任务或当天混合日志。
- 点击反馈只本地收集；通用反馈可主动选关联任务，切任务不留旧自动附件；日志缺失不偷偷换全局日志。
- 一次提交才网络发送；清单有查看/移除和固定截图提示，没有新增二次安全审批/逐图强制打码。
- index解压后离线可导航/查看动作，脚本结束标签等文本不会变成代码；断网无外部请求，几何缺失不画假落点。
- 正在运行/正在构包时的等待、用户明确仅日志提交、无帧/日志缺失、旧草稿恢复任务归属均准确且可取消。
- 候选12MB ZIP分块上传/控制台重组哈希一致；缺块、乱序、重复、越界数量/合计、不同内容复用seq都可检出。
- 正文响应遗失同key无重复；附件响应遗失/取消/重启固定seq补传不覆盖；未完成不显示已完整收到。
- 清理不删准备/上传pin文件；失败包保留本地可重试，跨重启缺失明确说明，不自动上报/重发；没有云端密钥或session配置进入附件。
- 所有验证先用临时历史DB/SQLite、合成日志/ZIP/API与离屏UI；新增server/客户端协议测试需联动，不能只靠本轮文档lint代替实现验收。
