# 无人值守批量

> 状态：已实现（2026-10-07，基线 v0.13.13）。批量配置的「无人值守」+「异常恢复工作流」。
>
> 实现契约（拦截点、调度器注入的信号、配置层兜底与落点）见
> [39-runtime/05-unattended-recovery.md](../../30-architecture/39-runtime/05-unattended-recovery.md)。

## 1. 问题

批量任务常要连跑几个小时，预期之外的页面可以通过 `pause` 声明异常阻断。
没有人在场时，应结束异常任务并恢复页面，以便继续后续任务。正常确认、输入
和选择属于任务的业务步骤，不能仅因等待用户就判为异常。

## 2. 边界

### 2.1 仅 pause 触发异常改道

- `pause`：中止当前任务，按异常记失败、不重试，再执行异常恢复工作流。
- `confirm` / `input` / `choose`：交给正常 UI 回调，等待用户决定，原样返回结果。
  无人值守不替用户选答案，也不把这些交互记为异常或触发恢复。
- `notify` 和其他 UI 事件：正常转发。

正常交互会等待用户，所以无人值守不保证任务全程无需人工。自动调律的回收
结果选择、材料询问和库存输入均保留交互；重置及导航的人工处理也使用确认。
安卓兑换码的手动输入步骤使用 confirm，拒绝时结束兑换并保留当前页面。

诊断由 WF 失败分支显式记录。需要异常 pause 时，先截图再 pause；无人值守
中断后不会执行该 pause 后的语句。正常交互本身不要求异常截图。

### 2.2 恢复目标只有一个页面

所有批量任务都假设游戏停在**登录页 - 登录主页视图**。所以恢复目标也只有这一个，
不按任务区分。

恢复按代价从低到高：已在登录主页 → 什么都不做；在启动页 → 点一次返回；两处都
不在 → 重启客户端再回到登录主页。**不是一撞弹窗就重启**：画面往往只是多了一个
弹层，重启要等客户端起来、还要重新选账号，是最后手段。

### 2.3 两个阶段

恢复不止"回到登录主页"：如果当前用户还有未执行的任务，停在登录页等于让下一项
任务在登录页上必然失败，白跑一轮。调度器把"本条目还有没有任务"作为信号注入，
恢复流程据此决定走到哪一步。

| 条目剩余任务 | 恢复到哪 |
|---|---|
| 没有了 | 登录主页，等调度器切下一个用户 |
| 还有 | 登录主页 → 点「当前角色」→ 游戏主页 |

重新登录**必然**撞上「角色在线」：异常中断或强杀客户端后服务端仍认为角色在线。
恢复流程点确定把角色顶下线——与正常流程里点取消改走"跳过"的处置相反，无人值守下
没有"稍后再来"这个选项。

### 2.4 重启是框架能力，不是某个任务的私事

恢复动作做成**批量配置的第五个生命周期工作流**（异常恢复工作流），由调度器在撞到
弹窗后调用。这样非重启类的批量任务也能用上同一套恢复，不必每个业务 wf 各写一遍
重启逻辑。

**没有配置异常恢复工作流的配置组不允许勾选无人值守**：缺了它，改道弹窗只会把整批
推到错误页面上连环失败，不如照旧弹窗等人。界面禁用勾选框并说明原因，配置层也会
清掉手改出来的这种组合，调度器启动前再确认一次。

### 2.5 恢复流程自己不能弹窗

恢复 wf 运行在"没人在看"的前提下，所以它自己绝不调用 `pause`。能自动收的收，
收不了就如实返回 `failed`，由调度器记录后继续往下走。

它复用正常登录的落地流程（顺带处理战令领奖与活动弹窗），那条路径在超时后仍会
`pause`；无人值守下这会中止本次恢复并报 `failed`，不会把批量挂在弹窗上。

### 2.6 重复脚本加载的性能边界

候选检查、生命周期和任务正文经公共解析入口复用未变化文件的解析结果，避免每个
成员、每轮重复执行 Earley 解析。缓存仅保存语法树，不保存用户参数、变量、过程
注册表或校验结果；每次加载获得独立副本。根文件和每个 import 文件仍读取当前内容，
修改立即触发重新解析，删除仍报错，循环依赖和定义冲突仍由本次加载检查。
缓存有容量上限；并发加载同一未变化文件不重复解析。首次加载仍需解析，不承诺
消除首次解析的 GIL 争用，也不以改变等待精度或键盘钩子行为代替此优化。
