# 配置迁移恢复指南

本指南面向普通用户，介绍「任务参数」从旧位置搬到新位置（迁移）时，四种常见
情况的处理步骤。只需照做，不需要理解内部实现。

## 背景：什么是「迁移」

旧版本把每个脚本的任务参数存在主设置文件里；新版本把它们单独存成一个文件。
程序会在首次读取时自动完成搬运，通常你什么都不会察觉。文件位置（供核对，
不需要主动修改）：

- 主设置文件：客户端 `config/session` 目录下的 `session.json`
- 任务参数新文件：同一目录下的 `workflow.json`
- 搬运前的原始备份：同一目录下 `.migrations/workflow` 文件夹

## 情况一：还没有迁移（新文件不存在）

**表现**：一切照旧，或升级后第一次启动。

1. 正常启动客户端即可；读取任何脚本参数时会自动完成搬运。
2. 搬运完成后旧位置里的参数副本会被删除，参数原样出现在新文件中。
3. 搬运前原始内容会自动备份到 `.migrations/workflow` 文件夹，随时可以核对。
4. 不需要手动创建或编辑 `workflow.json`——它不存在时程序才会从旧位置读取。

## 情况二：迁移中断（升级或搬运做到一半退出）

**表现**：升级过程中关机、崩溃或强退后，脚本参数看起来丢了或少了。

1. **不要手动新建 `workflow.json`**，直接重新启动客户端。搬运是可重复的：
   只要做了一半，下次启动会接着完成。
2. 重启后检查某个常用脚本的参数是否恢复（打开该脚本的设置看一眼）。
3. 如果参数仍未恢复：关闭客户端，检查 `config/session` 里
   - `session.json` 是否还能打开（是否仍是旧参数）；
   - `workflow.json` 是否已生成但内容不完整；
   - `.migrations/workflow` 里是否有带文件名的备份。
4. 什么时候该人工修复：重启一两次后参数仍未恢复、且 `session.json` 打开是
   乱码或明显残缺时，从 `.migrations/workflow` 里找到最近的备份文件核对
   内容，再决定恢复哪一份。拿不准就把整个 `config/session` 文件夹打包发给
   作者排查，**不要凭记忆手敲参数覆盖文件**。

## 情况三：已经迁错（新文件内容不对 / 参数串了）

**表现**：迁移完成后发现脚本的参数不是自己设置的那套（比如被别的账号或
默认值覆盖）。

1. 先确认没有登录错误的同步账号：参数文件是账号级同步的，多账号共用一台
   电脑时，后同步的一方会覆盖先同步的一方，这是正常行为而不是迁错。
2. 确认确实迁错后，关闭客户端。
3. 到 `.migrations/workflow` 找到备份文件，打开核对自己原来的参数。
4. 用备份内容修复 `config/session/workflow.json`（整份替换，不要只改一半），
   或者在客户端里重新把参数设置一遍——重设同样可靠。
5. 什么时候该人工修复：`workflow.json` 打不开、内容明显不是合法的参数表
   （乱码、截断）时，程序会拒绝读写参数来保护现有数据，此时必须用备份
   人工修复或删除该文件后重启让其重建；删除前先留一份副本。

## 情况四：检测到冲突（提示「配置已更新/存档冲突/写入冲突」）

**表现**：保存或启动时提示参数文件已被其他程序、另一实例或同步修改。

1. 先关掉多余打开了同一个客户端目录的实例，只保留一个。
2. 按提示重试一次保存；多数冲突在关掉竞争方后自然消失。
3. 提示「原件存档冲突」时，说明备份位置出现了两份不同的原始内容：
   不要删除备份文件夹，把 `config/session`（含 `.migrations`）打包发给作者
   核对后处理。
4. 提示「磁盘配置已更新，请刷新后重试」时，刷新/重新打开对应编辑窗口再
   保存即可；反复出现说明有别的程序（如编辑器、同步盘）在持续改动该文件，
   把它停掉再保存。
5. 什么时候该人工修复：同一冲突关掉所有已知程序后仍然反复出现，或按第 3 条
   出现存档冲突——这已经超出客户端能自动安全裁决的范围，需要人工核对。

## 通用原则

- **优先重启**：迁移与恢复逻辑是可重复的，重启能安全地接着做。
- **先备份再动手**：任何手动修改前，把 `config/session` 整个文件夹复制一份。
- **不要把备份文件夹当垃圾清理**：`.migrations/workflow` 是唯一的原始内容
  留档，冲突和错乱时都靠它核对。
- **拿不准就求助**：把 `config/session` 打包发给作者，比自行编辑安全得多。
