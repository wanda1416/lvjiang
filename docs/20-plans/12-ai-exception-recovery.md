# AI 异常导航恢复与安全续跑方案

> 状态：规划。提案，尚未实施；不表示视觉接管已可用。
> 代码核对基线：主仓 `3beec58a`。已有基础能力与下文建议分开描述；实施前重新核对代码。

## 1. 目标与非目标

在确定性脚本的有限重试仍无法确认目标页面时，可选引入可识图模型辅助恢复导航，
在程序确认恢复结果后继续自动化。正常路径仍由现有脚本完成，AI 仅低频、按需介入。

首个目标是关闭非交易遮挡、从错误页面返回、打开已声明的目标页面。
不以“任意异常都能自动救回”为目标，也不承诺恢复成功率、费用或延迟。

本方案不包括：

- 全程视觉 Agent、通用 Agent 平台、新账户/认证体系或云端截图存储。
- 让模型执行 shell、任意 Python/DSL、修改配置、任务结果或 Profile 账本。
- 自动购买、删除、领奖、切换账号，或替用户回答业务决策确认。
- 遇到任意异常自动接管，包括鉴权/配置错误、设备断连、用户停止、账本冲突及交易状态不明。
- 保存和恢复任意 DSL 指令快照，或任务退出后盲目重跑整项任务。

已有无人值守规则见[无人值守批量](../30-design/02-decisions/01-batch/03-unattended-batch.md)，
已有 AI 请求边界见[AI 连接与请求边界](../70-agent/05-ai-connection.md)。
本文只定义待实施的增量，不改变这些功能的现行契约。

## 2. 现有能力与待补能力

| 关注点 | 已有能力 | 本方案待补 |

本地仍必须执行同样的结构和权限校验。复用现有传输、凭据及错误处理，不另造认证链路。

## 3. 恢复语义：不是一句“处理完毕”就续跑

### 3.1 当前 pause、confirm 与退栈行为

- 有效无人值守同时要求运行草稿开启与配置组声明异常恢复工作流。
- 无人值守回调仅在 `pause` 时抛出 `UnattendedInterrupt`；
  `confirm/input/choose` 保留正常交互，不能一概自动回答。
- `UnattendedInterrupt` 退出当前任务调用栈，再由调度器按既有规则恢复公共初始页。
  它不是把解释器挂起并保存下一条指令。
- `_exec_body()` 的指令位置是局部变量，`_run_proc()` 在退出时恢复调用方变量；
  当前没有任意位置的可恢复指令快照。

基线中的 `nav_game_plans_to_main()` 已将终点失配改用 `pause`，
所以无人值守不会再在该处等待 `confirm`；这仍是现有异常恢复，不是 AI 接管。

依据（均仅源码检出）：
[无人值守回调](../../src/lvjiang/core/batch/unattended.py)的 `_unattended_ui_callback()`、
[DSL 执行器](../../src/lvjiang/workflows/engine/core.py)的 `_exec_body()`、
[子过程执行](../../src/lvjiang/workflows/engine/data_ops.py)的 `_run_proc()`、
[备战返回流程](../../config/system/workflows/subcall/loadout/game_plans.wf)的 `nav_game_plans_to_main()`。

### 3.2 两种回交契约

| 介入时机 | 允许的回交 | 不允许的做法 |
|---|---|---|
| 任务尚在声明的安全检查点内 | 保留调用栈，AI 恢复后由程序验证，重读状态并继续这一段 | 沿用旧 OCR/选中项，直接跳过验证 |
| 已抛异常、当前任务已退出 | 验证公共初始页后按既有调度继续后续任务 | 声称能从被中断的任意指令继续，或盲重跑有副作用的整项任务 |

要续跑当前任务，应在原有异常 `pause` **之前**调用声明的恢复入口。
成功则回到检查点重读；失败才进入原有异常/人工处理路径。
不通过拦截弹窗中文去猜测目标，也不全局替换所有 `pause` 或 `confirm`。

模型的 `done` 只表示“申请程序验收”。恢复成功只能由程序基于新画面与业务上下文判定，
不能由自然语言“处理完毕”、模型自报置信度或 `safe=true` 决定。

## 4. 最小职责与插件边界

只补三类增量职责，不要求建立三套独立子系统：

1. 扩展现有 AI 适配器：图像、结构化动作、用量与错误。
2. 有界恢复协调：本次运行/目标、停止、总时限、调用/动作预算、交接结果。
3. 声明式检查点：插件或业务流程声明触发原因、目标、允许导航动作、独立验证与重试位置。

公共 `core`、UI 和通用 `workflows` 引擎只认识 hook 协议，
不得导入具体插件、拼接插件内部路径，或硬编码游戏名和业务页面常量。
具体页面判断及导航动作由插件通过 hook 声明；业务示例不进入公共层分支。
hook 名称、参数及注册形状在实施时确定，不把本文示例当作已存在 API。

建议恢复循环运行在当前工作流执行线程中，网络使用可取消的异步等待；
Qt 主线程只处理进度信号和停止操作，不执行网络或阻塞等待。
原 DSL 在检查点内不再继续发输入，AI 属于同一个运行实例，不另开并行设备任务。

保留现有目标/用户占用直到线程结束，不因恢复而释放；交接前释放可能遗留的按键。
人工接管需先取消 AI，避免同一设备出现两个输入来源。

## 5. 有限截图—动作—验收循环

```text
确定性识别/有限重试失败
  → 检查恢复声明、启用授权、设备状态与剩余预算
  → 停在安全检查点，保留运行和目标占用
  → 当前目标的新截图 + 最短必要上下文 → 模型
  → 校验单个结构化动作 → 检查停止/时限/目标/观测关联 → 执行动作
  → 重新截图与程序检查；必要时在预算内继续
  → done 申请验收 → 程序独立验证目标与上下文
  → 成功：检查点重读后继续
  → 失败/超限：原有异常恢复或失败退出
  → 用户停止：优先停止，不再操作游戏进行恢复
```

### 5.1 结构化动作

以下是待实施协议的表达示例，不是可直接调用的 API，也不是供应方已支持的承诺：

```json
{
  "observation_id": "本次观测ID",
  "action": {
    "type": "navigate",
    "name": "本检查点声明的导航动作ID"
  }
}
```

动作类型先限于 `navigate`、`wait`、`done`、`unable`：

- `navigate` 只能引用该检查点声明的语义动作，例如返回或关闭非交易遮挡。
- `wait` 使用宿主规定的有界等待，也计入总预算；不能让模型指定无限等待。
- `done` 申请验收；`unable` 放弃本次恢复，返回明确失败。
- 严格检查类型、字段和动作是否在允许集合内，拒绝多动作串、未知动作及无效参数。

MVP 不开放任意坐标、按键序列或代码。以后如确需坐标点击，应另行评估并校验当前目标、
图像映射及允许区域；“坐标在窗口内”本身无法保证不会点中购买按钮。
不能只依赖模型对动作风险的描述，无法确认安全时应停手。

### 5.2 图像、坐标与迟到动作

- 每步重新获取当前目标画面，不把上一次 `screenshot from last` 当下一步观测；
  截图失败不能拿旧图继续点击，底层通道故障按既有机制处理。
- 图像编码明确 BGR/RGB、缩放和裁剪；若后续支持模型坐标，须逆向映射到原捕获区域，
  再复用现有画布/窗口偏移与输入后端，不能把缩略图像素当作 Windows 全屏坐标。
- Android 也要核对方向和尺寸；MVP 不将 PC 的 ESC 或窗口激活假设套到 Android。
- `observation_id` 绑定宿主发出的观测。动作前检查本次运行、当前目标、相关页面状态和取消标记；
  迟到响应、目标变化、观测不再适用或时限过期后不得落输入。
- 不要求逐像素锁帧，动画不必触发新事务系统；由具体目标声明足以判定动作是否仍适用的条件。

复用依据（均仅源码检出）：
[截图快照](../../src/lvjiang/workflows/capture_snapshot.py)的 `capture_frame()`、
[坐标换算](../../src/lvjiang/workflows/base/coords.py)的 `_ratio_to_screen()`、
[任务停止](../../src/lvjiang/ui/main/run_control.py)的 `_request_stop()`。

### 5.3 预算、取消与退路

同时限制总恢复时限、单次请求超时、总调用数和动作数；预算必须贯穿整轮，
不能每次模型返回就重新开始计时。具体默认值留待试验确定，本文不设未经测量的性能目标。

复用 `stop_event/task_stop_event`，将取消传入网络等待，返回后及动作前再次检查。
取消不能只改变 UI 状态；停止或预算到期后，迟到响应不得再执行。
本地取消不保证提供方没有处理已发请求或不产生费用。

无进展、非法输出、拒绝、网络失败、验收失败或预算耗尽时结束本轮，
按检查点声明走既有 `pause`/恢复工作流或记录失败；无人值守不新增无限等待的确认框。
用户主动停止时不得再重启/导航游戏。恢复失败不能改写成业务成功。

## 6. 权限、隐私与不可信画面

- 默认不因为“已配 AI 接口”或“开了无人值守”而自动开启截图接管。
  新功能需独立可选启用，告知截图发送给用户选择的模型提供方及可能产生调用费用。
- 现有 AI 配置是主动配置能力，不将其描述成隐私违规；新增用途需要对应告知与范围控制。
- 只发送当前目标窗口/必要裁剪与最短任务上下文，不发送账户凭据、整份 session、账本或完整日志。
  聊天/昵称等可按必要性遮盖，不声称可以自动完美脱敏，也不能遮掉恢复目标所需信息。
- 屏幕里的提示、聊天及“忽略规则/执行命令”等都是不可信视觉数据，不是操作授权。
  宿主动作白名单始终生效，不暴露 shell、任意代码或账本写工具。
- MVP 不自动购买、删除、领奖或切换账号；未来若有需要，须单独定义授权及安全契约。
- 记录恢复原因、动作、预算与程序验收结论，UI/日志/历史结论一致；默认不记录模型原始正文、
  凭据或整段截图会话，不将新增恢复记录伪装成任务完成记录。

## 7. 货运导航 MVP

以“物资采购返回后未确认货运材料页”为一个明确检查点，只恢复页面，不扩展成通用游戏 Agent。
货运是本地业务流程示例，不要求系统为用户生成、覆盖或下发个人 `config/local` 脚本。
首版建议由桌面宿主控制单个 Android 目标，复用桌面 AI 设置；
这不表示手机端已有 AI 凭据存储或本地接管能力，手机端运行不在首版承诺内。

1. 正常返回与有限识别失败，且尚未退出当前调用栈时，申请本检查点的 AI 恢复。
2. 保留当前材料槽位等必要上下文，只允许关闭非交易浮层、返回或打开货运材料页面。
3. 模型 `done` 后，程序用新截图确认目标页，并以确定性动作重新选择当前材料槽位。
4. 重新读取“是否仍缺材料/是否已提交”，成功后从这一读取检查点继续，
   不沿用旧 `$selected`，也不默认继续操作另一个已被选中的材料。
5. 不从“再次购买”开始重放，不让 AI 自行补货、决定花费、领取奖励或写周配额。
   领奖之后的异常需要单独检查点，不能盲目重放领奖/账本写入。
6. 若模型认为已到货运，但程序无法验证，不用模型结论豁免检查；失败退出或先修识别。

确定性缺陷应先处理：基线中的批量业务执行出口尚未统一检查顶层失败返回，
可能出现业务 `failed/return -1` 而批量进度/历史显示成功；返回页分类与末次识别的已知问题也应先修。
接入 AI 不能掩盖这些错误，更不能把模型恢复失败包装成任务完成。

批量修正应复用 `return_failure_message()` 的通用协议，不解析某个任务的嵌套字段。
依据（均仅源码检出）：[业务执行出口](../../src/lvjiang/core/batch/stages.py)的 `_run_script()`、
[调度器](../../src/lvjiang/core/batch/scheduler.py)、
[顶层返回协议](../../src/lvjiang/workflows/result_protocol.py)。

## 8. 分阶段实施与验收

本节是建议顺序，不代表已启动实现或已通过新功能验收。

| 阶段 | 范围 | 进入下一阶段前的验收 |
|---|---|---|
| 前置修正 | 固定代码缺陷、错误记账、异常与业务确认分类 | 业务失败与批量进度/历史一致，既有行为回归通过 |
| 只观察试验 | 合成图或经明确授权的截图，输出建议但不落输入 | 所选接口确实支持图像及动作格式；取消、错误、用量可观测 |
| 单目标导航 MVP | 一个货运返回检查点、一组语义动作、独立验证与有限预算 | 当前任务可安全回交，未知/危险动作及假 done 被拒 |
| 按需扩展 | 实测后再增加 Windows 或其它已声明检查点 | 逐目标验证坐标、停止、后置条件与原有退路，不一键接管所有异常 |

最低测试矩阵：

| 场景 | 必须满足 |
|---|---|
| 关闭功能或无恢复声明 | 原行为不变，不隐式发图或调用模型 |
| 当前目标被占用 | 恢复属于同一运行，第二输入方不能同时启动 |
| done 但页面/材料上下文不符 | 不续跑，不能改成成功 |
| 陈旧观测、窗口/方向/尺寸变化 | 拒绝不适用动作，重新观测或失败 |
| 非法动作、代码、购买、账号切换 | 宿主拒绝，不按模型自报风险放行 |
| 网络超时、取消、总预算耗尽、迟到响应 | 可结束等待，之后不落输入，Qt 主线程可操作 |
| 恢复成功 | 新截图验收，从当前槽位重读，不重买、不重复领奖/记账 |
| 恢复失败或用户停止 | 结论真实，分别走既有失败退路或立即停止 |

验证先用真实引擎公开入口、临时配置/用户根、合成截图/OCR/输入和模型替身，
保留真实配置写保护及离屏 UI 约束，再在明确授权后做目标设备与真实模型试验。
不以单个合成用例代替真机恢复验证，不为此跑无关全产品 CI。

## 9. 已有验证、未测边界与成本测量

可行性分析阶段在上述代码基线完成：

- 66 项现有定向测试通过：AI 请求/设置取消、无人值守、host abort、备战返回 `pause`。
- 6 项隔离合成探针通过：图像消息转发、原生工具回复缺口、回调返回保留栈/异常退出、窗口偏移映射。

这些结果只证明已有基础契约，不表示新恢复循环、hook 或货运 AI 接管已实现。
未调用真实付费模型、上传用户截图或运行游戏；真实视觉定位、坐标落点、
交易安全、恢复成功率、延迟与成本均未测，不据此给出承诺。

成本取决于异常发生次数、每次调用步数，以及各次图像/上下文/输出用量；
若持续重发全部历史截图，上下文成本还会增长，因此应限制历史图像数量。
不同提供方图像用量计法不同，不能仅以请求数推算价格。

后续试验分别记录每轮调用数、实际可得用量、总耗时、取消/失败原因和程序验收结果；
提供方未给用量时不编估计值。默认预算应基于这些实测再确定，保持低频按需调用。
