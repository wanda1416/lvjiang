# 官方配置增量更新需求

> 状态：规划（2026-10-11，基线 v0.13.15）。架构方案已整理，尚未实施；后续开发与正式切换须另行安排。

## 目标

作者可以不发布新版应用，提前更新与现有应用兼容的官方配置；用户自己的配置不受影响。

支持拼写修正、场景与区域补全、布局、默认调律配置和已有 WF 更新；在应用维护频率降低后，
仍可持续维护现有代码支持的任务。没有网络时依靠完整预置或此前有效更新正常使用。

此前“维护成本增加后再考虑”的初步草案已由本需求及配套架构方案细化取代。
整理方案不代表授权实施，代码切换前仍以现行配置加载规则为准。

## 业务边界

| 概念 | 目标含义 |
|------|--------------|
| 公开预置 | 随应用提供的完整官方基底，下载不到更新也能使用 |
| 公开增量 | 针对当前三段正式版本的累计修正，不要求逐个安装历史更新 |
| 会员包 | 无随包预置，独立在线发布与授权，不跟随公开增量的版本周期 |
| system | 客户端已应用的官方内容，吸收公开增量和有效会员内容 |
| local | 用户修改，按配置类型语义合并或整体覆盖 system |

会员专属内容不进入普通安装包或公开增量。公开内容来自官方 system 源文件；
用户 local、Session、数据库、凭据和私人截图不作为公开发布来源。

官方 system 源目录内所有文件均可下发，包括 app.yaml、说明文件、未知扩展名和客户端
尚不能识别的内容；不设置配置类型白名单。下发与加载分离：未知文件原样安全安装，
加载器仅消费自身支持的内容，不自动执行未知文件，也不凭安装成功宣称支持了新功能。
路径安全、包完整性、渠道归属和发布内容审查仍然有效，不能写出 system 安装边界。

## 更新规则

1. 公开更新默认适用于 `[x.y.z, x.y.(z+1))`。第四段版本属于同一兼容系列，
   新的三段版本从自己的预置开始；不自动采用更旧或更新系列的包。
2. 每系列保留原始预置备份及历次公开增量；会员包也归入统一更新档案，不增加配置读取层。
3. 下载并校验成功后立即应用、刷新相关界面和内存配置，无须重启。
   正在执行的任务保持原配置快照，后续任务使用新内容。
4. 下载不到则忽略本轮更新，继续使用当前可用内容。不得阻断启动、撤销已安装内容或
   将部分下载生效；明确授权失效与暂时断网分别处理。
5. local 与 system 保留两类规则：聚合配置语义合并，独立实体整体覆盖。
   官方更新不覆盖用户设置或编辑草稿。
6. WF 支持更新已有官方脚本，关联场景、布局和资源必须完整。会被当前消费者读取却
   依赖未发布代码的改动不得作为有效修正发布；未知文件可先行下发留存。
   下一版应用承接已发布的公开修正。
7. 用户可以关闭应用，删除 system 后从对应原始预置备份恢复；系统正确识别恢复状态。

## 发布与版本职责

管理控制台的推送包含公开推送、会员推送两个子页，支持线上状态查询、变更与依赖审核、
确认发布和失败重试。公开目标自动采用当前线上正式系列，会员采用独立包发布机制。
发布修订用于追踪更新，文件摘要用于识别和校验内容。新机制不再以文件内容版本仲裁
system 与在线内容；content_version 在新协议交付后统一为 1，随后退出。

## 验收标准

- 同系列含第四段客户端能更新，下一组三段版本不加载旧包；新装客户端能直接应用最新累计增量。
- system 内所有文件均可下发，不因客户端未知而拒收；当前会消费的内容仍需通过兼容检查。
- local 不被发布或同步覆盖；断网、撤回、关闭在线更新时仍有可用的随包基底。
- 更新完成立即刷新有效配置和界面，当前任务不混用新旧 WF 或识别资源。
- 应用升级后重新验证缓存适配；下载、校验、应用中断均不会生效半套内容。
- 公开与会员更新互不丢失有效内容；会员授权遵守原协议，普通网络失败不影响可用公开功能。
- 人工恢复原始预置后，更新状态与实际内容一致。
- 普通安装包不包含会员专属内容；重复重试不产生新的发布修订。
